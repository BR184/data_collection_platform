## 1. 测试要回答的问题

1. 响应模板缺少合法计划解决日期时，是否仍按响应时限加标；合法响应模板或回复模板是否取消响应延期。
2. 原有解决延期判定是否保持，两个延期标签是否分别正确加、摘。
3. 实际 GitLab 评论和标签变化，能否自动经过镜像、事实、队列、GitLab API，再同步回来收敛。
4. 未收敛、关闭开关、重启、并发接管和失败时，是否停止不具备资格的写回并保留待处理工作。
5. 其他标签、范围外议题和用户正在使用的服务是否保持原状。

### 2.4 调度和触发

当前没有独立的“立即执行延期写回”HTTP 接口。手动增量同步接口只提交同步，不等价于登记新一轮写回请求。

可在**独立测试实例**把 `CUSTOMER_ISSUE_DELAY_CHECK_DELAY_MS` 从默认 3600000 调到 60000，便于等待新一轮；记录原值，结束后恢复。其余关键默认值如下：

| 参数 | 默认值 | 验收用途 |
| --- | --- | --- |
| `CUSTOMER_ISSUE_DELAY_PROGRESS_CHECK_DELAY_MS` | 60000 ms | 恢复持久等待和分页，不登记新请求 |
| `CUSTOMER_ISSUE_DELAY_WRITEBACK_WORKER_DELAY_MS` | 5000 ms | 消费写回队列 |
| `CUSTOMER_ISSUE_DELAY_PROGRESS_LEASE_SECONDS` | 120 s | 来源进度租约 |
| `CUSTOMER_ISSUE_DELAY_WRITEBACK_LEASE_SECONDS` | 120 s | 作业租约 |
| `CUSTOMER_ISSUE_DELAY_ENQUEUE_BATCH_SIZE` | 200 | 有界分页登记 |
| `CUSTOMER_ISSUE_DELAY_PRE_WRITEBACK_SYNC_ENABLED` | true | 开启时要求前置同步；关闭则仅重算事实 |
| `CUSTOMER_ISSUE_DELAY_PRE_WRITEBACK_SYNC_TABLES` | issues,notes,label_links,labels | 常规轮次前置刷新，保持完整默认清单 |

平台总调度与写回 worker 均须启用。业务许可仍只有数据源页面“延期标签写回”开关；上表的 worker/调度参数用于运行控制，不是第二套业务许可。

识别一轮触发时核对日志 `Customer issue delay closure cycle submitted`，以及进度请求修订和本轮 mirror_run_id。所有阶段可能很快通过，不能要求每阶段都在人工轮询截图中被捕获。

评论物理删除的场景（R17、R19及回复删除）须先核对删除感知入口。普通 `updated_at` 增量无法发现一条已消失的源记录；仅重复四表增量不构成删除证据。应使用环境已配置的删除事件入口或现有删除对账，并验证 ODS `mirror_deleted` 后再核对事实。本批关闭了 GitLab 钩子，默认删除对账也关闭，首次删除场景因此等待360秒未收敛；随后仅在独立测试进程设置 `GITLAB_DELETE_RECONCILIATION_ENABLED=true`、`GITLAB_DELETE_RECONCILIATION_INTERVAL_MINUTES=1` 验证自动对账。1分钟是本地验证设置，生产周期须按实际来源和负载确定，不能直接照搬。

## 3. 预期计算方法与模板

### 3.1 时间和标签记号

- `T`：该轮实际判定时刻；准备样本时记录 `T0`。普通人工用例远离边界，不能把准备时刻直接当成数分钟后运行时刻。
- `R`：`响应已延期`；`S`：`解决已延期`；`∅`：两个延期标签都没有。其他标签在所有用例中均须保持集合不变。
- 响应默认样本：项目 325、open、创建于 T0 前 4 天、P1、无状态闭环标签，创建日期不早于 2026-01-01。每例默认预置 R，以便检查需保留还是摘除；加标用例另外复制一条初始不带 R 的议题。
- 解决默认样本：创建于 T0 前 20 天、open、P1、无闭环状态；响应模板填 T0 后 30 天的合法日期。响应不延期，解决期限受 18 天上限约束，默认应带 S。

当前响应代码先取 `Duration.toHours()`，再严格比较 `> 24/48/72`。因此 P1 的 24小时59分仍不延期，25小时才延期；P2/P3 对应49/73小时。这是当前实现的验收口径，与“超过24小时立即延期”的分钟级解释不同，必须单列记录，不能在测试中悄悄改规则。

解决判定使用 `now.isAfter(resolve_deadline_at)`，等于截止时刻时不延期；日期型计划时间解析为当日00:00。D8 的“15个工作日”不作为本次期望，当前保留最多18天及既有解决日期解析方向。

## 4. 每条真实 GitLab 用例的执行流程

1. **写前记录**：核对样本身份、创建时间和状态，保存 GitLab 当前全部标签、完整相关评论、平台三列延期值及进度/队列基线。
2. **修改源端**：按用例在测试 GitLab UI 新建、编辑或删除评论，或改变标签/议题状态。除时间边界和故障注入项外，不直接改平台表。
3. **等真实同步**：先观察自动增量把变化带入 ODS，再进入事实。需手工增量时使用页面已有入口，单独记下运行号，不把该动作当作写回成功。
4. **等新轮请求**：记录本轮请求修订和绑定的前置运行，确认 issues、notes、label_links、labels 均成功；来源资格不满足时保持等待。
5. **核对重算与入队**：检查三项延期字段、授权版本，以及该议题本轮差异。已一致时可以没有新作业；历史作业仍在不等于本轮又执行。
6. **核对真实写回**：由后台 worker 调用真实 GitLab API。保存成功/失败日志和 GitLab UI/API标签结果；人工不能替平台加摘目标标签来制造通过。
7. **核对再同步和第二轮**：等待写回变化进入 ODS/事实，再跑一轮。差异应为空，不再出现不必要的实际 PUT；不能只看队列行数，因为同一行会被复用。
8. **核对保护项**：两项无关标签、范围外对照议题均不变，当前测试没有影响既有平台实例。
9. 填第10节记录表。超出本批观察预算时记录停在哪一层、last_error 和运行号，判为待查或失败；不得改阶段、版本或租约强行放行。

建议先完成第7节详细示例，再批量执行第5、6节。小样本可约定每例观察5分钟；这是人工观察预算，不是产品固定超时，也不代表目标内网性能承诺。

2026-10-27来源复核：本节S12/S14描述当前候选行为，不能标为“与老平台一致”。老平台按API默认新到旧顺序取首个可解析响应计划，也没有整数天数分支；现候选取较早评论且可解析7天等数字。两套预期分别保存，未经裁定不改业务。用户另已确认：关闭状态同步并统计刷新后不再进入延期统计，因此本轮先不修改关闭后的旧标签保留；该范围不包含其它新旧差异。

## 6. 机制、故障与恢复用例

这些用例先完成正常真实链路，再逐项注入。需要断点、可控屏障、代理返回码或数据库事务的用例，由执行者在专用实例操作，人工复核证据；不能只点击页面便标成通过。

| ID | 操作 / 故障注入 | 必须观察到的预期 |
| --- | --- | --- |
| G01 | 页面写回开关关闭，源端制造明显延期 | 事实仍可判延期，GitLab标签保持原样，无写回PUT；不把页面命中当成已写回 |
| G02 | 开关打开，完整前置与事实收敛 | 本轮先绑定成功镜像，再取得事实授权；作业成功，真实标签符合事实 |
| G03 | 本轮前置镜像未结束，另一个无关运行先成功 | 不授权、不借无关终态推进写回；本轮完成后再继续 |
| G04 | 四表中一表失败 / 缺表 | 不授权；记录原因，失败轮重启/退避，不跳过失败表 |
| G05 | 事实来源尚无READY / 有未发布根 / 全量意图未结算 / 标签历史不完整 | 逐项验证不发送；条件恢复并真实收敛后可继续 |
| G06 | WAIT_MIRROR或WAIT_FACT阶段重启测试后端 | 从持久行恢复，不丢等待；不因重启提交并发重复镜像 |
| G07 | 入队后暂时停测试worker，页面关闭并保存开关，再启动worker | 授权撤销，未发送任务跳过/等待，GitLab不变；已发出的请求需单独记录 |
| G08 | G07后重新开启 | 新一轮前置和授权后才允许发送，不复用被撤销的旧许可 |
| G09 | 缺地址、缺令牌、来源停用、配置缺失或歧义 | 各自不发送，原因可查；不得回退默认来源。配置歧义仅在独立PG故障用例构造 |
| G10 | 已授权后，相关事实版本变化或相关同步开始 | worker执行前复核拦截，等待新资格/授权，不按旧差异直接发送 |
| G11 | 两执行者同时领取同一来源/作业 | 同一时刻仅一有效领取者；旧token结算不影响新领取者 |
| G12 | 发送中登记同议题的新差异 | 任务修订增加，旧完成不能清除新工作；下一轮按当前事实收敛 |
| G13 | 真实GitLab返回401/403；受控代理分别返回400/404 | 不可重试错误转DEAD，记录HTTP码，无无界自动重试；真实API与代理结果分开登记 |
| G14 | 受控代理返回429/5xx，之后恢复真实GitLab | RETRY_WAIT并有界退避，恢复后成功或按当前事实跳过；记录次数上限 |
| G15 | 代理模拟“GitLab已写成功，但平台未收到响应” | 记发送结果未知；再同步后按当前标签收敛，保护无关标签，不承诺HTTP只发一次 |
| G16 | 当前标签查询异常、ODS议题缺失 | 不用事实旧标签补齐，不凭空作加摘；数据库恢复后再评估 |
| G17 | 超过一页候选，等待/分页中插入新请求（R1） | 本轮processed_revision保持；完成旧轮后新请求仍待处理，下一轮有新前置 |
| G18 | 进度租约到期未接管、已接管、事务中到期（R2） | 原持有者不能推进/授权/结算；事务中到期使用真实时钟判定 |
| G19 | 重算后被接管 / 相关版本漂移（R3） | 重算与generation全部回滚、无旧授权，新持有者归属保留 |
| G20 | 改评论后走自动增量；另批走手工增量；最后走一次全量再自动增量 | 三种触发均正常进入同一事实/写回机制，水位与后续自动增量可持续 |

## 9. 通过标准与异常定位

**业务用例通过**必须同时具备：源端输入可见、ODS/事实匹配输入、资格正确、真实GitLab最终标签符合预期、无关标签和对照不变、第二轮收敛。截图只有延期页面命中，或只有作业SUCCEEDED，均不够。

**机制用例通过**必须有注入条件及前后状态证据；故障未实际触发记“未覆盖”，不能记通过。真实GitLab业务链与代理故障链分开统计，自动回归和人工验收也分开。

| 停点 | 先检查 |
| --- | --- |
| 无新请求 | 实际版本、业务开关、总调度、周期提交日志，是否仍在等待上一轮 |
| WAIT_MIRROR | 绑定运行号及四表任务，而非任意最近成功运行 |
| WAIT_FACT | READY、依赖、全量意图、未发布根、事件历史及相关在途运行，结合last_error |
| ENQUEUE或大量待处理 | 事实版本是否频繁变更、授权是否失效、分页游标和租约 |
| IDLE但标签未变 | 具体作业状态、worker启用与错误；IDLE本身不证明已写回 |
| 标签正确但页面不同 | 核对页面过滤范围、计划日期展示来源、统计排除和事实刷新，不直接改写回规则 |
| 下一轮再次相同PUT | 核对写回后ODS有效label_links是否收敛，是否存在旧平台或其他实例双写 |

整体报告按“通过 / 失败 / 阻塞 / 未执行”统计。任何必测项未执行时，本次真实接替验收不能写为全部通过；小样本通过不代表内网容量已验证。
