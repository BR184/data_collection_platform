## 老平台已确认功能

### 正式页宽表

老平台“缺陷原因分析”正式页是模块维度宽表，字段按原因大类分组：

- 需求问题：新增理解偏差、需求遗漏、新增需求、需求变更未同步。
- 设计问题：功能设计遗漏、设计方案不合理、场景考虑不全、术语、提示信息不合适。
- 编码规范：编码规范错误、功能编码遗漏、编码逻辑：计算与算法错误、编码逻辑：流程控制错误、编码逻辑：数据与状态处理错误、编码逻辑：业务逻辑错误、编码逻辑：集成与接口错误。
- 打包问题：环境配置问题、编译/打包/部署问题。
- 依赖问题：第三方库问题、算法不支持、机制不支持、前置数据异常、未识别的前后置任务。
- 精度问题：精度导致约束求解异常、精度导致算法执行异常。

老平台页面表格支持：

- 测试阶段下拉，默认选第一个测试阶段。
- 下载“缺陷原因统计表”。
- 每个原因列支持排序。
- 每个模块原因单元格可点击下钻到议题明细。
- “共计”行和“比例”行固定在底部。
- `共计` / `比例` 行不展示为可点击按钮。

### 原因字段兼容映射

老平台 `ModuleAndCauseTableRow` 中存在以下兼容映射：

- 新增理解偏差 = 新增理解偏差 + 需求理解有误。
- 新增需求 = 新增需求问题。
- 编码逻辑：业务逻辑错误 = 编码逻辑：业务逻辑错误 + 编码逻辑错误。
- 编译/打包/部署问题 = 编译/打包/部署问题 + 编译打包问题。
- 机制不支持 = 机制不支持 + 算法/机制不支持。
- 由修改其他问题引起的兼容匹配 `由修改其他问题引起的` 和 `是否由修改其他缺陷引起*是`，但该列不在正式页导出宽表中展示。

### 统计口径

老平台 `getModuleAndCauseTable` 口径：

- 先通过 `testingPhaseService.getByName(phase)` 展开测试阶段。
- 模块列表来自 `dropDownService.getModuleNameByProjectNameFromSpiderIssueData(phase, projectId, milestone)`。
- 数据范围来自 `spiderIssueDataDAO.findAllByCauseExist(phases, projectId, true, milestone)`，即只统计已填写议题统计/缺陷原因模板的数据。
- 按模块匹配时使用 `DataUtil.match(spiderIssueData.getModuleName(), moduleName)`，多模块会进入对应模块。
- 每个原因用 `DataUtil.match(t.getCause(), minorCause.getFindName())` 判断。
- 占比分母不是议题总数，而是“共计”行中所有正式展示原因列数量的合计。

### 导出

老平台导出入口：

- `POST /dataAnalysis/exportModuleCauseTable`
- 文件名：`缺陷原因统计表.xlsx`
- Sheet 名：系统测试用 `phase`。
- 导出使用 `ExportModuleAndCauseTableRow`，字段与前端正式页保持一致。
- 导出包含“共计”和“比例”两行。
- “比例”行保留两位小数并拼接 `%`。

### 多元看板图表

老平台多元看板中的“缺陷原因分析”不是模块宽表，而是按缺陷原因聚合的堆叠柱状图：

- 接口：`GET /dataAnalysis/getTestingPhaseAndCause`
- 导出：`GET /dataAnalysis/exportTestingPhaseAndCause`
- 每个原因按一级缺陷、二级缺陷、三级缺陷、建议四个系列统计。
- 原因按总数降序，相同时按一级缺陷数量降序。

## 新平台现状

新平台 `/question-metrics/defect-cause` 使用统一统计板：

- 后端服务：`SystemTestDefectCauseBoardService`
- 接口：`/api/statistic-boards/system-test-defect-cause`
- 支持测试阶段筛选、规则说明、下钻明细、CSV 导出、实时刷新。
- 当前表头仅包含 6 个原因列：需求理解偏差、新增需求、编码逻辑错误、环境部署问题、算法机制不支持、其他原因，以及总计。
- 当前总计 = 当前模块内 `reason_category` 非空的议题数。
- 当前原因统计基于 `issue_fact.reason_category` 单值字段。
- 当前规则说明写的是“只保留 issue_fact.reason_category 非空的议题”。

## 已发现缺口

### P0：原因字段不完整

新平台缺少老平台正式页的多数原因列。老平台正式页展示 24 个正式原因列，新平台当前只有 6 个原因列，无法做到字段和数据展示对齐。

缺少的代表字段包括：

- 需求遗漏、需求变更未同步。
- 功能设计遗漏、设计方案不合理、场景考虑不全、术语、提示信息不合适。
- 编码规范错误、功能编码遗漏、编码逻辑：计算与算法错误、编码逻辑：流程控制错误、编码逻辑：数据与状态处理错误、编码逻辑：业务逻辑错误、编码逻辑：集成与接口错误。
- 环境配置问题、编译/打包/部署问题。
- 第三方库问题、算法不支持、机制不支持、前置数据异常、未识别的前后置任务。
- 精度导致约束求解异常、精度导致算法执行异常。

### P0：原因统计粒度不一致

老平台按 `cause` 文本中命中的每个原因统计，规则汇总也要求“分子和分母都是缺陷原因个数，不是议题个数”。

新平台当前依赖 `issue_fact.reason_category` 单值字段，按议题归一后的单一原因统计。若一条议题包含多个原因，新平台会丢失多原因计数能力。

### P0：总计口径不一致

老平台正式表的“共计”是每个原因列的列总和；占比分母是所有正式展示原因列的数量合计。

新平台当前“总计”是当前模块内 `reason_category` 非空的议题数。该口径与规则汇总第 4.6.5、4.6.6 不一致。

### P0：缺少“比例”行

老平台正式页和导出都包含“比例”行，比例 = 指定原因总数 / 所有模块下所有缺陷原因个数总和。

新平台当前统一统计板没有“比例”行。

### P0：新旧模板兼容映射不完整

新平台当前原因字段仅体现粗粒度 `reason_category`，没有完整复刻老平台 `ModuleAndCauseTableRow` 的新旧模板兼容映射。

规则汇总明确要求至少兼容：

- 新增理解偏差 = 新增理解偏差 + 需求理解有误。
- 新增需求 = 新增需求问题。
- 编码逻辑：业务逻辑错误 = 编码逻辑：业务逻辑错误 + 编码逻辑错误。
- 编译/打包/部署问题 = 编译打包问题 + 编译/打包/部署问题。
- 机制不支持 = 机制不支持 + 算法/机制不支持。

### P1：模块行来源需要复核

规则汇总要求“模块筛选来自全量议题模块信息”。老平台正式页模块来自 `getModuleNameByProjectNameFromSpiderIssueData(phase, projectId, milestone)`。

新平台当前只对最终命中缺陷原因的议题展开模块并生成行。若某个模块在当前阶段存在于模块全集但当前原因数为 0，新平台可能不展示该模块行。

### P1：导出格式不一致

新平台统一统计板当前导出为 CSV；老平台正式页导出为 Excel 宽表，并包含多级表头、“共计”和“比例”行，比例行保留两位小数并带 `%`。

### P1：下钻明细匹配口径不一致

老平台点击某个模块 + 某个原因时，传入 `moduleName`、`phaseName`、`cause` 到 `ModuleTableDetail`。

新平台下钻按当前 `reason_category` 单值过滤，无法表达老平台部分合并列，例如：

- 点击“新增理解偏差”应命中“新增理解偏差”和“需求理解有误”。
- 点击“编码逻辑：业务逻辑错误”应命中“编码逻辑：业务逻辑错误”和“编码逻辑错误”。
- 点击“编译/打包/部署问题”应命中“编译/打包/部署问题”和“编译打包问题”。
- 点击“机制不支持”应命中“机制不支持”和“算法/机制不支持”。

### P1：多元看板的缺陷原因图表口径需要复核

老平台多元看板“缺陷原因分析”图表按原因统计一级、二级、三级、建议四个系列，并按总数/一级缺陷排序。

新平台多元看板的 `buildCauseChartOption(causeBoard)` 复用 `system-test-defect-cause` 统计板数据。该数据当前没有一级/二级/三级/建议四个系列，图表口径与老平台多元看板不一致。

### P2：标题和文案细节

老平台正式页下载文件名为 `{测试阶段}-缺陷原因统计表`，多元看板下载为 `{测试阶段}-缺陷原因分析`。

新平台当前统一统计板导出文件名是 `{boardKey}.csv`，文件名和用户可见下载内容不一致。

## 暂未判定为问题

- 新老平台 UI 风格不同，不作为缺口。
- 新平台筛选交互方式不同，不作为缺口；但筛选后的数据口径必须与老平台一致。
- 分页默认值差异不作为缺口。
