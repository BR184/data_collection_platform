# BI 看板技术架构与决策

## 运行形态

- BI 是数据采集平台内嵌的一级业务模块，不是独立站点、独立服务或外部消费者。
- 前端随现有 Vue 3、TypeScript、Vite、Element Plus 应用构建；后端随现有 Java 21、Spring Boot 单体构建，继续产出一个前端发布物和一个后端 JAR。
- BI 共用平台进程、端口、PostgreSQL 数据源、LDAP Session、RBAC、CSRF、日志、健康检查、Docker 和离线发布入口，不创建第二套登录、网关、配置中心或部署单元。
- 首期不做 Maven Reactor 物理拆分。详细决策、代价和未来重新评估条件见 `decisions.md`（D-01）。

```text
浏览器
  -> 数据采集平台 Vue / BI 一级模块
  -> 同源 /api/bi/**
      -> BI 薄网关
      -> 进程内 BI BFF / 页面应用服务
          -> BI 计算器与页面模型
          -> 平台只读事实/基础查询端口
          -> CAT 出站端口（仅单元测试、集成测试）
```

## 代码边界

### 后端

- 所有 BI 后端代码位于 `com.data.collection.platform.bi`，按 `api`、`application`、`domain`、`infrastructure` 分层；平台现有包不得反向依赖 BI。
- BI 只能通过显式构造参数和窄接口依赖平台能力，不能依赖平台 Controller、页面 DTO、前端接口、全局可变单例或进程内 HTTP 回调。
- BI 页面聚合、指标计算、来源版本校验和状态映射由 BI 独立实现。现有平台页面 Service 可以作为业务证据，不能直接成为 BI 页面应用服务；只有稳定事实、基础查询端口和成熟基础设施允许直接复用。
- BI 专属 SQL 只能封装在 `bi.infrastructure` 的只读仓储中，优先读取已发布事实或快照；Controller、图表适配器和浏览器不得拼 SQL，也不得绕过事实发布边界读取半成品。
- BI JDBC Adapter 在边界读取整数字段时必须接受驱动返回的 `Number` 原生表示并执行精确长整数转换，数据库 `NULL` 保持为空；不得依赖 `getObject(column, Long.class)` 的驱动特定跨类型转换，也不得用补零或 SQL 强制转换掩盖字段缺失和 Schema 漂移。
- `BiSourceDimension` 是 BI 内来源快照分组的唯一模型，承载真实 `sourceValue`、展示名和是否已识别；它不代表跨平台业务实体 ID。作者、模块和当前指派人等仅用于单页分组的来源名称必须通过该模型进入领域层，缺失值使用不与真实成员碰撞的显式未知组，不生成哈希或伪 ID。
- 编码合并请求在领域层使用来源感知的强类型身份：兼容态固定为 `source_instance + merge_request_iid`，正式态固定为 `project_id + merge_request_id`。代码规模、作者、模块、提交、走查质量、问题类别、扫描和注释率按自身依赖字段独立去重与校验，一个事实族冲突不得清空无依赖的其它区块。
- 字段级核对表约束业务语义与公式，基础设施 Adapter 负责把已核实的真实 `table.column` 映射到领域模型。字段名不同但语义相同直接维护为单一“等价映射”；不得因早期英文候选名不同而拒绝数据，也不得为此增加别名、回退或新旧模型双轨。

### 前端与图表

- BI 前端代码集中在独立功能目录，页面路由、状态、数据适配器、图表模板和 PNG 下载逻辑不进入平台现有看板模块。
- `product.md` 中每一种图表模板都必须有一个 BI 专属具体类；页面通过组合模板类、显式变体和数据适配器构建图表，不复制 ECharts option，也不创建包含所有页面条件的万能渲染器。
- 图表类只允许在 BI 看板内部复用。平台现有质量看板、代码走查看板和系统测试看板不得依赖、替换或改造这些类；双方只共同依赖 Apache ECharts 6。
- 可以复用平台通用布局壳、侧边栏、Element Plus 控件、图标、下载按钮视觉样式和通知能力，但图表容器、ECharts 生命周期、页面状态壳、完整数据 PNG 导出和响应式布局由 BI 独立实现。
- BI 页面视觉验收边界固定为物理显示器 `1920×1080`、最大化 Chrome 原生窗口；不得用强制 `1920×1080` 浏览器内容视口代替。六个阶段页面滚动到底时，最后图表必须完整显示在 Windows 任务栏上方且无横向溢出。其它分辨率和非最大化窗口不属于本阶段显示承诺，不通过平台全局滚动规则为其增加专用适配。

## 进程内 BFF

- 保留 BFF，但它是 `com.data.collection.platform.bi` 内的页面编排层，不是独立进程或网络代理。
- 六个页面各有独立 API 和应用服务；BFF 负责冻结请求范围与来源版本、调用同页查询、执行 BI 计算、校验守恒关系、生成页面 DTO，并把空数据、不可计算、来源不完整和失败映射为明确状态。
- 单个页面只访问一个业务数据来源：需求、设计、编码和系统测试访问平台；单元测试和集成测试访问 CAT。不存在为了同一页面并行拼接平台与 CAT 的流程，也不要求两个平台共享批次号。
- 同页内部查询可以在实现阶段基于实测采用有界并行，但并行只是延迟优化，不能承担一致性；必须先固定同一读取上下文，并具备统一截止时间、取消和失败收敛。首期不预设线程池、缓存或并发数量。
- 页面级 `ERROR` 高于业务区块状态：前端只展示一次明确失败原因和重试入口，不继续把缺失业务区块渲染成 `INCOMPLETE`，也不显示空来源版本或空规则版本。
- 六个页面的区块键由页面计算器/应用服务固定定义；正常、空数据、来源冲突和异常响应都返回完整集合。前端只消费后端明确状态，不能把缺少区块键转换为“数据暂不完整”。固定键集合见 `data-contracts.md`。

## 平台兼容模式边界

- BI 不创建兼容/正式模式开关、设置项、请求参数或回退链。数据采集平台现有兼容模式总开关及其页面读源规则是唯一权威，BI 与对应平台页面读取同一模式下的同一类来源。
- 每次 BI 页面请求在开始时读取并冻结一次平台兼容模式上下文，需求、设计和编码查询在整个请求内保持同一模式；不得逐图重复读取开关、同时查询兼容态和正式态来源、拼接两种模式结果，或在一侧为空时静默回退另一侧。系统测试仍只读取已发布 `issue_fact`，不因代码走查/评审读源切换而改变。
- 内网真实部署的常态是兼容模式开启，几乎不会关闭；兼容态是主要运行和发布验收路径。正式态仍必须保持逻辑正确和可测试，但不得据此为 BI 建立第二套配置或实现。

### 编码三类事实边界

| 事实族 | 兼容态 | 正式态 | 服务区块 |
|---|---|---|---|
| 代码规模与维度 | `code_review_match_mode_records` | `code_review_formal_records` | 代码趋势、合并请求数、人员贡献、模块代码增量 |
| GitLab 提交 | `merge_request_commit_fact` | `merge_request_commit_fact` | 提交趋势（含按日/周的提交次数） |
| 人工代码走查 | `code_review_match_mode_records` | `code_review_formal_records` | 整体/模块人工走查质量、问题分布、单次散点、静态扫描、注释率和质量趋势 |

- 编码页人工走查兼容态复用平台兼容表 `code_review_match_mode_records`，与代码规模类同一读源，不再维护独立的 BI 独占走查表。
- `merge_request_diffs` 和 `merge_request_diff_commits` 属于平台 GitLab 推荐同步与血缘，不由 BI 另建 GitLab 抓取任务；最新 Diff 的稳定提交 SHA 和真实提交时间发布到 `merge_request_commit_fact` 后供 BI 读取。
- GitLab 提交明细是独立于平台通用 MR 事实的增强能力。推荐/全部同步模式默认启用；自定义白名单只有同时选择 `merge_request_diffs`、`merge_request_diff_commits` 才启用。缺少任一表时不得阻断、清空或降级平台原有 `merge_request_fact` 和代码走查页面。配置已启用但当前 MR 范围尚未发布任何提交事实时，BI 提交趋势仍必须显式返回 `INCOMPLETE`；不得读取残留事实，也不得用 MR 日期生成全零提交序列伪装为当前提交数据。

## BI 自有分类规则

- 系统测试缺陷原因并非上游单一大类/子类字段的直接透传。`BiSystemTestCauseClassifier` 在 BI 域内以版本化词典从 `issue_fact.reason_category` 和 `issue_fact.label_names` 生成稳定大类/子类；词典未命中的事实必须保留为“未归类”。
- 延期图由 `issue_fact.delay_issue` 决定范围，`BiSystemTestDelayCauseClassifier` 以版本化七类规则读取 `delay_cause`、`delay_reason` 和 `label_names`，未命中项保留为“未归类延期原因”。图表交叉维度是延期原因和严重级别，不存在单独的延期申请状态模型。
- 两个分类器都是无状态普通 Java 对象，由 BI Runtime Factory 显式装配，规则版本进入页面追溯。新增或修改分类必须更新核对表、规则版本和确定性分类/聚合测试，不改变平台现有系统测试看板。

## CAT 集成测试适配

- CAT 开发方已提供 `集成测试平台接口使用手册.md`，当前覆盖项目目录、版本/测试阶段树、模块统计和功能下钻四个 POST 查询。强类型字段映射、完整路径疑点和缺口统一维护在 `data-contracts.md`。
- 现有 `BiCatTestSourcePort` 继续作为单元/集成测试唯一领域端口；基础设施层按 `TestStage` 读取各自显式阶段 ID。两页共用传输协议，不共用阶段范围，也不回退平台数据。
- CAT 客户端使用专属强类型请求/响应 DTO，校验响应信封、必填字段、百分比范围、稳定 ID、阶段映射和功能全量计数后再映射领域模型；CAT 的 `Map<String, Object>` 说明不能穿透到 BI 应用层。手册没有执行/通过用例数时，模块 `passFeatureCount/notPassFeatureCount` 只映射为 `FUNCTION` 单位的达标功能计数，不能写入用例计数。
- BI 产品版本通过配置或受控映射资源显式关联 `catProjectId`、`catVersionId`、`unitTestingPhaseId` 和 `integrationTestingPhaseId`。适配器不得使用 CAT 默认项目、当前版本、中文阶段名称或显示文本猜测范围。
- 模块接口与功能接口是多次独立调用，当前手册没有快照或来源版本。不得把调用时间或响应哈希伪装成 CAT 发布身份，也不得在无法证明一致时构造 `BiCatTestSource` 的 `READY` 结果。
- 模块响应中的通过/未通过数量是功能数量，不是用例数量；适配器把它们放入带 `FUNCTION` 单位的可选计数摘要，不能伪装为通过/执行用例数。三层用例计数仍需 CAT 补充或提供可验证的基础记录。

## 复用边界

| 类型 | 处理方式 | 边界 |
|---|---|---|
| Session、CSRF、RBAC、统一响应、日志、数据源、导航框架 | 直接复用 | 成熟平台基础设施，不复制实现 |
| 侧边栏、通用按钮/图标、通知、基础表单控件 | 直接复用 | 只复用无业务口径的 UI 基础能力 |
| 已发布事实、来源版本、阶段目录、稳定基础查询 | 通过窄端口消费 | BI 不依赖平台页面 Controller 或页面 DTO |
| 平台现有图表、看板页面状态、ECharts option | 不复用 | 在 BI 域按模板独立实现 |
| 系统测试修复率、评审问题口径、BI 页面聚合 | BI 独立实现 | 直接遵循字段级核对表并建立 BI 测试，不改造平台页面 Service |
| CAT 单元/集成数据 | BI 专属出站适配器 | 浏览器不直连 CAT，平台其它模块不参与 |
| PNG 下载按钮外观 | 复用平台基础控件 | 捕获完整图表和文件命名由 BI 独立实现 |

“独立实现”表示在 BI 所有权内实现并测试已确认逻辑，不表示复制粘贴平台代码。发现平台与 BI 需要同一业务规则时，先以规则文档和确定性测试对齐；除非未来明确批准平台级抽取，不为了 BI 修改现有看板的实现边界。

## Runtime 运行舱

- Spring 启动期只注册 BI 薄网关、权限入口、Runtime Manager 和必要配置；BI 内部页面服务、计算器、CAT 客户端和仓储使用普通 Java 对象，由 Runtime Factory 在第一次已授权 BI 请求时延迟创建。
- BI 内部类不使用自动扫描的 `@Component`、`@Service`、`@Repository`、`@Scheduled`、`@Async` 或启动期副作用；依赖由 Runtime Factory 显式装配，从而避免 CAT 配置缺失或 BI 初始化失败阻断平台启动。
- Runtime 初始化失败、CAT 异常、BI SQL/计算异常和 PNG 请求异常统一收敛在 `/api/bi/**`，记录脱敏诊断并返回 BI 状态，不改变平台其它页面的 Spring Bean 和路由状态。
- Runtime 可在失败后按明确操作重新初始化，但不保留新旧实现双轨，也不回退到 mock、旧 Provider 或过期数据。
- 该运行舱不是进程隔离。JVM OOM、进程退出、全局死锁、平台数据源耗尽或共享依赖的致命错误仍会影响整个应用；用户已接受内嵌子模块无法完全解耦的边界。
- 当前不为 BI 单独设计连接池、线程池、缓存或资源配额。实现后如实测出现对其它页面的影响，再以固定负载基准决定是否增加隔离或限流。

## 构建、打包与 Reactor

- 首期继续使用唯一的 `backend/pom.xml`、现有 Spring Boot JAR、Dockerfile/镜像和离线打包脚本；`com.data.collection.platform.bi` 与平台代码一起编译、测试和打包，不改变端口和部署步骤。
- 强包边界不会改变现有打包产物形态，但 BI 编译失败、依赖冲突或测试失败会阻止整个后端包生成。这是单体模块的正常构建耦合，必须通过 BI 定向测试、平台回归和发布门禁控制。
- Maven Reactor 不是废弃方案，而是未来可重新评估的物理边界。只有先定义无环的稳定平台查询契约，并完成根 POM、测试、Spring 装配、Docker、离线打包、升级/回滚的完整迁移设计后才能实施。
- 未来候选依赖方向为“平台查询契约 <- BI 模块 <- 应用装配”，平台事实实现和 BI 都不反向依赖应用模块；不得直接把现有单体拆成互相依赖的 Reactor 模块。

## 版本、同步与页面可见性

- BI 不重复同步平台已有 GitLab 或页面事实，也不把“每 20 分钟”硬编码为自身契约。GitLab 提交随平台事实链路发布；人工走查兼容态直接复用平台兼容表 `code_review_match_mode_records`，不再由 BI 独立任务发布。编码页来源版本由平台代码走查快照版本统一校验。
- 平台完成一次同步并成功发布新事实后，未打开页面的下一次请求读取新版本；已打开页面保持原版本并提示“有新数据可刷新”，用户刷新后整体切换，不能让同一页面的图表逐块换版本。
- 集成测试手册已说明 CAT 项目 ID、版本 ID 和测试阶段 ID，但尚未提供与 BI 产品版本的映射规则、同版本多阶段选择规则及来源版本/快照；单元测试版本字段仍未知。CAT 页面在这些边界冻结前保持 `INCOMPLETE`。
- 系统测试直接使用平台“议题测试阶段定义”及其父级版本到测试轮次的成员关系，不新建 BI 专属版本解析器或第二套阶段目录。
- 六页产品版本目录沿用“议题测试阶段定义”的管理顺序，目录第一项是无显式版本入口的默认范围。URL 中显式稳定 ID 继续用于深链，六个 BI 页面内部切换只继承当前选择；浏览器会话历史不得覆盖管理员调整后的默认项。
- 具体页面接口、状态和来源身份见 `data-contracts.md`。

## 请求与安全

- 页面只调用同源 `/api/bi/**`，权限固定为 `bi.dashboard.view` 和 `bi.dashboard.download`；下载必须同时具备查看权限。
- 前端隐藏路由或按钮不能替代后端授权；六页数据接口要求查看权限，PNG 下载要求查看和下载权限。
- CAT 凭据和传输保护参数只存在于后端配置或安全存储，不进入浏览器、URL、日志、Git、构建产物或页面响应。
- CAT 手册未说明认证；当前客户端严格按手册列出的 `Content-Type` 请求头执行，只读凭据配置暂不引入。若内网联调要求认证，必须补充正式契约后在该单一客户端增加后端配置，不允许浏览器直连或新增旁路。客户端已具备有界连接/读取超时、响应大小限制、强类型响应校验、脱敏错误映射且不自动重试；地址和同步时间策略由系统设置维护，路径、认证、传输保护、并发和迟到数据策略由部署配置维护。

## 旧接口收口

- BI 不使用 `/api/external/v1/datasets`，也不通过外部 Provider 回调本平台。
- `BiDashboardDatasetProvider`、`BiDashboardPayload` 及其 BI 专用测试和配置是被撤回独立 BI 方案的遗留路径；实施 BI 模块前先审计真实消费者，再删除 BI 专用路径，不保留别名、转发、回退或双轨。
- 通用外部数据集框架和其它 Provider 是否保留，只由 BI 之外的真实进程外消费者证据决定。

## 决策摘要

- 已选：内嵌一级模块、进程内 BFF、强包边界、延迟 Runtime、同源 API、单应用部署和平台统一安全边界。
