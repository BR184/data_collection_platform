# ADR-001：BI 内嵌模块与强包边界

## 状态

已接受

## 日期

2026-08-04

## 背景

BI 最初按独立浏览器应用和外部数据集消费者设计，随后确认应作为数据采集平台一级模块，以复用统一登录、权限、侧边栏、部署和平台事实。当前后端由单一 `backend/pom.xml` 构建为单一 Spring Boot JAR，测试、Docker 和离线打包均围绕该产物工作。

若现在直接引入 Maven Reactor，BI 又要调用平台现有服务，会同时出现以下问题：

- 平台事实实现、页面服务和应用装配尚未形成无环的可下沉查询契约。
- 根 POM、测试入口、Spring 组件扫描、Docker、离线打包、升级和回滚都要同步改造。
- 为了快速拆模块，容易形成 BI 与平台实现互相依赖，或复制一套平台公式和 DTO。

BI 与平台共享 JVM 意味着无法做到进程级故障隔离，但用户接受内嵌子模块存在这种运行耦合，同时要求普通 BI 故障尽量不影响平台启动和其它页面。

## 决策

首期不实施 Maven Reactor，采用以下边界：

1. 后端代码统一位于 `com.data.collection.platform.bi`，前端代码位于独立 BI 功能目录。
2. BI 随现有 Maven 工程、Spring Boot JAR、前端发布物、Docker 和离线包一起构建部署。
3. 保留进程内 BFF，负责六页 API、来源版本、聚合计算和页面状态，不创建第二个网络服务。
4. Spring 启动期只创建薄网关和 Runtime Manager；BI 内部服务使用普通对象并在首次已授权请求时显式、延迟装配。
5. BI 直接复用平台成熟基础设施和稳定事实/基础查询端口；页面计算、页面状态、CAT 适配和图表体系在 BI 域独立实现。
6. 图表类型类只在 BI 内复用，不修改平台现有看板，也不允许平台看板反向依赖 BI。
7. Reactor 保留为未来候选，但必须作为平台级重构单独评审和验证。

## 备选方案

### 立即实施 Maven Reactor

优点是编译边界更强，可定向构建 BI。缺点是当前没有无环平台契约，会迫使先拆平台核心或形成循环依赖，并扩大测试、容器和离线发布风险。首期拒绝。

### 独立 BI 服务与独立 BFF

可获得进程隔离，但会重复登录、权限、部署、配置和运维，并重新引入外部数据集契约。与“平台内一级模块”的产品方向冲突，拒绝。

### 直接复用平台现有看板组件和页面 Service

初期代码较少，但会把 BI 的六阶段页面、图表抽象和聚合生命周期绑定到现有看板内部 DTO 与交互，后续修改任一侧都容易产生连锁回归。拒绝；只复用稳定基础设施和窄查询端口。

### 只使用包边界，不做 Runtime 运行舱

实现最简单，但 CAT 配置、BI 初始化或自动扫描 Bean 失败可能阻断整个平台启动。拒绝；保留薄 Spring 边界和延迟初始化。

## 后果

- 平台现有构建、打包、部署和端口不因 BI 首期发生结构变化。
- BI 的编译或测试失败仍会阻止整个单体包生成；这是被接受的构建耦合，必须由定向测试和平台回归控制。
- 普通 BI 初始化、CAT、SQL 和计算异常可限制在 `/api/bi/**`；JVM OOM、进程退出、全局死锁和共享依赖耗尽仍可能影响平台。
- 包边界依赖代码审查、架构测试和禁止反向依赖的规则维持，不等同于 Maven 的物理隔离。
- 未来若实施 Reactor，至少要先具备稳定平台查询契约、无环依赖图和覆盖 Maven、Spring、Docker、离线包、升级/回滚的迁移验证；不能仅新增一个子模块目录。
