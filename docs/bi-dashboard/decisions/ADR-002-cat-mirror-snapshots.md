# ADR-002：CAT 数据采用 BI 专属全量镜像快照

## 状态

已接受

## 日期

2026-08-06

## 背景

单元测试和集成测试由 CAT 全权供数。初版 BI 在页面请求中依次调用 CAT 阶段树、模块统计和每个模块的功能统计接口。该方式没有持久化数据，页面延迟和可用性直接受 CAT 影响，也无法保留可复现的调试证据。

用户确认 BI 对实时性要求不高，并要求在系统设置的数据镜像设置中管理 CAT 同步。CAT 当前协议没有变更游标、更新时间水位、删除事件或原子快照标识，不能实现可证明正确的增量同步。

## 决策

1. CAT 数据写入 PostgreSQL 中 BI 专属的配置、同步运行、快照、模块、功能、原始响应和当前发布指针表。
2. CAT 镜像不进入 GitLab 镜像表注册、兼容模式、GitLab 同步运行或现有表级增量引擎；任一 CAT 同步失败不得改变其它镜像任务和平台页面。
3. 首版只提供定时全量、手动全量和全量补偿。三种触发共享唯一全量采集实现，不提供名称为“增量”但实际全拉的入口。
4. 每个产品版本和测试阶段独立构建快照。只有阶段树核验、模块统计、全部功能统计和领域校验都成功后，才在短事务中切换当前发布指针；失败保留上一成功快照。
5. 单元测试和集成测试页面只读取当前发布快照，不在页面请求中调用 CAT，也不在镜像缺失或过期时回退实时直连。
6. 镜像发布版本是数据采集平台的采集快照身份，表示一个明确采集窗口内完整取得并原子发布的数据集，不冒充 CAT 原生来源版本。追溯信息必须保留 CAT 项目、版本、阶段和采集开始/结束时间。
7. 系统设置复用平台现有镜像查看、配置和同步权限。CAT 配置与运行状态使用独立 API 和前端组件，不扩大 BI 查看/下载权限。

## 备选方案

### 页面请求时直连 CAT

实现简单，但每次查看都会重复调用 CAT，无法保留上一成功数据、稳定下载来源或可复现的调试证据。已被本决策取代。

### 接入 GitLab 表级同步引擎

CAT 是 HTTP 聚合接口，不具备数据库表、主键游标和更新时间水位。强行接入会让两种不同来源共享错误抽象，并增加对现有 GitLab 同步的回归风险，拒绝。

### 在当前协议上实现增量同步

没有变化水位就无法证明新增、更新和删除集合。用响应差异或本地时间模拟增量会产生漏数和残留，拒绝。

## 后果

- BI 页面读取本地已发布快照，速度、可用性、下载来源和调试能力改善。
- 页面数据会落后于 CAT，延迟上限由同步配置决定；页面需要展示采集时间和最近同步状态。
- 平台可保证自身发布原子性，但 CAT 多接口调用期间仍可能发生上游变化。采集窗口必须可见，后续 CAT 若提供原子快照令牌，应把该令牌加入追溯而不是改变页面读源。
- 需要维护独立表、同步状态、保留策略和迁移，但不会改变现有 GitLab 镜像或兼容数据生命周期。
