# 议题统计、评审导入与页面刷新对齐方案

## 1. 总原则

1. 新平台是老平台 `D:\projects\spidergitdata-dev` 的架构重构和体验升级，不重新设计业务口径。
2. 凡涉及数据底层、事实字段、统计数量、列表字段、字段值、非法判定、导出、下钻、默认筛选范围和页面展示口径，优先遵从老平台源码和 `docs/platform-page-business-rules.md`。
3. 新平台可以优化刷新、查询性能、筛选体验、权限、可维护性和用户效率，但不能改变用户看到的业务结果。
4. 内网真实数据验收时，同一数据源、同一筛选条件下，新平台展示的数据集合、总数、字段含义、字段值和导出结果应尽量与老平台一致。

## 2. 系统测试阶段和里程碑

### 2.1 口径解释

GitLab 标签是议题事实来源，例如 `CC2026R1第一轮系统测试`、`CC2026R1回归测试` 这类标签直接落在议题上。老平台中的 `testing_phase` 表不是替代 GitLab 标签的业务数据源，而是把这些标签组织成可展示、可切换的项目/阶段层级。

因此新平台不需要额外新建一个用户侧“议题测试阶段定义”页面作为本次修复前置条件。当前目标是按老平台逻辑自动生成或复用阶段目录，让页面下拉和统计能按老平台口径工作。

### 2.2 实现方案

1. 建立共享测试阶段目录能力，优先读取新平台已有阶段定义；没有定义时，从 `issue_fact` 的 `testing_phase`、`system_test_label`、`label_names` 等事实字段中按老平台标签规则推导。
2. 识别系统测试阶段时，只按老平台已使用的系统测试/回归测试标签语义处理，不从标题、页面名称或任意文本中反推；`CC2026R3系统测试`、`CC2026R3第一轮系统测试`、`CC2026R3回归测试` 均归并到父级版本 `CC2026R3`。
3. “系统测试缺陷汇总”保留里程碑/轮次层级切换能力，父级版本下拉展开到对应子阶段标签。
4. “申请延期缺陷分析”“缺陷原因分析”“议题阶段统计”等页面按版本/里程碑切换，后端负责将父级版本展开为子阶段范围。
5. 页面显示名称可以不完全等同老平台内部表名，只要下拉可选项、默认范围、统计结果和用户理解保持一致。

## 3. 系统测试非法数据

1. 非法数据判定改回老平台口径，支持同一议题命中多个非法类型。
2. 非法类型包括但不限于“未设定严重程度”“未设定模块”“未按照模板回复”“缺陷原因不唯一”。
3. 对老平台已有或内网真实数据中出现的非法原因，不因新平台当前枚举收口而丢弃；能够归一化的做别名归一化，不能归一化的保留原始原因展示。
4. 页面数据数量、筛选范围和导出结果以老平台非法数据列表为对齐目标。

## 4. 申请延期缺陷分析

1. 延期原因类型固定为：技术卡点、方案卡点、资源卡点、数据异常、算法问题、机制问题、计算效率。
2. 页面表头保留老平台独立表格口径：一级缺陷、二级缺陷、三级缺陷、建议类缺陷、总计。
3. 总计按老平台 `DefectLevelEnum.values()` 结果相加；同时继续复用系统测试公共过滤，因此建议类数据在公共过滤后通常为 0，这是老平台真实查询行为，不为了“看起来合理”擅自纳入。
4. 页面需要支持版本/里程碑切换；选中父级版本时，后端展开到对应系统测试和回归测试阶段。
5. 数据为 0 时必须能追溯是确实无数据，还是阶段目录、事实字段或过滤条件未命中，不允许因为新平台收口导致全 0。

## 5. 缺陷原因分析

1. 缺陷原因分析以老平台源码和规则总表为准。
2. 优先使用事实层已经解析出的缺陷原因字段；事实字段缺失或历史数据未补齐时，按老平台评论模板解析逻辑兜底。
3. 新旧模板兼容映射遵守 `docs/platform-page-business-rules.md` 中“缺陷原因分析”章节。
4. 统计口径是缺陷原因个数，不是议题个数；缺陷原因占比的分子和分母都按原因个数计算。
5. 后续性能优化不能改变统计范围、原因归类或模块行骨架。

## 6. 议题阶段统计

1. 统计范围使用系统测试公共范围，表头保留老平台一级缺陷、二级缺陷、三级缺陷、建议类缺陷、总计口径。
2. 项目/版本下拉来自共享测试阶段目录。
3. 轮次来自项目/版本对应的子阶段；选中父级版本时展示该版本下各轮次严重程度数量。
4. 页面不得因没有手工维护阶段定义而显示空数据；事实层存在老平台可识别标签时应自动进入统计。

## 7. 评审数据导入

1. 老平台导出的 Excel 是当前评审导入的标准输入格式，不称为“兼容模式”。
2. 导入逻辑需要按老平台导出文件格式识别字段、项目、模块、评审类型、缺陷数量和密度相关列。
3. 对不影响主数据落库的历史字段、空字段或新平台暂不展示字段，应尽量提示并降级处理，不能因为新平台收口过窄导致整批导入失败。
4. 如果某字段确实无法安全推断，应在解析提示中说明具体行列和原因，并保留可导入数据的处理能力。

## 8. 页面刷新策略

1. 采用“首次进入自动刷新”策略：同一浏览器会话内，同一统计页面和同一数据范围首次进入时自动刷新一次。
2. 后续在同一会话内再次进入同一页面和同一范围，不再自动刷新；用户仍可手动点击刷新。
3. 不做焦点触发刷新，避免多用户和多标签页场景中反复触发页面刷新。
4. 自动刷新状态按页面和数据范围隔离，避免一个页面刷新影响其他页面判断。
5. 该策略只减少不必要刷新请求，不替代后端查询性能优化；关闭自动刷新后仍偏慢的页面需要继续从 SQL、事实字段索引、聚合缓存和下钻查询拆分等方向优化。

## 9. 验收和待确认项

1. 已完成的本地最小验证应包括后端编译和前端类型检查。
2. 仍需在内网真实数据上逐页核对：系统测试缺陷汇总、申请延期缺陷分析、系统测试非法数据、缺陷原因分析、议题阶段统计、评审数据导入。
3. 如果新平台与老平台数量不一致，先按老平台源码和规则总表排查阶段范围、默认过滤、事实字段解析、模块行骨架、严重程度和评论模板解析，不先改页面展示凑数。
