# 测试阶段白名单屏蔽口径（显示与统计）

日期：2026-06-23

> 本文件是"测试阶段切换"功能在显示和统计层的硬性口径。与之配套的维护页结构、字段映射、两级维护交互见 `docs/current-state/testing-phase-two-level-management-20260622.md`；总业务规则以 `docs/platform-page-business-rules.md` 为准。三者冲突时，先对齐后再改代码。

## 1. 背景

新平台是老平台 `D:\projects\spidergitdata-dev` 的重构版，必须 1:1 复刻老平台的数据口径（见 `AGENTS.md` §0.0 红线）。老平台用一张 `testing_phase` 表（字段：`原始数据ID`、`项目代号`、`优先级/序号`、`任务名称（简体中文）`、`状态/标志`）当作**测试阶段的总闸**：只有这张表里维护并启用的阶段，才允许出现在平台的下拉、统计和明细里。表外的阶段以及它们对应的议题数据，平台一律不显示、不计数。

新平台已把这张表拆成两级数据化落地：

- 父级（`项目代号`，如 `CC2026R3`）→ `testing_phase_groups`
- 子级（`任务名称（简体中文）`，如 `CC2026R3第一轮系统测试`、`CC2026R3回归测试`）→ `testing_phase_calendar`

字段映射详见两级维护方案文档，此处不再重复。

## 2. 核心口径（必须同时满足两层）

### 第一层：下拉只列维护表内启用的阶段

1. 系统测试类页面的"测试阶段 / 切换里程碑"下拉，选项只能来自维护表中 `enabled = true` 的阶段。
2. 父级停用 → 不进下拉，其子级也不参与任何匹配；子级停用 → 父级仍可进下拉，但展开时不含该子级。
3. 不允许从 `issue_fact.testing_phase`、GitLab 原始标签字符串或任意文本反推下拉选项。表外阶段连"选"都不应出现。

### 第二层：表格数字只算"当前选中阶段范围"内的数

这是本文件的重点，也是最容易做错的地方。

1. 表格里任何"总数 / 总计"指标，**不是**该维度（模块、负责人等）在 `issue_fact` 或数据库里的全量条数，而是被**当前选中的测试阶段范围**圈定后命中的条数。
2. 选中粒度到哪一层，就严格按那一层的范围算：
   - 选中**父级**（如 `CC2026R3`）→ 范围 = 该父级下所有启用子级阶段命中的数据之和。
   - 选中**具体子级**（如 `CC2026R3第一轮系统测试`，仅缺陷汇总页支持下钻到子级）→ 范围 = 仅这一个子级阶段命中的数据。
3. 落在维护表之外的阶段（或无阶段）的议题，无论该维度在库里有多少条，都不计入任何一层、不显示。
4. 阶段选择变化时，所有数字必须按新范围实时重算。

### 父级 / 子级展开的页面差异

- **只有"系统测试缺陷汇总"页面**会把选中的父级展开成第一轮~第 N 轮系统测试 + 回归测试这些具体子级阶段（用于模块表的轮次展开），并支持下钻选中到某个具体子级。
- **其他系统测试页面**（申请延期缺陷分析、缺陷原因分析、议题阶段统计等）只在**父级**这一层切换，不展开到具体轮次。
- 两类页面的**数字口径完全一致**：都遵守第二层——总数 = 当前实际选中阶段范围命中的真实条数。差别只在"选中粒度能下钻到多深"，不在计数规则。

## 3. 标准示例（验收基准）

以"工程图"模块为例：

| 场景 | 库内/范围内数据 | 表格应显示的工程图总数 |
| --- | --- | --- |
| 整个数据库 | 1000 条工程图 | —（不直接展示，全量不是口径） |
| 维护表覆盖的所有阶段（CC2024Rx/CC2025Rx/CC2026Rx…）合计 | 命中 500 条 | 剩余 500 条落在表外阶段，永久屏蔽，不进任何系统测试统计 |
| 选中父级 `CC2026R3` | 该父级所有启用子级合计命中 10 条 | **10** |
| 选中子级 `CC2026R3第一轮系统测试` | 仅该子级命中 2 条 | **2** |

口径一句话：**总数 = 当前选中阶段（到选中的那一粒度）在 `issue_fact` 里命中的真实条数；选什么算什么，表外一律不算不显示。**

## 4. 实现锚点（新平台现有代码）

落实本口径时对齐以下现有实现，不要在页面 / SQL 里另起一套隐藏口径：

1. 下拉与白名单：`SystemTestPhaseCatalogService`（`backend/.../service/SystemTestPhaseCatalogService.java`）。`loadConfiguredEntries` 的 SQL 写死 `where c.enabled = true and coalesce(g.enabled, true) = true`，下拉/目录只返回启用阶段。默认项目 `LEGACY_CROWN_CAD_PROJECT_ID = 9`（对应老平台 CC projectId 9）。
2. 选中阶段展开为表内子级：`SystemTestPhaseScopeResolver`（同包）。`resolvePhases` 把选中的父级/阶段展开成维护表里配置过的具体 `testing_phase` 列表；表外阶段不在列表里，统计层自然算不进。
3. 统计层按"展开后的子级集合"过滤 `issue_fact.testing_phase`：见 `service/statistics/` 下各系统测试看板服务（`SystemTestDefectSummaryBoardService`、`SystemTestPhaseStatisticsBoardService`、`SystemTestDelayAnalysisBoardService`、`SystemTestDefectCauseBoardService` 等）及共享的 `SystemTestPhaseFilterSupport`。

## 5. 开发自检清单

改动任何"测试阶段切换"相关页面前后，逐条确认：

1. 下拉选项是否只来自维护表中启用阶段？有没有混进 `issue_fact` 里出现过但表外的阶段？
2. 表格"总数"是否按当前选中阶段范围算，而**不是**该维度的全量库存数？
3. 选父级时，是否按"该父级下启用子级的合计"算？选子级时，是否只算那一个子级？
4. 表外阶段 / 无阶段的议题是否被完全排除（不计数、不在明细、不在导出）？
5. 切换阶段后数字是否实时重算？
6. 导出口径是否和页面一致（同样的阶段范围、同样的屏蔽）？
7. 缺陷汇总页之外的页面是否误做了子级展开 / 误在父级层多算或漏算？
