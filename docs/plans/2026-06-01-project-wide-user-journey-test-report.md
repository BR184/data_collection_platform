## 发现的问题

### P1: 后端 `/actuator/health` 返回 500，且被包装成普通业务异常

现象：

请求：

```powershell
Invoke-WebRequest http://localhost:18080/actuator/health
```

返回：

```json
{"success":false,"code":"C0001","message":"服务处理异常，请联系开发人员排查","data":null}
```

日志证据：

```text
GET "/actuator/health"
NoResourceFoundException: No static resource actuator/health.
GlobalExceptionHandler: Unhandled exception
```

判断：

这不是数据库或 GitLab 健康检查失败，而是当前后端没有真正暴露 actuator health endpoint。`PlatformSecurityConfiguration` 已放行 `/actuator/health`，但运行时没有 handler，导致请求落到静态资源处理，再被全局异常处理包装为 500。

影响：

- 运维和部署探针会认为服务不健康。
- 响应体只说“服务处理异常”，无法区分是 endpoint 未暴露还是依赖异常。
- 内网部署时如果用健康检查做启动/重启判定，会产生误判。

建议：

- 如果要保留 `/actuator/health`，应明确引入并暴露 Spring Boot actuator health。
- 如果不打算引入 actuator，应提供一个轻量 `/api/health` 或 `/healthz`，并让部署文档和安全放行路径一致。
- 全局异常处理不应把 `NoResourceFoundException` 伪装成服务内部异常；至少应返回 404。

### P1: 同源重复配置的前端文案仍说“平台不会阻止保存”

现象：

数据镜像设置页仍显示：

```text
当前数据源和 Smoke CC minimal source（smoke_cc） 指向同一个 GitLab 源库。平台不会阻止保存，但如果这些源同时启用，同一批 Issue、MR 和评论可能进入事实层多次，业务页面会看到重复数据。
```

判断：

后端已经实现同物理源保护：在特定启用/自动同步场景会阻断保存。因此“平台不会阻止保存”已经不是完整事实。

影响：

- 用户看到 warning 后可能以为保存一定可以继续，只是有风险。
- 实际保存被后端阻断时，用户会觉得前后端规则不一致。
- 这类问题容易被接口测试漏掉，因为接口行为正确，但用户读到的规则是旧的。

建议：

- 将前端 warning 改成与后端策略一致，例如：
  - 停用或草稿源允许保存。
  - 多个启用自动同步源指向同一 GitLab 源库时，平台会阻止保存。
  - 如需保留 smoke/minimal 源，应关闭自动同步或停用数据源。
- 文档中涉及“不会阻止保存”的历史描述应保留为历史背景，但当前行为说明要更新。

### P2: 游客态质量看板会产生多条 401 控制台错误和“部分看板加载失败”提示

现象：

未登录访问首页质量看板时，页面会尝试加载若干需要登录的摘要接口，控制台出现：

```text
Failed to load resource: 401 Unauthorized
评审摘要 加载失败 Error: 请先登录
代码走查摘要 加载失败 Error: 请先登录
集成测试摘要 加载失败 Error: 请先登录
系统测试摘要 加载失败 Error: 请先登录
```

页面显示：

```text
部分看板加载失败，已展示可用数据
```

登录管理员后该提示在本轮深测中没有继续残留；但游客首次进入时仍会看到“失败”语义。

影响：

- 对游客或首次打开页面的用户来说，“部分看板加载失败”更像系统故障，而不是权限限制。
- 控制台 401 噪声会干扰真实前端错误排查。
- 管理员登录前先看到失败提示，会降低对平台状态的信任。

建议：

- 游客态下不要请求明确需要登录的摘要接口；或在请求前按 `authState.currentUser.authenticated` 判断。
- 游客态空态文案应表达“登录后查看管理数据”，不要使用“加载失败”。
- 登录成功后可以主动重载质量看板摘要，避免用户需要手动刷新。

### P3: 离开镜像设置页会静默丢失未保存草稿

现象：

1. 在数据镜像设置页把 `补偿间隔(分钟)` 改为 `127`。
2. 不点击保存。
3. 点击左侧“数据库查看”。

- `补偿间隔(分钟)` 恢复为服务端保存值 `360`。
- 页面没有离开前确认，也没有提示“存在未保存修改”。

判断：

建议：

- 对镜像设置页增加 dirty state 离页保护。
- 只在表单存在未保存修改时提示。
- 同页内的“测试连接”“刷新最新数据”等局部操作不应触发离页确认，因为本轮已验证它们不会覆盖草稿。

### 第 7 轮：真实 Excel 导入与导出文件校验

覆盖动作：

- 在评审数据管理页面打开导入弹窗。
- 选择 `.xlsx` 文件并执行“解析预览”。
- 确认预览中出现可导入行和唯一前缀。
- 执行“确认导入”。

新增确定问题：

### P2: 窄屏下管理员登录入口和登录弹窗点击区域不可靠

现象：

- 390px 级别窄屏视口下，“管理员登录”按钮虽然可见，但点击时被顶部导航或 header 区域拦截。
- 强制打开登录弹窗后，弹窗内“登录”按钮也出现点击区域被 overlay/dialog 层拦截的情况。
- Playwright 普通点击无法完成登录，必须使用 force click 才能继续后续测试。

影响：

- 如果现场用户使用窄屏浏览器窗口、远程桌面窄窗口、平板或移动浏览器，可能无法正常登录。
- 这不是接口问题，也不是账号问题，而是点击命中区域/响应式布局问题。
- 当前平台主要面向桌面内网使用，因此优先级低于健康检查和同源文案，但发布级体验上应修复。

建议：

- 给顶部导航和 header actions 增加真正的窄屏布局：导航换行、折叠菜单或横向滚动。
- 确保登录按钮不被 nav/header 覆盖，弹窗 footer 按钮位于可点击层级。
- 增加至少一个 390px 或 768px 宽度的登录 smoke 测试。

证据：

- `.tmp/user-journey-release-round9/report.json`
- `.tmp/user-journey-release-round9/mobile-quality-board.png`
- `.tmp/user-journey-release-round9/mobile-mirror-settings.png`

窄屏补充说明：

- 登录后部分页面在移动上下文中报告 `innerWidth=1160`，说明页面可能存在桌面最小宽度或 viewport 适配不足。对于当前桌面优先的内网平台，这不一定是阻断问题；但如果计划支持移动或平板，需要单独做响应式改造。
