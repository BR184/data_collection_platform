## 证据与根因分析

### 1. 轮次乱序根因（问题 4）
- **现象**：系统测试各轮次图表中，轮次顺序呈现为：二、六、三、四、五、一、回归测试。
- **技术根因**：
  前端 `sortRoundQualityRows` 中默认排序使用了 `a.name.localeCompare(b.name, 'zh-CN', { numeric: true })`。在汉语拼音字典序中：
  - 二 (er) -> 排在第 1
  - 六 (liu) -> 排在第 2
  - 三 (san) -> 排在第 3
  - 四 (si) -> 排在第 4
  - 五 (wu) -> 排在第 5
  - 一 (yi) -> 排在倒数第 2
  - 回 (hui) -> 排在中间
  拼音排序完全脱离了轮次的自然业务时序。而后端 `BiSystemTestCalculator.java` 内部实际上在生成 DTO 时早已对每轮赋予了严格的整数 `roundOrder`（1, 2, 3...，回归为固定末位）。前端此前未将该字段作为主要排序依据。

### 2. 整体修复率 0% 被异常置顶根因（问题 5）
- **现象**：在“各模块系统测试修复率达成情况”中，整体修复率为 0.00% 的模块被强行排在最顶端。
- **技术根因**：
  在 `SystemTestStageContent.vue` 和 `sorting.ts` 中，判定达标的代码为：
  ```ts
  const achievedA = left.fixRate != null && left.fixRate >= 0.95;
  ```
  平台中 `fixRate` 的存储与下发数值为百分比标量（0 ~ 100，例如 71.43、95.00、100.00）。代码作者误将百分比当成了 0 ~ 1 的小数进行判断。导致：
  - 修复率为 71.43% 的模块：`71.43 >= 0.95` 为 `true`（被误当成达标）；
  - 修复率为 100% 的模块：`100.00 >= 0.95` 为 `true`（达标）；
  - **唯独 0.00% 的模块**：`0.00 >= 0.95` 为 `false`（全表唯一被认定为“未达标异常”）。
  在默认的“异常优先”（未达标优先排在前面）规则下，0.00% 因而被强行置顶！

### 3. 静态代码扫描结果图表调查结论（问题 2）
- **图表现状**：
  图表将“扫描记录数（次）”与“扫描Bug数（个）”堆叠在单根柱状图上，X 轴为纯技术执行状态（如 SUCCESS、FAILED 等）。
- **硬伤分析**：
  1. **量纲混淆**：“扫描执行了多少次”与“查出了多少个Bug”属于完全不同的物理量纲，垂直堆叠在视觉和数学上均不具备加总意义。
  2. **缺失严重级别分类**：静态扫描最核心的价值在于识别阻断（Blocker）、严重（Critical）、主要（Major）缺陷。底层数据源未下发严重级别明细。
  3. **缺乏质量洞察**：按构建执行状态展示，只能说明流水线有没有跑通，无法反映代码库本身的健康程度与缺陷消除趋势。
- **建议**：直接下线删除该图表（或在未来引入 SonarQube 多维严重级别扫描数据后重新设计）。

### 阶段三：系统测试按指派人统计按组织架构/模块查看调研（问题 6 调研落档）

#### 1. 业务痛点与领导诉求
- **现状**：目前“按指派人统计缺陷数”是以开发人员姓名作为维度的扁平排行榜。在几百人的研发团队中，研发管理者无法宏观按“部门/科室/开发组”把控质量风险，也无法按“某个业务模块”过滤具体指派人。
- **诉求**：支持按照“模块”或“组织架构”进行下钻或层级聚合。

#### 2. 数据可行性与架构制约
1. **模块维度**：
   - 当前禅道/TAPD/Jira 等数据源中，Bug 记录天然同时关联了 `Module`（所属模块）和 `AssignedTo`（当前指派人）；
   - 改造路径：可在图表上方增加 `[ 所属模块筛选下拉框 ]`，前端按选中模块动态过滤指派人列表，技术成本最低，立即可落地。
2. **组织架构维度**：
   - 当前缺陷源表仅包含人名/账号标识，未持久化研发人员的科室/部门层级；
   - 改造路径：平台已在规划接入 LDAP / HR 组织架构。未来可通过人员工号关联 `dept_name / team_name`，在图表上支持 `[ 按开发组聚合 ]` 或 `[ 部门 -> 个人 ]` 级联展开。
