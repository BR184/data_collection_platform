## 目标与边界

- 原始需求：CC_PRODUCT 页面与 Excel 使用同一列顺序和字段事实；页面补齐测试阶段、议题指派人、延期原因、缺陷修复人、功能名称，议题状态使用中文业务值；处理人与指派人不再错误合并。
- 成功标准：页面、筛选、分页、排序和导出使用同一记录投影；每个字段保留独立事实语义；未知测试阶段明确显示、可精确筛选但不从标题或里程碑推测。
- 明确禁止：不为缺失源数据臆造测试阶段、修复人或延期原因；不把 `申请延期` 当作延期原因；不在 Excel 单独解析或复刻页面规则；不影响延期问题及其他记录页的既有字段契约。

## 约束与背景

- 老平台是业务展示基准，但当前 GitLab ODS 对应议题只提供一份规范指派身份；因此 `handler_name` 与 `assignee_name` 结构上独立，当前数据值可能相同。
- `function_name`、`delay_cause`、`fix_user`、`testing_phase` 均来自 `issue_fact`；`fix_user` 仅从合法修复状态评论生成。
- `delay_cause` 以七类合法原因或 CC_PRODUCT 的 `未设定类别` 回退值为事实契约；组合值的分隔符为无空格 `&`，读取端按成员解释。
- Flyway 迁移只前进：结构与存量回填分为 `V20260722_03`、`V20260722_04`，不得改写已执行迁移。
- 既有 `schema.sql` 的客户问题响应时效索引由 `V20260722_05` 在升级路径创建；不得仅修改 `schema.sql` 而遗漏 Flyway。

## 证据与根因

- 原实现把 `assignee_name` 同时投影为“议题处理人”和“议题指派人”，导致两列及筛选语义被错误合并。
- 当前 CC_PRODUCT 源事实的 `testing_phase` 全为空；将其显示为 `未设定测试阶段` 是展示契约，不能反推真实阶段。
- Excel 与页面此前分别维护列映射，存在顺序及字段漂移风险；当前均由同一记录响应字段生成。
- 新平台原先按固定优先级只取一个延期原因，且将单独的 `申请延期` 返回为原因；根因是把延期状态和延期原因共用了一条单值推断路径。
- `schema.sql` 已声明客户问题响应时效索引但旧 Flyway 序列没有对应迁移，升级库会缺少该索引；已新增前向迁移和烟测覆盖。

## 方案与步骤

1. 以 `issue_fact.handler_name` 作为处理人事实，保留 `assignee_name` 为指派人事实，并穿透事实构建、查询、响应、筛选、排序与 Excel。
2. 将 CC_PRODUCT 的空测试阶段标准化为展示/筛选占位值，原始空值保持空。
3. 为处理人/指派人独立性、空测试阶段、前端列映射、源 SQL 与迁移添加定向回归测试。
4. 将延期原因的事实归一化、成员筛选、候选、统计回退和 CC_PRODUCT 标签展示纳入同一条成员语义链路，并覆盖“申请延期”无原因和多原因样本。
5. 同步页面业务规则与当前进度，完成编译、类型检查、迁移校验和受影响测试；部署后执行真实数据核验。

## 决策记录

- 已选：新增独立 `handler_name` 字段；理由是业务语义必须独立于当前数据源是否恰好返回相同值。
- 已选：空测试阶段显示 `未设定测试阶段`；理由是数据缺失必须可见、可筛选，且不可被推测值污染。
- 已选：事实层保留多原因组合文本，读取端拆分成员；理由是保持老平台导出/接口文本契约，同时让页面、筛选和统计正确表达一条议题的多个原因。
- 已选：仅 CC_PRODUCT 主表将延期原因映射为多个标签；延期问题及其他记录页保持既有列和文本契约，避免展示层改动扩大到无关页面。
- 否决：继续共享 `assignee_name` 或在页面层复制字段；理由是会持续混淆筛选、导出与后续来源扩展。
- 否决：从议题标题、里程碑或标签推断测试阶段；理由是没有老平台或当前事实层依据。

## 接口契约

- CC_PRODUCT 列顺序固定为：议题编号、模块名、功能名称、议题标题、客户、议题提交人、议题处理人、议题指派人、议题状态、测试状态、测试阶段、严重程度、缺陷优先级、议题类别、里程碑、延期原因、缺陷修复人、计划解决时间、计划合并版本分支、提交时间、缺陷滞留时长（小时）、更新时间。
- `handlerName` 与 `assigneeName` 为独立 API 字段和独立筛选参数；`testingPhase=未设定测试阶段` 只匹配事实空值。
- `delayCause` 接口和 Excel 保持事实层组合文本；CC_PRODUCT 表格将 `&` 分隔成员逐个渲染为标签，单独 `申请延期` 的客户问题值为 `未设定类别`。
- 对外状态显示：`open` / `opened` 为“未关闭”，`closed` 或具有关闭时间为“已关闭”。

## 风险与假设

- 风险：迁移完成但未重建事实时，新同步前的历史源字段仅由回填覆盖，必须在目标环境重建事实以获得当前 ODS 数据。
- 风险：真实 GitLab ODS 可能没有合法修复状态评论，`fix_user` 为空是正确的源数据结果。
- 风险：规则和事实字段发生变化后，目标环境必须执行一次 `scope=issue, full=true` 重建；否则历史 `delay_cause=申请延期` 或单原因旧值会继续停留在事实表中。
- 假设：当前 source SQL 中的规范指派人仍是 GitLab 对应的唯一可用人员身份；如将来接入独立处理人来源，应只在事实构建层填充 `handler_name`。
