## 5. 方案与步骤

### S1. 收敛修复时间的唯一来源

1. `fixed_label_time` 只来自当前有效的精确修复标签对应的有效 add 事件，取最大 `created_at`。保留事件聚合算法，不引入 add/remove 生命周期表。
2. 当前 `bug_status` 成员集合包含精确值 `已修复/完成` 才保留事件时间，否则为空。复用既有成员解析器及领域常量；不改全局 `isFixed` 的广义统计定义。
3. 删除 label_links 时间回退、布尔选择的双 SQL 入口及 `hasResourceLabelEventSource()`；事件所需列、整数 action 类型由既有来源结构门禁显式检查。数据访问异常按失败处理，不变成另一种业务时间。
4. 在 `GitlabFactDependencyCatalog` 将事件表从 ISSUE 的信号依赖移到业务依赖，必需表集合不增加。MR 仍按原信号关系运行，不将 MR 的修复时间需求凭空引入。
5. 区分两类缺失：来源未完整同步＝来源未就绪；来源完整但单议题没有匹配事件＝合法未知值 null。前者不发布新事实，后者不猜测时间。已有可读事实保留，不把同步失败展示成成功的零条结果。
6. 完整性复用当前表状态和来源发布状态：检查本来源事件表成功全量验证证据 `last_full_verified_at` 以及本轮依赖终态，不能用建表标记或每页更新的 `last_success_at` 冒充完整性。自动与手动 ISSUE 构建入口执行同一来源资格检查。
7. 现有 `SyncFactPublicationStateService.isReady()` 同时包含“有待发布工作”的条件，实施时把来源资格与是否有工作分成明确职责，更新调用者，不用它直接判定手动重建资格，也不保留旧名转发。

**影响声明**：这是共享 ISSUE 来源契约收敛，不是仅前端变更。合规事件来源上的既有事实和解决效率应不变；依赖旧回退值或缺少完整来源的环境将被要求补齐事件并重建，必须在发布前预检，不能到上线后才发现系统测试等 ISSUE 消费者受阻。该技术调整待本方案审批，不视为已获执行授权。

### S2. 补齐事件到事实的真实依赖

1. 来源血缘登记事件的 ISSUE 直接派生；根解析从每个事件 before/after 的 `issue_id` 并集获得目标。不得先按 after.action=add 过滤，否则删除、动作纠正和归属迁移会漏掉旧值清理。
2. 保留事件对 Issue/MR 当前标签集合的权威补读关系。新增直接目标只覆盖确实读取事件时间的 ISSUE，MR 继续通过当前标签关系变化生成目标。
3. 标签名称/删除状态参与时间计算，所以标签变化反查要覆盖“当前标签关联＋历史事件关联”的 Issue 根，且按批次和来源隔离；不能只检查当前 label_links。
4. 复用既有 ODS 事务、outbox、来源互斥、版本围栏、定向构建和投影发布，不另建任务、线程或刷新定时器。
5. 正常 GitLab 撤标/重加产生新 ID 事件，走现有主键增量。源库直接改旧事件 ID、低 ID 历史补录和物理删行不属于单调主键增量能发现的变化：采用既有全量补偿/删除对账恢复；对账未启用时在运维验收中明确边界，不擅自开启全局删除反熵。

### S3. 打通查询模型、范围与快照

1. 在客户记录请求和 `CcProductFilters` 增加 `fixedLabelTimeStart/End`，入口解析为合法日期边界；单边允许，起止颠倒或日期非法走现有参数错误响应。新字段限 `topic=cc-product`，其他 topic 的显式误传须拒绝，不能静默生效。
2. `IssueFactRecordRepository` SELECT、`IssueFactRecordRowMapper`、`IssueFactRecord`、客户响应和全部相关构造调用同步增加 `fixedLabelTime`。不为避免更新调用点新增旧签名补空构造器；被替换的内部构造入口直接更新或删除。
3. SQL 条件构建和标签组内存路径都使用 `[开始日00:00, 结束日次日00:00)`。解析在请求级完成，不逐记录解析日期；count、分页和导出使用同一个过滤规格，不在前端过滤当前页。
4. 新范围沿用现有计划解决时间的快速范围入口，与现有高级条件组按原优先级组合。**本次不新增高级筛选器的修复时间操作符集合**，避免顺带改变高级 datetime 的既有契约；高级标签组/AND/OR 与新范围组合必须测试。
5. 修复时间排序接入现有字段白名单和内存比较器；默认排序不变，空值顺序沿用记录页当前规则，不借此修改跨页面空值排序。时间相同使用稳定议题身份作次级顺序，避免翻页漏重。
6. 新参数进入规范化请求和快照哈希。更新受影响记录画像规则版本，旧快照自然失效，不全库清缓存。
7. `CustomerIssueRecordRowResponse` 是 CC_PRODUCT 与延期共用的内部响应，统一增加字段，不为隐藏结构扩展另造 DTO。延期 JSON 因此可能多一个字段，其页面/Excel不展示；这是须登记的预期结构变化，不宣称整个延期接口字节不变。共享快照记录也新增字段，两个画像均升版本；其他模块若不序列化或消费它，不改输出 DTO。

### S4. 页面、详情与 Excel 一次贯通

- CC_PRODUCT 快速筛选增加独立“修复时间”日期范围，使用清楚的起止占位符；状态仍选现有“已修复/完成”。日期默认不选，不自动改变用户原列表。
- 沿 `customer-issue-record-query-contract.ts` 的权威映射同步范围键、路由白名单、加载监听、活动条件标签、重置和列表/导出 API 参数。复用 `customer-issue-record-range-filters.ts`，不在组件中另写同义转换。
- 列表和详情在“缺陷修复人”后增加“修复时间”，其余列相对顺序保持；Excel 相同位置增加该列，统一为 23 列，格式 `yyyy-MM-dd HH:mm:ss`。未知值页面按现有空态显示，Excel 留空，不填零日期。
- 页面说明必须可见：这是最近一次标注完成的时间；没有事件时间的已完成议题不进入日期范围；撤销/重修会改变历史区间结果。继续显示现有最近同步状态，不把查询时刻当作数据更新时间。
- 现有 Excel 入口、权限、文件名和 sheet 结构继续使用原契约，不新增“周报下载”API。
- 解决导出期间变化导致的跨页混读：在现有导出服务使用一个只读 REPEATABLE READ 事务读取一致的事实视图，复用 `loadRecords` 的筛选/分页逻辑，不混用不同时间生成的页面缓存。显式事务边界必须真实生效，不能依赖同类自调用注解；不加数据库写锁。共享导出涉及延期专题，须锁定其结果不变并评估长读事务成本。
- 页面与另一次导出之间如果事实已更新，结果允许反映新事实；不承诺跨两个独立请求的永久冻结。只保证相同事实版本和相同条件结果相同、一次导出内部一致。

### S5. 迁移、回填与性能

1. 不新增业务表或同义时间列，保留 `fixed_label_time`。若需要新的物理索引，新增 Flyway 迁移，不改已执行脚本。
2. 部署前按真实来源核查事件表完整性、action 物理类型、缺失事件和旧回退影响范围。仅在事件历史未完整时补齐该来源事件镜像及其依赖，不把 GitLab 全库同步当作默认步骤。
3. 删除回退后必须做同源 ISSUE 全量事实重建，消除存量回退值并覆盖“事件补齐但 issues.updated_at 未变”的议题；不是清库，也不要求 MR 全量重建。发布清单明确 `facts.rebuildRequired=true / scope=issue`。
4. 复用现有构建发布流程。D-10 的全量构建是分批提交，重建过程中不能宣称整库原子切换或新字段已全部可信；以重建与投影终态作为本功能发布验收时点。
5. 测量周范围带/不带里程碑、客户和标签组时的 SQL、导出及事件反查。候选索引按来源/项目/修复时间及稳定身份设计；是否建索引及列顺序由 `EXPLAIN (ANALYZE, BUFFERS)` 决定，不在日期列上套格式化函数导致范围索引失效。
6. 不新增缓存掩盖慢查询，不改变增量扫描算法，不顺带处理已记录的全平台事实目标洪峰。目标容量在内网固定数据量实测，本地夹具不外推。

## 7. 接口契约

### 7.1 现有端点扩展，不增加新端点

- `GET /api/customer-issues/records`
- `GET /api/customer-issues/records/export`

共同示例参数：

```text
topic=cc-product
bugStatus=已修复/完成
fixedLabelTimeStart=2026-09-14
fixedLabelTimeEnd=2026-09-20
```

- 参数是日期，不传时区偏移或前端计算的 `23:59:59`。范围为 `>= 2026-09-14 00:00` 且 `< 2026-09-21 00:00`。
- 其他过滤条件、默认范围、分页及授权延续现有契约。请求日期为空不新增范围约束；不需要 `onlyFixed`/`weeklyMode` 等第二套状态参数。
- 响应新增可空 `fixedLabelTime`；沿用平台现有日期序列化契约。TypeScript 类型显式 `string | null`，不能只用有值 mock。
- SQL值全部绑定参数；排序列只允许白名单，日期和状态不拼进 SQL。

### 7.2 日期与时区约束

本次按平台现有展示日期的日历口径筛选，前端不能随浏览器时区二次改变所选日期。来源 `timestamp` 无偏移值目前原样保留，`timestamptz` 按既有入口归一 UTC；不能从列类型或响应的 `+08:00` 推断它已正确换算为北京时间。

证据：`docs/architecture.md:35`，`GitlabSourceTimestampNormalizer.java:17`，`backend/src/main/java/com/data/collection/platform/config/PlatformJacksonConfiguration.java:22`、`:43`。后者给 LocalDateTime 附加 Shanghai 偏移，不执行 UTC 到北京时间的换算。

本功能不局部 `+8h`，不改全局 Jackson。验收必须对照跨午夜源事件、事实值、页面、Excel和查询边界；若业务要求北京时间自然周且真实来源与当前平台口径不一致，须先报告共享时间契约差异并单独取得修正批准，不能带着未解释的时区偏差宣称“每周修复数正确”。

## 8. 验收标准

### 8.1 确定性业务矩阵

| 场景 | 期望 |
| --- | --- |
| 已完成，最近加标在区间内 | 纳入一条，列表/total/导出身份集合一致 |
| 区间前已修复，只在区间内编辑标题或评论 | 不纳入，不能把更新时间当修复时间 |
| 只有待合并/未更新/未复现/关闭状态 | 精确周修复查询不纳入；原广义修复率不变 |
| 已完成但议题仍opened | 纳入；GitLab开闭状态与测试状态独立 |
| 先修复后撤标 | 当前时间为空，区间查询不纳入 |
| 上周修复，本周撤标再修复 | 只按本周最近时间纳入，不保留上周冻结记录 |
| 复合状态包含精确完成成员 | 按成员规则处理，不按整个字符串相等或子串模糊匹配 |
| 完整事件来源但该议题无事件 | 时间null；普通列表仍可见，日期范围不纳入，不伪造 |
| 起日00:00、结束日最后微秒、次日00:00 | 前两者纳入，最后一个排除 |
| 只给开始/结束，跨月/年，闰日，非法日期，起止颠倒 | 单边和合法日历正常；非法入参明确失败 |
| 2025创建、当前周修复 | 按用户选择不纳入 |
| 多客户、多模块、多状态，同源/跨源同IID | 不把一议题拆成多行，不混淆完整身份 |
| 修复范围＋客户/里程碑/标签组/AND或OR高级条件 | SQL和内存路径结果一致；不能漏掉范围条件 |
| 仅新增修复事件、当前标签与issues均未变化 | 自动派生并更新事实/投影，页面不依赖人工重建 |
| 删除最新事件/标签改名/归属迁移进入ODS | 旧/新目标正确重算，无残留时间或跨源污染 |
| 来源只建表、全量半途失败、取消、完整空表 | 前三者不能冒充就绪；完整空表可合法就绪 |
| 导出超过一页且期间有新事实提交 | 单次导出保持同一数据库读视图，不漏行/重行 |

### 8.2 测试层和回归范围

- 后端单元/真实 PostgreSQL 集成：来源SQL、Mapper、血缘/Resolver、事务门禁、全量/定向构建、请求装配、SQL及标签组内存范围、快照键、排序、完整Excel表头与单元格。不能只断言SQL字符串。
- 正向自动链路：新增/撤销/重加事件 → 镜像 → outbox → ISSUE事实 → 投影 → 查询；失败恢复不越过来源门禁。普通新增事件和人工历史修订修复路径分别测试，不混为“增量都能发现”。

- 前端：query映射、路由刷新/返回、清除单项与全重置、API列表/导出参数一致、标签组组合、空时间、详情及23列。真实浏览器选择精确状态和日期完成筛选、翻页、下载；检查请求参数、控制台、延期页面及其他客户页面。
- 命令入口：后端现有 Maven 默认测试及定向集成测试；前端 `npm.cmd run test`、`typecheck`、`lint`、`build`；仓库API/事实字段/迁移契约及四项文本产物门禁。执行以隔离测试库为前提，不触碰用户业务库做测试夹具。

## 9. 风险与假设

1. 此方案根据当前代码证明“已有能力及缺口”，不证明内网事件历史已完整。真实来源、时区与数据量是部署验收项。
2. 删除临时来源回退意味着不完整环境显式受阻；这是推荐的目标契约，不是隐藏降级。未补齐来源和完成ISSUE重建，不得启用该功能并宣称结果可靠。
3. 既有响应效率同样读取该字段。完整合规数据必须保持原值；若旧值来自关联时间或非精确状态，新值纠正属于需展示与审阅的有意数据变化，不以“零回归”字样掩盖。
4. 本次不修改全局时间语义、空值排序或全量构建可见性。涉及这三项的验证发现不得用局部条件补丁吞掉，应按真实影响范围裁定。
5. 当前快照、评审代码与进度文档已有用户改动。任何实现、基线更新、提交、发布及真实数据操作均在用户指派后按范围执行；本方案阶段到文档交付为止。
