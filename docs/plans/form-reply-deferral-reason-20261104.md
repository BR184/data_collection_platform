# 回复表单延期原因与标签同步方案

## 当前状态与待办

业务需求已确认：延期原因必须单选。以下实施方案待用户审批，审批后员工沿原表单功能分支实施。

| 编号 | 目标 | 完成标准 |
| --- | --- | --- |
| R1 | 增加条件必填单选项 | 选择申请延期时必须且只能保存1个原因；切换其他状态后该字段隐藏、清空 |
| R2 | 复用现有标签写回 | 技术卡点改资源卡点后，旧原因摘除、新原因添加；取消延期后本期标签清空；其他标签保持 |
| R3 | 验证真实闭环 | 本地325 Issue完成保存→加标→改原因→换标→取消延期→摘标，重复处理无标签差异 |

本期仅面向CCProduct（325）的FORM回复。新增持久表、队列、worker及独立业务类均为0，扩展既有字段规格、业务快照和写回规划。

## 表单规则

在“修复状态”后增加“延期原因”，使用与修复状态相同的单选圆钮：技术卡点、资源卡点、数据异常。

- `修复状态=申请延期`：显示，必填，保存一个枚举值；缺失、数组、多值或未知值均拒绝保存。
- 其他修复状态：隐藏并清空延期原因；后端按同一条件校验，拒绝残留值。
- “缺陷原因”仍为原多选，“具体原因”仍为原文本，三者分别维护。

使用已冻结的字段/选项稳定身份及既有条件必填、条件清空、单选控件，不在页面按字段名称硬编码。管理页及填写页布局保持。

更新默认规格，在现有草稿上追加字段并保留管理员其他配置，通过草稿→预览→空结构发布流程，为已启用的325回复范围发布新版本。旧记录原位保留、旧规格不改；旧版缺字段不当作取消延期、不自动清标签。使用新字段及本期自动标签需填写新版回复。

## 标签规则

本地CC镜像已核对以下实际标签及325议题关联：

| 业务选择 | GitLab实际标签 |
| --- | --- |
| 申请延期 | `状态：申请延期` |
| 技术卡点 | `技术卡点` |
| 资源卡点 | `资源卡点` |
| 数据异常 | `数据异常` |

建议复用现有`状态：申请延期`，作为本次审批内容；界面继续显示“申请延期”。

仅对存在本次新版回复记录的FORM议题纳入本期规则（包括后来作废的记录）。这四个标签由最新有效回复维护；其他原因和业务标签保持原样。人工改动这四个标签后，既有写回轮次仍按表单目标收敛。

| 最新有效回复 | 本期目标标签 |
| --- | --- |
| 申请延期＋技术卡点 | 状态：申请延期、技术卡点 |
| 申请延期＋资源卡点 | 状态：申请延期、资源卡点 |
| 申请延期＋数据异常 | 状态：申请延期、数据异常 |
| 改为其他修复状态，或已无有效回复 | 空集合 |

新增=目标中缺少的标签；移除=当前四标签中不再属于目标的标签；已一致则该部分无HTTP写入。原因切换时保留申请延期、只换原因。

沿用`(创建时间,记录ID)`取最新有效回复，编辑时间不重排；编辑旧回复不覆盖较新回复，作废后回退到下一条有效回复。旧版缺字段沿前述旧版本边界处理。

`数据异常`在现有规则中也参与状态识别，写入/摘除会沿既有统计口径传播。本次保留该行为及原有七类延期原因口径；新增单选字段只提供本期三类写回目标。

## 实现路径

| 入口 | 修改 |
| --- | --- |
| `issue_reply.json`、既有规格校验/生成器 | 增加单值枚举与条件，发布新版字段结构 |
| `IssueBusinessInput.ReplySnapshot`、`FormIssueInputResolver` | 按所属版冻结规格读取延期原因，区分旧版缺字段与明确取消 |
| 既有事实/延期轮次 | 保存后沿原head→事实公开→授权轮次触发规划 |
| `CustomerIssueDelayLabelWritebackPlanner/Service` | 保留响应已延期/解决已延期判定，合并本期四标签差异 |
| 既有Queue/Worker | 复用add/remove目标、授权修订、事实版本及form_input_hash；发送前重新核验，新原因发布后旧任务不发送 |

规划在既有稳定读事务内，确认表单输入签名与已发布事实一致后取目标；不同则等待原事实链收敛。标签目标保存在现有作业字段。写回后的标签回采走原镜像/事实链，不从标签反推表单选择。

继续使用现有“延期标签写回”开关及授权，不新增旁路、开关或发送接口。表单保存成功表示入库成功，标签由既有链路异步更新。本需求与链接评论投放方案独立。
