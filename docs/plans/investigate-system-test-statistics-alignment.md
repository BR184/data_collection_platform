- 老平台缺陷汇总链路：`ModuleTable.vue -> /dataAnalysis/getModuleTable -> DataAnalysisController -> SpiderIssueDataService.getModuleTable -> SpiderIssueDataDAOImpl.findByModuleTableAndTestingPhase -> ModuleTableRow`。
- 老平台“工程图 / 回退”规则：项目 9；父阶段展开子阶段后对 `testing_phase` 逐项执行包含匹配；严重程度为“一级缺陷”；标题包含“（退”“回退”“倒退”任一项；应用公共排除；模块字段按 `&` 拆分、去空白后与“工程图”精确相等。同一多模块议题在每个命中模块各计一次，总计只计一次。
- 老平台标签解析会把同类多个阶段标签保存为 `阶段A & 阶段B`，这是缺陷汇总和部分图表使用包含匹配的真实数据原因，不是宽松查询的偶然实现。
- 新平台 `IssueClassificationRules.isRegression`、严重程度归一、模块成员和公共排除与该指标一致；当前 `SystemTestDefectSummaryBoardService` 已在提交 `5ad8d7c7` 改为基于 `testing_phase` 的包含匹配，并统一用于父表和下钻。
- 本地目录含 CC2026R4 的 7 个子阶段，但 `issue_fact` 中没有 CC2026R4 测试阶段事实；CC2026R3 有一条复合阶段事实。按老平台规则重算 R3“工程图 / 回退”为 110，精确阶段子集在该指标样本中也恰为 110，最新统计快照单元格为 110。因此当前源码的缺陷汇总链路在本地代表样本对齐，内网 R4 差值不能由本地数据直接归因。
- 确定缺陷一：`SystemTestDelayAnalysisBoardService` 的 SQL 使用包含成员谓词加载数据，随后 `buildRuleFlowSnapshot` 调用精确成员匹配，复合阶段事实会先被加载再被丢弃；老平台该页面通过 `SpiderIssueDataQueryBuilder.setTestingPhases` 使用包含匹配。
- 确定缺陷二：`SystemTestHorizontalComparisonExportService` 对议题事实使用 `lower(testing_phase) = ?`，而老平台横向对比直接复用缺陷汇总 `getModuleTable`，其议题指标应使用包含成员匹配。原因分析部分仍应保持精确匹配。
- 确定缺陷三：新平台议题多元看板对 11 张图统一使用 `testing_phase in (...)`。老平台实际为混合契约：缺陷阶段、缺陷模块、未关闭缺陷占比 3 张图使用精确匹配；缺陷严重程度、缺陷原因占比、缺陷原因、模块修复率、修复人缺陷数量、申请延期模块、申请延期原因、回退模块 8 张图通过 `SpiderIssueDataQueryBuilder.setTestingPhases` 使用包含匹配。当前统一精确会漏掉这 8 张图中的复合阶段事实。
- 缺陷原因表、议题阶段统计、议题查询和非法数据的老平台入口使用阶段集合 `IN` 或单阶段 `=`，新平台保持精确匹配符合基准。不能用全局 `LIKE` 修复上述差异。
- 架构根因：阶段目录只负责父子展开，但“展开后的成员如何匹配事实”被分散到 SQL helper、内存 helper、看板自定义逻辑和导出自定义 SQL；同一页面甚至在 SQL 与内存层选择不同语义，缺少结果级契约测试。
