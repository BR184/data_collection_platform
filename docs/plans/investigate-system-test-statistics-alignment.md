## 恢复线索

- 当前阶段：代码与数据证据采集。
- 恢复后首条命令：`rg -n "回退|工程图|缺陷汇总" backend frontend D:/projects/spidergitdata-dev`。

## 目标与边界

- 目标：以老平台为基准，确定 CC2026R4 下系统测试缺陷汇总“工程图/回退数量”的老平台统计方式、新平台实际方式、差异根因及正确修正范围。
- 扩展检查：确认系统测试其他页面是否复用同一阶段范围、状态、标签或维度规则，并列出受影响面。
- 成功标准：每项结论均有具体源码、SQL/数据样本或运行结果证据；明确应修改的权威模型、调用点和回归测试。
- 禁止：调查阶段不修改业务代码；不把老平台源码复制进新平台；不干扰其他工作树改动；不以页面显示或类名替代真实代码链路。

## 约束与背景

- 老平台目录 `D:/projects/spidergitdata-dev` 只读，仅提取外部行为、业务不变量和统计口径。
- 新平台正式系统测试链路以 GitLab 镜像、ODS、事实层和统计快照为准，不引入老平台数据库依赖。
- 本地缺少内网完整数据时，代码结论与本地样本结论分开标注。

## 证据与根因

- 待补充：入口、阶段解析、事实字段、聚合条件、维度映射、缓存/快照和导出链路。

## 方案与步骤

1. 定位新老平台页面入口、请求参数和后端统计入口。
2. 深读老平台 CC2026R4 阶段解析及回退数量的原始查询/聚合规则。
3. 深读新平台对应事实字段构建、阶段范围解析、统计快照和展示映射。
4. 使用本地数据库对代表性工程图记录逐层对账，必要时查询 Git 历史确认回归来源。
5. 扩展审计系统测试其他统计页的共享规则和独立规则，形成影响矩阵。
6. 输出确定根因、目标设计、修改清单、迁移/重建要求和验证方案。

## 决策记录

- 已选：从具体指标反向追踪至源数据，随后扩展共享调用链；原因是可避免把单一页面误判为全局问题。
- 否决：仅比较页面 DTO 或直接调整显示值；原因是无法证明统计口径一致。
- 待定：是否需要修改事实模型、阶段目录成员或仅修改统计聚合，须由证据决定。

## 接口契约

- 本轮调查不新增或修改 API、表结构、函数签名和交互协议。

## 风险与假设

- 风险：本地数据不等同于内网 270 万级真实数据，无法直接复现用户看到的绝对计数。
- 风险：老平台可能同时存在前端二次计算、后端服务和 Mongo/MySQL 查询，必须确认实际运行入口，不能只读单一文件。
- 假设：用户所称“回退数量”对应系统测试缺陷汇总中工程图行的回退状态统计；若代码存在多个同名指标，将逐一辨别。
