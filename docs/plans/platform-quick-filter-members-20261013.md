## 目标与边界

- 用户要求调查全平台快速筛选并落成修正方案：明确为集合的字段，候选应是独立成员，不能把多个测试状态等合成一个可选标签。
- 快速筛选每个字段选择一个独立值；多个状态通过条件筛选增加条件，以 AND/OR 组合，不把多状态串作为一个条件值。
- 成功标准：候选、展示和筛选命中使用同一字段语义；选择其中一个成员能命中包含该成员的议题，议题仍只出现一次；新状态名称无需改枚举。
- 不改事实合并文本、议题粒度、同步链路、指标公式、统计范围和导出事实值；不调整客户问题功能缺陷明细主表的状态列，该需求属于另一计划。
- 不全局拆分所有字符串，不更换共用选择控件，不增加兼容别名、双轨候选或固定状态清单。

## 证据与根因

### 已核实的影响范围

| 链路 | 已证实情况 | 本单元处理 |
| --- | --- | --- |
| 客户问题缺陷汇总、缺陷原因、延期、响应效率、按功能、客户维度统计下钻 | 6 个生产者调用共用明细分页和候选生成；均返回 `bugStatus` | 覆盖全部生产者，包括展开区字段 |
| 系统测试缺陷汇总、延期、阶段统计下钻 | 3 个生产者使用同一链路并返回 `bugStatus` | 覆盖状态及实际存在的其它集合字段 |
| 系统测试缺陷原因下钻 | 使用同一链路，但当前明细不返回 `bugStatus` | 核对其模块/原因/目录显示字段，不制造不存在的状态列 |
| 客户问题、系统测试记录页及非法数据页的状态候选 | 使用 `fromIssueStatusMembers`，已按成员生成 | 保持，增加与下钻一致的行为回归 |
| 上述记录页类别候选 | 标签归一化将多个类别以 ` & ` 合并，候选使用普通 `toOptions` | 修正类别候选及对应匹配 |
| CC_PRODUCT 记录页测试阶段候选 | 事实可能含多个阶段，候选使用普通 `toOptions(values.testingPhases())` | 修正真实事实阶段成员，不影响系统测试范围目录候选 |
| 评审、代码走查及其它页面 | 控件共用，但分别构建候选；不能由控件复用推断同一缺陷 | 锁定标量/既有独立成员行为，不批量重写其业务规则 |

### 根因链

1. `RecordTableFilterFields.vue` → `RecordTableFilterFieldRenderer.vue` → `SmartSelect.vue` 只渲染传入 options，不负责解释业务字段。
2. `StatisticBoardDetailDialog.vue` 的 `detailColumnFilterOptions` 同时读取后端候选和当前页原始值；`addDetailFilterOptionValues` 使用仅识别逗号/顿号的 `splitTags`，遗漏 `&`。即使只修后端，当前页补充也会重新加入组合候选。
3. `AbstractStatisticBoardService.buildDetailQuickFilterOptions/detailOptionValues` 同样没有字段上下文，仅按 `[、,，]` 拆所有文本。
4. 下钻 `detailCellMatches` 对所有字段统一执行 `actual.contains(expected)`；这不同于集合成员匹配，也与普通输入搜索没有区分。
5. 主记录页状态有专用成员工厂；类别、CC_PRODUCT 事实阶段使用标量工厂。`IssueFactFilterValuesQuerySupport.splitAggregatedValues` 只拆查询聚合的换行，不拆成员，因此不能指望上游已修正。

## 方案与步骤

### A1：建立字段清单并增加失败回归

- 按实际列定义和查询源登记集合/标量/文本搜索，不依据中文列标题推断。复用已有 `StatisticDetailColumn.key/type`，集合列明确使用 `tags`；目录显示名、标量标签使用 `tag` 或现有标量类型。无需新增通用元数据协议。
- 状态复用 `IssueStatusMembers`；延期原因复用 `IssueDelayCauseMembers`；模块复用 `IssueModuleMembers`。类别和 CC_PRODUCT 事实阶段按各自来源的规范合并格式实现最小成员解析，候选和匹配共用，不套用状态的“已修复”特殊逻辑。
- 目录父阶段显示名与原始事实阶段不是同一语义：系统测试目录显示名保持完整；只对明确来自复合事实的阶段使用成员解析。
- 原始标签列表按原列表边界处理，不能把单个原始标签名称中的 `&` 再拆开；项目、标题、人员显示名、自由文本原因等不因含符号变成集合。
- 先用现有公开组件/API 测试复现：状态组合候选、类别组合候选、阶段组合候选，以及成员名称相近时的误命中。

### A2：一次修正共用下钻链路

- 后端候选生成携带列定义，用同一字段规则处理候选提取和选择匹配。只对登记为集合的字段拆成员；单值选择按既有业务契约匹配；任意关键字和标题输入保留模糊搜索。
- 前端按同一列语义生成标签和当前页补充候选；`bugStatus` 继续调用现有状态解析器。独立候选不能再次被拼回带 `&` 的组合。
- 主表和展开区同一字段复用规则，维持同一明细记录、分页、排序及过滤上下文。当前候选数量上限不在本单元扩大，不把容量问题混入修正。
- 不移除读取身份、版本、集合切换或业务日参数；分页改变和筛选改变仍只发出一条有效请求。

### A3：补齐主记录页遗漏

- 在客户问题、系统测试记录及非法数据候选服务中替换类别的标量处理，同步核验 SQL/内存查询匹配。
- 在 CC_PRODUCT 记录候选服务中修正事实测试阶段成员；对应快速筛选和条件筛选复用同一规则。
- 已正确的状态、延期原因、模块、计划合并分支等保持各自规则；不将它们统一替换为任意字符串拆分。

### A4：验证与收口

- 自动测试覆盖下列验收表；前端定向 Vitest、类型检查、后端相关单测/查询集成回归及默认快速覆盖护栏。

- 日常实施不主动运行黄金全链路、不更新快照。接口候选和筛选结果属于有意产出变化，记录旧/新差异；后续仅在用户明确要求或发布验收时运行门禁，快照更新另行取得用户确认并审阅，不能手改或弱化比对。

## 决策记录

- 采用“共用下钻修正 + 主记录字段补齐”，因为共用控件不拥有业务候选语义。
- 采用按真实字段语义解释既有事实文本；不迁移事实存储，也不新增状态枚举。
- 否决只修前端、只修后端、给所有文本扩大分隔正则、把所有选择都改成模糊匹配，以及把多个状态变成一个组合候选。
- 本方案不包含功能明细状态列替换。建议先完成本方案，使另一需求复用的快速筛选正确；两者可独立实现和回退，后一方案不能冒领本方案的修复验收。
- 不需要重大架构决策或新 ADR；规则权威仍为现有业务规则文档。

## 接口契约

- 无新增端点、表结构或事实格式；沿用明细 `columns/records/quickFilterOptions`、`filters[detailFilter.<key>]` 与现有条件组协议。
- 示例：记录 `bugStatus="已修复/完成 & 已测试通过 & 新状态"`，候选为 `["已修复/完成", "已测试通过", "新状态"]`；单个快速筛选值为 `detailFilter.bugStatus="已测试通过"`。
- 多条件示例：`logic="AND"`，两条 `fieldKey="bugStatus", operator="eq"` 的条件分别使用 `value="已测试通过"`、`value="新状态"`；OR 表示任一命中。不得使用 `value="已测试通过 & 新状态"` 伪造一个成员。
- 共用内部帮助方法应显式接收列定义，例如 `detailOptionValues(StatisticDetailColumn column, Object value)`；候选和匹配必须复用同一解析入口，参数变更同步改所有调用点，删除旧的无上下文路径。
- API 内容的有意变化限于候选拆分与正确匹配结果；事实值、业务成员数和统计公式保持原义。

## 验收标准

| 输入/操作 | 预期 |
| --- | --- |
| 三个状态含两个此前不存在的名称 | 三个独立候选/标签，无状态白名单 |
| 状态含混合分隔符、空白、重复成员 | 去空去重，`已修复/完成`保持一个成员 |
| 分别选择组合中的任一状态 | 命中同一议题，每页及总数不重复 |
| 两个条件 AND/OR | 分别为全部满足/任一满足，符合成员语义 |
| 后端候选与当前页补充同时存在 | 不重新出现组合候选 |
| 类别/事实阶段各两个成员 | 分成两个候选，选择任一成员可查询 |
| 普通项目名含 `&`、逗号，目录显示名含符号 | 保持完整，不误拆候选 |
| 状态“已修复”及相近名称 | 保留既定特殊口径；其它状态按成员匹配 |
| 主表/展开区、换页、重置、范围切换 | 候选和查询语义一致，读取身份与范围不丢失 |
