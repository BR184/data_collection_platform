### 二、逐项解决方案

#### R01：数据库浏览器泄露未声明的敏感列

**根因位置：**`backend/src/main/java/com/data/collection/platform/service/DatabaseBrowserQuerySupport.java:77`

当前使用 `SELECT *`，行映射器又将所有物理列写入响应。页面声明的 `columns` 并未限制 `rows`。

##### 目标设计

**表定义不仅描述如何展示，还必须限定允许查询和返回的字段。**

1. 查询构造器按照允许列生成显式投影，删除这条路径中的 `SELECT *`。
2. 行映射器按照同一列定义读取结果，不再遍历全部 ResultSet 元数据。
3. 排序、搜索使用经过验证的字段定义，不接受任意物理列名。
4. 对数据库浏览器的列表、详情、导出等实际入口进行调用链核对，防止只修页面请求、遗漏其他输出。
5. 对动态表定义，允许列必须来自服务端受控目录及其权限规则，不能直接把“数据库中存在”解释为“允许公开”。

对于 `gitlab_sync_configs`，`db_password`、`api_token`、`system_hook_secret` 不进入公开查询结果。

**不采用：**

- 前端隐藏列；
- 查出全部数据后针对三个字段临时置空；
- 根据字段名包含 `password` 等关键词做模糊脱敏；
- 允许列配置不完整时回退到 `SELECT *`。

##### 防回归验收

使用合成敏感值验证：

- 原始 JSON 中不存在敏感字段及其值，而不只是界面看不到。
- 允许列的名称、类型、空值、排序和分页保持正确。
- 后续新增物理列不会自动进入响应。
- 正常配置接口的脱敏行为不受影响。
- 未授权访问仍被拒绝。

这里删除敏感字段属于有意的输出变更，应单独展示黄金基线预期差异，不能悄悄更新快照。

#### R02：新装包无法直接进行首次增量升级

**根因位置：**`scripts/package_intranet_offline.py:502`、`:555`

新装 `.env` 未写入卷名，增量 Compose 却要求它们必填；打包自检使用合成环境变量掩盖了这条断链。

##### 目标设计

**新装、升级和回滚共同使用明确、持久的实例身份与存储身份。**

1. 新装包生成时明确写入 PostgreSQL 卷名和后端日志卷名。
2. 新装与增量 Compose 使用相同的卷身份变量。
3. PostgreSQL 卷是否由首次安装创建、是否在升级中作为外部卷引用，可以不同；实际卷身份不能变化。
4. 升级前验证目标卷存在、实际挂载关系正确，不能只验证 Compose 能解析。
5. 打包校验增加真实生命周期组合：
   - 新装产物；
   - 使用该产物生成的运行环境；
   - 首次增量升级；
   - 后续再次升级。

##### 已交付旧包的处理

已经部署且缺少卷变量的实例，需要单独的一次性升级准备步骤：

- 从实际容器挂载及 Compose 标识读取卷身份；
- 精确核对 PostgreSQL 数据目录和日志目录的挂载；
- 发现缺失、多义或不一致时停止，不猜名称；
- 验证成功后原子写入规范环境文件。

这不是给新实现长期保留兼容分支，而是把真实旧部署迁移到目标契约。其范围和退出条件应写入部署标准，并在实施前确认。

**不采用：**按项目名拼出一个“看起来正确”的卷名，或缺变量时自动创建空卷继续升级。

##### 防回归验收

- 新装后首次升级不需要人工补参数。
- 连续两次升级均连接原 PostgreSQL 数据卷。
- 数据标记、卷身份、端口与数据库身份不变。
- 多实例之间不会串卷。
- 无法确认卷身份时，在加载镜像、替换文件、停止服务之前退出。
- 日志不打印完整环境文件或展开后的秘密值。

#### R03：回滚失败时已经覆盖现场 Compose

**根因位置：**`scripts/package_intranet_offline.py:1299`

当前顺序是先替换现场文件，再判断恢复后的镜像是否符合目标基线。

##### 目标设计

将回滚拆为三个明确阶段：

**只读预检 → 原子提交配置 → 启动与验收。**

**第一阶段：完整预检。**

在临时文件上完成：

- 备份清单及完整性检查；
- 包身份、目标基线和镜像身份检查；
- 使用现场有效环境解析候选 Compose；
- 数据卷、网络、端口、挂载等不变量检查；
- 镜像可用性检查；
- 应用回退与当前数据库状态的适用性检查。

镜像检查使用结构化 Compose 结果，不再依赖全文 `grep`。

回滚语义应明确为：**回退应用版本，保留实例身份与持久数据。** 不顺手恢复数据库，也不静默替换数据库密码、备份主密钥等现场身份。

**第二阶段：提交。**

只有预检全部通过，才原子替换现场 Compose，且保留原现场配置用于补偿。

**第三阶段：启动验收。**

启动失败与预检失败必须区分：

- 预检失败：现场完全不变。
- 切换后启动失败：执行预先定义的补偿流程，并明确报告服务状态。
- 补偿也失败：保留证据和恢复入口，不能输出“已回滚成功”。

**不能承诺应用回滚自动撤销数据库迁移。** 不适合应用单独回退的版本，应在预检时拒绝并指向数据库恢复 Runbook。

##### 防回归验收

覆盖错误基线、文件损坏、镜像缺失、环境不匹配、解析失败、启动失败。

所有预检失败必须满足：

- 原 Compose 和 `.env` 字节不变；
- 容器运行状态不变；
- 数据卷不变；
- 不执行任何停止或启动动作。

#### R04：过期 RUNNING 投影任务无法收敛

**根因位置：**`backend/src/main/java/com/data/collection/platform/service/FactProjectionTaskService.java:46`

任务领取不处理过期 `RUNNING`，但汇总又一直把它算作活动任务。

##### 目标设计

**租约必须能决定任务是否可以继续执行，不能只是一个时间戳。**

1. 为每次领取建立独立执行身份，不能只依赖可重复使用的 worker 名称。
2. 领取或回收路径原子识别过期 `RUNNING`：
   - 尚可重试：进入明确的重试流程；
   - 达到重试上限：进入 `FAILED`；
   - 不能无限保持活动状态。
3. 心跳、成功、失败和重试更新均校验本次执行身份。
4. 长任务按实际执行边界续租，失租后停止后续阶段。
5. 投影发布必须验证有效执行身份及目标 generation，防止旧 worker 在任务被重新领取后发布迟到结果。
6. 父运行汇总、发布栅栏和投影任务终态使用一致语义。

需要同时处理现有入队冲突路径：更高 generation 到来时，不得仅清空 owner，就假设旧执行者已经失去写入能力。

**不采用：**

- 只把过期任务重置成 `QUEUED`；
- 只让汇总忽略过期任务；
- 在完成 SQL 上加 owner 条件，却不约束实际投影发布。

##### 防回归验收

使用真实 PostgreSQL 事务测试：

- worker 崩溃后任务可恢复；
- 旧 worker 恢复运行时不能覆盖新执行结果；
- 重试次数有限且最终收敛；
- 高代际已发布后，低代际不能覆盖；
- 同一任务并发领取只有一个有效执行身份；
- 正常全量、增量、定向刷新及父运行发布行为不回归。

#### R05：备份失租后继续执行，与巡检争抢文件和终态

**根因位置：**`backend/src/main/java/com/data/collection/platform/service/backup/BackupOrchestrationService.java:390`

心跳异常只写日志；执行主体仍然可以移动文件、上传、轮转和写成功，巡检却可能同时删除其临时文件。

##### 目标设计

必须联合修正三条边界，不能只延长租约。

**1. 执行权传递到主体。**

- 每次备份建立独立执行身份。
- 心跳无法确认运行权时，主体进入停止提交状态，而不是继续当作持有租约。
- `pg_dump`、校验及上传操作受该执行上下文管理。
- 失租触发子进程终止和取消，并等待停止得到确认。

无法确认子进程已经停止时，不能假装清理完成，更不能立即删除仍可能被写入的目录。

**2. 产物与成功提交分离。**

- 临时文件按运行及执行身份隔离，禁止不同执行尝试共用 `tmp-<runId>.dump`。
- 最终产物具有唯一、不可覆盖的身份。
- 文件写完不等于备份成功。
- 只有持有有效执行权且完成校验的运行，才能登记成功产物。
- 本地列表、远程列表、下载和轮转遵守同一成功判定，不能仅凭文件存在或名称匹配认定成功。

远程上传和数据库事务无法天然原子化。因此必须接受并治理一种明确中间态：**可能存在未登记的孤立产物，但不能存在被误认成功的无效备份。**

单次“上传前检查租约”不能解决这一问题，因为检查之后仍然可能失租。

**3. 终态与清理协调。**

- 成功、失败、阶段更新均使用执行身份和预期状态条件更新。
- 终态不可被迟到执行者覆盖。
- 巡检先撤销执行权、协调停止，再清理已确认不再写入的暂存产物。
- 轮转只能基于已提交成功产物执行，失败运行不能删除最后一份有效备份。
- 对提交中断留下的孤立产物建立明确、可重复执行的清理规则。

##### 防回归验收

覆盖：

- 心跳失败、数据库短时不可达；
- dump、校验、上传阶段分别失租；
- 巡检与成功提交竞争；
- 文件完成但成功登记前进程退出；
- 取消失败或子进程迟迟未退出；
- 远程上传失败、轮转失败。

关键断言是：无效执行不能成为成功备份、终态不互相覆盖、有效历史备份不被误删、正在写入的暂存文件不被巡检争抢。

#### R06：首绘等待阻塞请求，且不受超时和取消保护

**根因位置：**`frontend/src/api-client/request.ts:304`

网络请求等待 `requestAnimationFrame`，但超时和中途取消监听在等待之后才建立。

##### 目标设计

**进度展示不能决定网络请求是否开始。**

1. 请求入口启动进度状态后，直接进入网络生命周期。
2. 移除网络执行路径对首绘 Promise 的依赖。
3. 超时和取消从请求入口统一建立。
4. JSON、Blob、下载响应共用同一网络执行路径，避免重复等待、重复计时和清理遗漏。
5. 进度条的延迟出现、最短展示时间属于展示层，不能阻塞或延迟真实请求结果。
6. 后台标签页不绘制时，请求仍正常完成、超时或取消。

这不是简单增加一个 `setTimeout` 与 rAF 竞争，而是移除错误依赖。

##### 防回归验收

- rAF 永不触发，请求仍能开始并结束。
- 请求前取消、请求中取消、超时均及时生效。
- JSON 和文件下载行为一致。
- 快请求无异常闪烁，慢请求进度正常。
- 后台标签页实际验证。
- 请求结束后计时器、监听器和进度状态均释放。

#### R07：旧列表响应覆盖当前筛选结果

**根因位置：**`frontend/src/composables/useRouteTableState.ts:95`、`frontend/src/views/review-data/useReviewDataRecords.ts:64`

当前请求编号只保护 loading，不保护数据、摘要和错误状态。

##### 目标设计

**每条列表查询链只有一个结果提交入口。**

1. 查询开始时冻结完整查询快照：页面、项目、筛选、分页、排序等。
2. 查询意图变化时立即使旧查询失效，不能等下一个 HTTP 请求真正发出后才失效。
3. loader 负责取得结果，不直接修改公共页面状态。
4. 统一提交入口仅接受仍属于当前查询的结果。
5. records、total、summary 和相关结果元数据一起提交。
6. 错误提示、失败清空、loading 和初始化标记也归属于对应查询。
7. 取消旧 HTTP 请求用于节省资源，但正确性不能依赖取消一定成功。

先核对 `bindLoader` 全部调用方，再决定公共组合函数的修改范围；不在两个页面各堆一组临时编号判断。

##### 防回归验收

- 旧成功晚于新成功：保留新结果。
- 旧失败晚于新成功：不能清空新表格或弹出旧错误。
- 快速切换项目、筛选、分页：表格、总数、摘要始终同源。
- 页面卸载后不提交结果。
- 自动刷新与手动筛选交错时，仍由当前查询决定展示。
- 已有独立保护的页面不能因公共改动失效。

#### R08：字段切换导致错误配置草稿被保存

**根因位置：**`frontend/src/views/DropdownOptionSettingsView.vue:131`、`:244`

当前字段身份、已加载配置身份和草稿内容可以来自不同请求。

##### 目标设计

**草稿必须拥有不可混淆的归属。**

草稿至少绑定：

- `fieldKey`；
- `configId`；
- `version`；
- 本次加载身份。

具体修改：

1. 切换字段后，旧草稿立即失去保存资格。
2. 配置加载成功时，只有字段和加载身份仍匹配才创建可编辑草稿。
3. 配置、候选、预览各自控制请求归属；预览还应对应具体草稿版本。
4. 保存使用已冻结的草稿身份，不能临时读取左侧当前字段再拼接共享内容。
5. 保存期间再次切换字段，旧保存响应不能回写新字段页面。
6. 新建、绑定、解绑、删除、重命名等实际存在的操作，都核对其异步归属。

##### 后端同时收紧契约

仅有 `version` 不够，因为不同配置可能同版本。

保存请求应携带明确配置身份，后端在同一事务中验证：

- 当前字段仍绑定该配置；
- 配置 ID 一致；
- 乐观锁版本一致。

不匹配就明确拒绝，不自动转存到当前绑定。

继续遵循 D-09：多个字段共享配置是合法行为，修改共享配置应影响其绑定字段；不能为了修复串草稿而偷偷改成一字段一配置。

##### 防回归验收

覆盖 A→B→A、相同版本不同配置、请求期间绑定变更、预览乱序、保存期间切换字段及共享配置更新。

必须实际点击界面保存，检查 API 参数与持久化归属，而不是只检查最终标签文字。

#### R09：迟到详情改变新增/编辑模式和保存目标

**根因位置：**`frontend/src/views/review-data/useReviewRecordDialog.ts:38`、`frontend/src/views/review-data/useReviewProblemItemDialog.ts:32`

多个独立可变字段共同决定编辑模式，迟到响应能够将“新增”变成“编辑另一条记录”。

##### 目标设计

**用明确的编辑会话代替可以互相矛盾的状态组合。**

编辑会话区分：

- 关闭；
- 新增；
- 加载指定对象；
- 编辑指定对象；
- 提交中。

每次打开、切换、新增或关闭都创建或推进操作身份。

1. 编辑目标在请求详情之前确定。
2. 详情只补充当前会话的数据，不能在返回时重新决定当前会话是什么。
3. 关闭立即使在途详情失效，迟到响应不得重新打开弹窗。
4. 提交冻结模式、目标 ID 和 payload。
5. 问题项同时绑定所属记录 ID 与问题项 ID。
6. 提交结果只更新对应会话；实际数据变化可以触发正确范围的列表刷新，但不能污染随后打开的新弹窗。

**已经发出的写请求不能靠前端取消视为已撤销。** 如果允许提交期间关闭，界面和结果处理必须承认服务器可能已经提交成功。

##### 防回归验收

- 编辑 A→编辑 B→A 迟到。
- 编辑 A→新增→A 迟到。
- 关闭后详情返回。
- 问题项跨记录切换。
- 提交期间关闭或切换。
- 连续点击提交。
- 详情失败后，不能误提交上一个对象。

验收不仅检查弹窗内容，还检查实际调用的是 create 还是 update，以及目标 ID。

#### R10：权限保存后未真正刷新当前用户权限

**根因位置：**`frontend/src/composables/auth-state.ts:31`、`frontend/src/views/PermissionSettingsView.vue:96`

初始化缓存和主动刷新共用一个会提前返回的入口。

##### 目标设计

将两个契约明确分开：

- `ensureCurrentUser()`：保证身份已初始化，允许复用当前缓存。
- `refreshCurrentUser()`：重新向服务器取得当前权限，不因已初始化而短路。

同步替换所有调用方，不保留旧函数作为转发别名。

并发规则：

1. 初始化可合并重复请求。
2. 权限保存后的刷新，不能复用保存之前启动的旧请求。
3. 新刷新结果不能被旧初始化结果覆盖。
4. 登录、退出和重新登录建立新的身份代次，旧请求不能重新写回已退出用户。
5. 刷新失败应明确展示未完成同步，不能伪装为刷新成功。

权限更新后，菜单、按钮、路由和当前页面访问状态都应重新计算；失去当前页访问权限时进入合法页面。

不改变 D-01 的 LDAP 身份与角色更新约定，也不把前端权限显示当作后端鉴权的替代。

##### 防回归验收

- 增加权限、撤销权限、恢复默认均立即刷新。
- 旧请求不能覆盖新权限。
- 刷新期间退出登录不会“复活”用户。
- 临时网络失败不被误判成正常刷新。
- 页面和按钮状态一致，后端拒绝路径仍有效。

### 四、防回归验收体系

#### 1. 确定性测试

- 升级回滚不更换数据卷。

###### 本轮问题与具体整改要求

**R03-F01（P1，失败部署的回滚入口被新的运行态前提阻断）**

- `scripts/package_intranet_offline.py:1536–1537` 用 `compose ps -q backend` 获取后端，空值即拒绝；该命令默认不列出停止的容器。升级中止、后端退出或被停机时，恰是需要应用回滚的情形，现在必须先让后端处于运行态才能继续预检。生成脚本替身复现：PostgreSQL healthy、备份完整、后端 stopped，脚本仍以“backend container is unavailable for volume identity verification”退出 1，未到达恢复步骤。原先“错误备份先覆盖 Compose”的缺陷已修，但不能因此通过当前回滚生命周期。
- **方案**：把“可验证的容器身份”与“容器正在运行”分开。使用包含 stopped 容器的确定身份查询，校验其 Compose 项目/服务标签与真实挂载，不能任意拿同名容器或跳过挂载保护；确实没有可证明身份时明确拒绝并给恢复入口。新增真实生成脚本正反例，覆盖停止后端、错误标签/挂载、合法回滚、启动失败补偿成功 exit 20、补偿失败 exit 21。
- **关闭条件**：同 schema 的 stopped 后端可合法回滚，错身份仍无副作用；正常/补偿三条路径有自动证据，真实部署演练另列待验。

**R05-F01（P2，停止确认、终态和运行权释放仍未形成同一收敛流程）**

- 另一确定顺序：恢复器已将执行撤销，worker 退出后 `release` 被 `execution_revoked=false` 条件拒绝，但 `executions.remove` 仍删除已确认停止的上下文；若此时没有持久化子进程 ID，后续 `stopExpiredExecution:590–603` 永远返回 false。实际复现：旧 worker 已结束，运行权仍占据，新手动触发 accepted=false。安全保留未知孤儿是必要的，但不能丢弃已有的停止确认后制造永久阻塞。

- **正式测试**：将两种顺序落实到真实编排＋仓库＋数据库测试，另覆盖回收器与 finally 交错、DB 结算失败后恢复、SUCCESS 后轮转失败、重启孤儿的受控处置。存量 legacy/PID 缺失仍按明确停止证据处理；Runbook 的“受控运维流程”须提供可执行的检查/结算步骤，不能只无限等下一巡检。
- **关闭条件**：停止后的运行必有可恢复结算路径，不存在“RUNNING 却无恢复索引”或“已停止但永远占用运行权”，旧执行者不能碰新运行/历史有效备份。

## 风险与假设

- 方案基于固定评审版本和核验时点工作树；后续并行变更可能改变问题位置或消除部分问题，实施前必须复核，不重复改动。
- R01、R04、R05 的前置核验是源码闭环，未证明真实环境已经发生泄露、任务事故或备份丢失；整改验收仍需相应运行证据。
- 租约检查与外部副作用之间存在竞争窗口；只在开始前检查一次运行权不足以保证发布正确，必须验证提交边界。
- 远程上传、文件系统和数据库事务不能假设全局原子；备份设计必须明确孤立产物和恢复边界，同时保护已有有效备份。
- 公共请求、路由表格和认证状态的调用范围可能较大；实现前要锁定全部调用点，禁止局部改签名造成隐性回归。
- 已发出的写请求可能已由服务器提交；界面取消不等于事务撤销。
- 有意的公开输出收紧和请求身份契约变更可能产生预期基线差异；差异必须经用户确认，不能自动接受。
- 一次性迁移不能借机自动修复来源不明的历史业务数据，也不能形成永久兼容层。
- 本地固定输入验证不外推内网容量；不以小数据演练宣称目标负载性能已经通过。
