### 证据与根因

以下是已验证的调查起点，不是所有现场失败的唯一归因；接手应结合当前代码复核：

- 0930 与 141807 包的 `backup.sh` 除部署身份三行外一致，仍为整库 custom dump 加关键表 dump；两包日志归档 Service/Scheduler class 相同。不能把现象简单归为新增备份步骤或硬件慢。
- `critical-tables.dump` 不包含 `read_dataset_rows`、`sync_run_fact_targets`，却包含三类事实表、ODS、统计/页面快照。所有文件增长不能只归给前两张大表；需要检查两份备份交集的数据增长。
- 数据集捕获保留原 ODS/业务表，再生成完整行 JSONB 修订。第一轮已取消有稳定键的 FULL_RECONCILE 强制新 epoch；当前完整副本、首次/无键捕获及全源 JSONB 判等成本仍在。
- 事实表从自然业务键唯一变成发布修订唯一；全量新 epoch 会与旧版本并存。历史修订是数据库可见的有效行，逻辑备份会导出，不等于死元组。
- 历史回收默认宽限 15 分钟、每周期一个域/最多 500 行，受引用保护；读生产/维护共用专用单线程调度。该设置没有证明能追上大库产生速率，也未证明长捕获下回收不会长期排队。
- 回收有重复零删除检查风险，并使用完整 COUNT 判断“是否还有行”；这类存在性需求应核查能否改成有索引支持的 EXISTS，不能据改一条 SQL 就宣布容量治理完成。
- 首错必须保留；失败/中止候选清理、已发布历史回收及正常发布是不同路径，不把最后一条 DELETE 或 IO 等待当作全部失败根因。

重点入口：

- `service/read/ReadDatasetRepository.java`：matchesCompleteSource、captureRelation、publishRevisions、deleteUnreferenced、countCreatedRows。
- `service/read/DatasetPublicationService.java`、MirrorDatasetPublicationWorker、DatasetRefreshWorker、DatasetProducerCatalog：冻结输入、捕获与触发。
- `service/FactTargetPublicationService.java` 与三类事实持久化协作者：完整/增量候选及事实修订。
- `service/read/ReadPublicationService.java`、ReadPublicationRepository、ReadMaintenanceService/Scheduler、ReadFallbackProperties：保留引用、清理及预算。
- `service/FactTargetJournalArchiveService.java`：审计日志生命周期。
