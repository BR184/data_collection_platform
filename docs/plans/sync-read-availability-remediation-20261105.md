## 已批准技术方向（实现尚未完成）

1. 保留发布版本作为正确性依据。同步失败只影响新版本产生，不撤销已发布版本的读取资格；缓存只是加速层。
2. 把可由完整事实按需计算的页面缓存预热移出强制发布门禁；保留真正必要的事实、关联、业务投影完整性校验。逐消费者证明可按需计算后才解除门禁，不把所有投影统称缓存后删除。
3. 最终原子提交不再承担与全量行数成比例的可见性改写。优先评估复用现有发布身份、在不可见准备阶段完成数据工作，最后切换少量发布元数据。增量修订覆盖、删除、父子关系、旧页面版本及回收必须先形成完整物理设计与真库反例；禁止只给现有UPDATE加LIMIT分批公开。
4. 以显式变化依赖缩小构建范围，避免局部配置变化扩大成无关事实全量；不能仅凭行数或最大时间戳判定内容未变。
5. 构建、必要投影、提交、缓存预热、回收分别记录状态和耗时。失败重试必须区分可重试故障与确定性错误；候选续做只在输入和执行权仍有效时允许。
6. 回收按行数及时间预算推进并监测产生/回收速率，保护当前和在用版本。默认不复制所有筛选组合，不为页面租约建立无限历史保留。

否决：统一放大30秒超时作为修复；同步前穷举所有页面组合；让读请求等待全量同步；返回空数组掩盖失败；缓存失效便删除旧完整事实；未证实归属就回退/混合其它会话代码。

## 发布协议实施设计

目标是消除最终事务里的全量事实改写，不承诺整个任务恒定耗时。保留一个来源域只允许一个活动候选和发布基线CAS，沿用已有输入证据、表单签名及执行权校验。

### 全量构建

候选写入独立epoch，事实、父子关系及必要业务投影在分批事务中完成；每批持久记录完成证据、行数和执行权。候选数据的公开资格由其所属发布身份决定。最终事务验证准备证明和基线，再一次切换域指针与发布状态，不逐行填写visible_from，也不逐行关闭旧epoch。旧页面仍按固定旧epoch读取，历史回收由引用保护决定。

### 增量构建

增量不能每次复制整域。拟复用现有候选根清单，持久记录每个受影响根的替换/删除及前后修订关系，准备阶段分批写入；这些关系只有所属发布成功后才参与可见性判断。读取固定发布序号下已发布的修订及其覆盖关系，候选或中止关系不影响旧结果。替换、删除、跨项目移动和父子关联必须以完整业务身份核验。

这是待真库反例验证的物理设计：下一步需对照现有根清单索引确定能否直接复用，只有缺少必要字段或约束时才新增前向迁移。不先引入第二套权威表。所有依赖visible_from/visible_to的读取、诊断、回收及初始采纳入口必须统一迁移，不能永久保留两种发布路径。

### 最终提交及恢复

- 完整输入和业务产物证明在准备阶段形成，最终提交只核对不可变证明、当前执行权及基线。表单记录签名和head的并发校验不能省略。
- heads消费、范围generation、写回资格与表单链接登记逐项审查；凡按根增长的工作，必须移到不可见的候选记账阶段，并由发布身份控制生效。不能只去掉visible_from更新后仍把同等规模工作留在事务里。
- 元数据原子提交失败时不出现新版本。准备结果是否可复用取决于输入证据、基线及执行权；有效时允许续做，无效时中止并有界回收，不能无条件重试整次重建。
- 多事实类型与多来源页面继续使用读取目录定义的完整依赖集合；单域成功不能使页面混读正在准备的其他域。

### 缓存与可观测性

可从固定事实版本计算的页面响应缓存按需产生，预热移至发布后有界后台任务；真正必须物化的业务投影仍留在准备阶段。缓存键包含发布版本、规则版本和完整请求语义，权限在每次请求重新验证。失败和未命中不删除当前可读事实。

状态明确区分采集、事实构建、必要投影、最终发布、缓存预热和回收。页面显示当前阶段、已完成量、最后进展时间及首个失败原因；不能在已进入发布后仍以“等待投影”代替真实状态。事件携带SQL操作名、耗时、批量、候选身份及SQLState，不记录Token和业务全文。
