## 摘要（评审先读这一段）

把现有「单一硬编码模板 + 固定列 + 同一表单上下文仅一行、存在则更新」的 `collect_form_records`，改造为**模板可登记、物理表按版本分离、按条目逐条提交**的表单框架。本期只交付基础框架、只落地**代码走查表**一个模板；其余模板、webhook→comment、可视化配置与「表单取代评论」的链路留阶段二（§6.5）。

三条根因（§5.3）：①单表固定列、无版本机制 → 字段一变就冲突既有统计规则；②表中无创建人标识 → 「仅创建人可编辑」无处判定；③唯一键是「一个上下文一行」→ 无法承载多走查人条目。

**评审需决策的 4 项**（决策共 16 项，见 §7：13 项已裁定；D14① 已实证、② 待决策；D15 有建议待定；D16 待决策）：

## 目标与边界

- 用户原始需求：见 §6.0（会议要点原文摘录）。
- 成功标准（可验证）：
  1. 代码走查表按新规范上线：竖版单列、除「补充说明」外全部必填、提交后只读且仅创建人可编辑。
  2. 多走查人以独立块级条目承载、支持接力填写；统计规则明确且不重复计数。
  3. 只保留创建时间与最新更新时间；不提供任何用户可见的编辑历史（审计日志保留，见 D1）。
  4. 表单挂平台域下共享登录态，访问与保存均无需二次登录。
  5. 存量数据在改造后仍可被代码走查/评审统计消费（不会被漏读、也不会重复计数）。
  6. `code_review` 相关黄金基线差异全部可解释；有意变更先展示差异再重建快照，复跑全绿。
  7. 两人同时打开同一表单、各自填写并保存，任一方的已保存条目都不被他人保存抹掉；并发修改同一条目时给出显式冲突提示，无静默覆盖。
  8. 打开页面后长期不操作或离开，不占用任何服务端资源、不影响他人填写与保存；未保存输入在重开页面或会话过期重登后不丢失。
- 明确不做：
  - 不做实时协同编辑（不推送他人编辑、不做 OT/CRDT/光标共享、不做后台自动草稿合并）。
  - **不引入占用/锁定/预约机制**——这是「页面长时间停留不影响他人」的前提；并发问题由「按条目逐条提交 + 冲突显式提示」解决，而非加锁。
  - 不强制绑定 GitLab 账号身份；不限制填写非本人的走查人。
  - 不承担「下线老数据采集平台」：老平台仍提供代码走查非法数据、评审数据与标签写回，且其写回无法在运行期关闭，属另一工作单元（见 §8）。
  - 不为尚未确认的模板（「测试相关」「CC 及 RS」）预留空实现或占位字段。

### 5.3 根因

现有实现无法承载新规范，根因三条：①单表固定列且无版本机制 → 任何字段变更都会破坏既有统计规则；②表中无创建人稳定标识 → 「仅创建人可编辑」无处判定；③唯一键是「一个上下文一行」→ 无法承载多走查人条目。三条都指向「需要一个带版本与条目的表单模型」，而不是在现表上加列。

  2. **一个 MR 有多条记录几乎全是"多个走查人各一条"（99.3%）**，同一走查人多条仅 12 个 MR（0.7%，且都是 7 天内短间隔）。故：①把一个 MR 的多条合并成一行时，核心是**跨走查人汇总（求和）**；②"同人多条取最新还是求和"这一选择对结果影响可忽略；③老平台 `cleanDumPlicateData`（同人只留一条）**基本生效**，与它的意图一致。**订正记录**：v1.11 的"同一走查人占 77%"（用错列）与 v1.17 的"13.4%／93% 间隔 ≥30 天"（用错键）均作废；正确结论与 v1.10 初判一致——**多条＝多走查人**。
  3. **条目身份是「条目」本身，不是「人」（用户 2026-09-29 订正，会议原文支撑）**——会议原文：多走查人场景「通过顶部加号按钮新增独立条目」「点击即可新增走查模板填写其他走查人信息」，且「不限制用户填写非自身的走查人信息」。故同一个登录用户可以在一个表单实例里新增**多个**条目，同一个走查人名字也可以出现多次 → 表单**功能上允许**同人（同创建人／同走查人）多条，「同一人只留一条」若需要只是产品层软提示或约束，**不是条目的机制身份**。订正：先前写成「以 (实例, 走查人) 为身份、同人再填即覆盖」是我多加的约束，作废。表单用两个语义不同的动作消歧——**编辑**（改了同一次走查的数据）与**加号新增**（真的又走查了一次）——因此不必替业务猜"是改错重填还是又走查一遍"。老平台存量是每次填写各一条记录，迁移与跨来源合并仍按 D14② 处理。
  4. **下游数据来源随读模式切换，两种模式下行的含义不同**：非法数据页有**两个**加载器——`MatchMode` 走 `CodeReviewMatchModeRecordLoader` 直读兼容表 `code_review_match_mode_records`（一条走查记录一行，`select count(*)` 不去重，`:130`），`Formal` 走 `code_review_formal_records`／`merge_request_fact`（GITLAB 行是一个 MR 一行：`mr.id as merge_request_id`，实测 10,010 行 / 10,010 MR；LEGACY 转正式行是一条走查记录一行：按记录建键，只读推演 30,508 行 / 25,651 MR）；当前设置 `code_review_read_mode = compatibility` 故走前者。同一 MR 的行数因此随读模式变化（实测：CC／CrownCAD 非法集 8,545 行 vs 去重 7,303 MR）。见 D14。
  5. 存量：`collect_form_records` 在本地开发库 **0 行**（`deleted=false`；同 MR 多行 = 0）→ v1 表单从未被真实使用；D13 的 v1→v2 迁移在本地是空集，内网存量须在实施前确认。

### 5.6 表单取代评论后的统计影响（用户 2026-09-29 提出；本单元只记录，不实施）

### 5.7 模板版本化与同模板跨版本迁移（D13 的机制设计）

**用户的版本语义（2026-09-29 确认）**：表单类型几乎是固定的（代码走查表、响应模板、回复模板等），但每个模板会随版本演进增删改字段；**字段一变，底层就是一张新表**，但业务身份仍是同一个模板 → **必须把该模板的历史数据一次性迁移到新版**。例：响应模板改了某个字段，响应模板的历史数据仍要迁进新版的响应模板表。不同模板之间不迁移。

**机制（六件套）**

1. **模板身份与版本分离**：模板有稳定 `template_key`（如 `code_review`、`issue_response`），版本是它下面的序列（v1、v2…）。物理表名含版本：`form_<template_key>_v<n>`（含主表与条目表两张）。业务的"同一个表单"= 同一个 `template_key`，与物理表无关。
2. **元数据表（阶段一新增）**：
   - `form_template_definitions`：`template_key`、显示名、当前版本、状态。
   - `form_template_versions`：`template_key`、`version_no`、物理表名、`field_spec`（jsonb 字段定义）、`migration_spec`（jsonb，见第 3 条）、发布时间。
   - 应用与事实层**只从元数据读当前版本表名**，不在代码中硬编码表名。
3. **迁移规格显式化（`migration_spec`）**：每个新版本必须随发布声明"上一版本 → 本版本"的映射，包含：
   - 字段映射：等价改名、类型转换、新增列给常量/默认值、删除列（丢弃或保留在老表）；
   - 结构变化：如 v1「一行表单」→ v2「主表 + 一条目」的行→主+子拆分，需声明实例键与条目字段归属。
4. **迁移执行**：以 Flyway 迁移脚本形式随版本发布（`V…__migrate_form_<template_key>_v<n-1>_to_v<n>.sql`），单事务内 `INSERT … SELECT` 完成后写入一条迁移审计行（模板、from/to、迁移行数、执行时间）。以实例键去重，重复执行不会写重复。
5. **迁移校验（同一工作单元内自动化）**：行数守恒（v1 行数 = v2 实例数 = v2 条目数，当结构为行→主+子时）；关键字段逐一比对（改名/转换后值相等）；若该模板已接入事实构建，重算后相关产出（如 `merge_request_fact` 的对应列）与迁移前一致。
6. **读取规则与历史可见**：读取只针对当前版本表——迁移保证数据都在当前版本里，因此**不做跨版本 union/视图**（避免字段语义漂移把查询 SQL 越拖越脏，也符合会议"避免新旧数据统计冲突"）。老版本表保留只读，注册进数据库查看作为历史版本；版本号同时落在记录列（`template_key` + `template_version`，自描述，便于导出与按版本号 URL 查看）。

**「历史数据在新表里」的确切含义（防止误读）**

三种说法必须区分清楚，否则会得出不同设计：

| 说法 | 是否成立 | 说明 |
| --- | --- | --- |
| 同模板的历史数据**在新版本表里** | ✅ 成立 | 跨版本迁移即将旧版本数据按新结构一次性迁移至新版本表；迁移完成后，新表覆盖该模板的**全部历史数据** |
| 表单系统**不读老版本表**、不做跨版本 union | ✅ 成立 | 页面/接口/导出只对当前版本表工作 |
| 历史数据**不在新表里**（留在老表） | ❌ 不成立 | 这是常见的误读；若如此则表单页与统计会看不到历史，立刻需要 union 或回落老表 |

**两个版本相关字段的语义（执行方案需锁定）**：

- `template_key`：模板身份，跨版本不变；业务上"同一张表"由它界定。
- `template_version`：记录该行数据**产生时**的模板版本（v1 迁移过来的行仍标 1），而不是"它当前所在表的版本"。这样才能让消费侧识别算法变更点与"该行缺哪些后加字段"。物理表名（`form_code_review_v2`）表达的才是 schema 版本，两者不可混为一谈。
- **MR 不是版本载体**：带 `template_version` 的是**表单记录**（"这条是当年用 v1 表单填的"），不是 MR（MR 只是 GitLab 实体）。因此**不存在"访问某个版本的表单/某个老 MR → 触发迁移"**：迁移是版本发布期的一次性整表动作，此后任何时刻的访问都只读当前表，旧行随表自带。区分"迁移（发布期一次）"与"访问（任意时刻一次当前表读）"，避免把迁移误当成按需/懒加载。

**由此推出的行为**（写入 §6.3 执行方案）：

- 查询：只查当前版本表；历史行随表自然被带出，无需版本过滤即可覆盖全历史；需要区分代际时按 `template_version` 过滤。
- 页面：按当前版本 `field_spec` 渲染；历史行缺失的后加字段显示为空占位而非报错。
- 编辑：历史行被编辑时按**当前版本**的必填规则要求补填（见「必填不追溯历史行」）。
- 保存与乐观锁：统一走当前版本表与版本列。
- 导出：按当前版本 schema 输出全量行（含迁移来的历史行）。
- 迁移脚本是**唯一**读老表的地方（一次性）；此后老表只有两个用途——①数据库查看追溯（人看）；②被删除字段的回落查询（其他模块，须显式登记）。

**为什么不用「数据留在各自版本表 + 读时 union」**：读侧不用写迁移看似省事，但每个消费方都要自写跨版本映射，SQL 随版本数线性膨胀、字段语义漂移无法集中治理，且老表永久不能被清理——与会议"避免新旧数据统计冲突""历史版本可查"两条目标都相悖。

**两个必须一并定的细节**

- **必填约束不追溯历史行**：新增的必填字段在迁移时允许为空（历史行豁免），服务端必填校验只对新建/编辑提交生效；页面在编辑历史行时提示需补填。
- **删除字段**：老表保留该列只读，新表不再有；不做按字段单独归档的表（避免过度设计）。
- **历史记录没有归属人**：v1 表没有创建账号列，迁移到新表后这些记录的创建账号为空。按归属判定，它们本期**只读**——不可编辑、不可作废；若确需补填新增的必填字段，走 D16 的一次性运维流程（第三轮复核意见）。**内网存量须在实施前确认**：本地开发库 `collect_form_records` 为 0 行（§5.4-F 推论 5），内网行数须用只读查询核对（`select count(*) from collect_form_records where deleted = false`）；若内网同样为空，本规则实际不生效但仍予保留。

**跨版本消费的两条补充规则（用户 2026-09-29 确认）**

- **同名不同义必须在 `migration_spec` 里显式换算**：例如「规范」评分由 0–100 改为 0–5，若不声明换算，历史与新数据不可比；消费侧需能按 `template_version` 识别算法变更点。
- **「迁移不是消费」**：迁移脚本会读老表（`INSERT … SELECT` 的来源），但那是搬迁动作、**不形成业务依赖**，不应被解读为"表单系统依赖老数据"。

**已考虑并否决的方案**：把表单内容存为 `payload jsonb`、字段定义只放元数据，从而"字段变更不必新建物理表"（迁移退化为 JSON 键改名）。否决理由：与会议「字段变更直接新起独立表」的明确要求冲突；平台现有链路（事实层 SQL 按列读取、数据库查看列定义与中文标签、导出列序、黄金快照）都假设**真实列**，JSON 化会让这些链路全部重写；统计侧需要索引与稳定列类型，jsonb 提取会引入额外成本与不确定性。

**维护方式与变更代价（评审意见补充，2026-09-29）**

- **本期元数据如何维护**：本期不提供运行期编辑入口（配置界面在第二期）。模板元数据随版本发布的数据库迁移脚本写入，与代码一同评审（会议亦要求「变更在发版间隙推进、风险提前告知需求方」）。
- **每次字段变更都要走一遍黄金基线回归**：字段一变即新建物理表，事实层合并逻辑所读取的表名与列随之变化，相关黄金基线对照数据必须同步更新并复跑通过。故字段变更的成本为**物理表 + 事实层合并逻辑 + 黄金基线**三处。
- **「登记」与「不再改代码」的准确边界**：登记消除的是平台代码中的模板判断与模板专有权限码；页面结构本期仍写在代码中（§6.5），事实层合并逻辑仍随字段变更调整。

**对本计划的直接结论**：阶段一 v1（`collect_form_records`）→ v2（`form_code_review_v2` 主表 + 条目表）属于**同一模板的版本跃迁**，按上述机制**必须迁移**，且阶段一恰好是最难的一类（结构从"一行"变"主+子"）；把它做对，后续纯字段增删的迁移就是同一机制的低难度复用。

### 6.4 并发与长时停留场景清单

平台现状对并发**没有任何保护**：`collect_form_records` 无版本列（`V20260506_02:94-115`），`save` 是整行覆盖式写入（`CollectFormRecordMapper.java:70-84`），且任何持 `code_review.form.edit` 者都可改任意记录（`CollectFormController.java:98-99`）。以下场景必须逐条落实并测试：

| 场景 | 风险 | 处理要求 |
| --- | --- | --- |
| S1 两人先后打开同一表单页、各自新增条目（含前后脚提交） | ①若保存是整表单覆盖，后保存者会静默抹掉先保存者的条目；②若同名走查人的提示只依据前端已加载的列表，可能重复添加同一走查人的条目 | 按条目增量提交；任何一次保存只影响自己那一条；禁止表单级整体覆盖与"请求里没有就删除"（FR-B5）；保存成功后重新加载全部记录；同名走查人提示在服务端判定（FR-B12、FR-B13） |
| S2 两人并发修改同一条目 | 静默覆盖 | 按条目的乐观锁；冲突按平台既有 `A0409` 语义返回并提示「已被他人修改 → 重新加载」（先例 `DropdownOptionSettingsView.vue:353-357`、`BackupSettingsView.vue:259-263`），前端保留用户输入（FR-B6）。因「创建人」按每个条目各自判定（D10），该场景只剩同一账号多端 |
| S3 同一人双击/网络重试 | 产生重复条目 | 新增条目带客户端去重键，服务端按键去重；按钮 loading 禁用（FR-B7） |
| S4 打开后离开/忘记、长时间挂着 | 对他人**无影响**（前提是无锁设计）；本人会因会话过期导致保存失败，误关页面则直接丢失 | ①不引入占用/预约/锁定并写成自动化测试（FR-B8）；②保存失败（含 401）保留已填内容并可重试（FR-B9；平台已有全局 401 提示 `request.ts:428-435`）；③本地草稿自动留存与恢复（FR-B10）；④未保存离开需确认（FR-B11；先例 `CodeReviewIllegalRuleConfigView.vue:215-258`、`MirrorSettingsView.vue:353-433`） |
| S5 一人作废时另一人在编辑 | 保存可能静默复活或覆盖已作废数据 | 作废为逻辑删除且逐条处理；目标条目已作废时保存返回明确提示，不复活 |
| S6 服务端或网络异常导致保存失败 | 界面可能「看起来成功」 | 保留输入 + 可重试；失败必须如实报告，不得用乐观界面掩盖 |

边界：不做实时协同（无编辑推送、无 OT/CRDT/光标共享）、不做占用/锁定/预约、不做后台自动草稿合并。草稿恢复后提交仍必须通过乐观锁校验，草稿不得成为绕过只读态或他人条目的路径。

## 风险与假设

- **存量数据迁移**：内网 `collect_form_records` 有真实数据（黄金库为空），模型改造必须给出可回退的迁移与守恒校验；缺陷回归须同时验证总量守恒与唯一所有者，不能只看界面数值。
- **统计侧没有消费方**：表单数据要进代码走查/评审统计（`V20260506_02:93`、`GitlabFactSourceSqlProvider.java:201-211`），字段或表结构变化须与统计消费侧同步评估，黄金基线差异必须逐项解释；`form_records` CTE 目前按 MR 聚合单 reviewer，改多条目会改变这个约定。
- **模板集合硬编码的风险**：现有实现只认 `code_review`（`CollectFormService.java:207-209`），若框架沿用硬编码，则「代码自查数据」与会议其余模板每次都要改代码。本期必须做成数据驱动登记（§6.3-11）。
- **AI 自动填充的既有风险（会议 22:45 点名）**：会议提到「AI 存在识别挂在后台的评论页面自动填充信息时容易出 bug 的问题，明确需和袁寄杰核对相关开发细节」。这是既有实践带来的风险，与 S3/S4（长时间停留、会话过期、误关闭）相邻但不相同；须在实施前与该实践相关的开发细节核对一次，确认表单页是否会被同类自动化操纵、以及是否需要防护。
- **正名候选的数据新鲜度**：走查人候选依赖 LDAP 目录，而 `platform_ldap_users` 仅首次登录全量同步 + 各人登录时更新自己那条（见 LDAP 治理方案），新入职/改名人员可能短期缺失；离职人员已不在目录但历史 MR 仍需补填。**因用户已明确禁止自由文本（FR-A8），此处必须给出受控回退**，候选来源与选项见 D15，避免"无法填写走查人"。
- **顺带发现（不属本单元，属兼容模式退出工作单元；结论为读码 + 只读推演，未在真实转正式运行中复现）**：`LegacyPlatformFormalImportService` 转正式时把 `merge_request_id` 写成 `legacy_source_id`（老平台走查表行主键），而 GITLAB 源写的是 `mr.id`（`GitlabFactSourceSqlProvider.java:283`）→ **同一列在两种来源下含义不同**：GITLAB 行 = GitLab MR id，LEGACY 行 = 走查记录 id。由此该路径的冲突键 `(source_system, source_instance, project_id, merge_request_id)` 是**按记录**的（`reconcileRemovedCodeReviewData` 用同一表达式，见 `:425-440`，故重复转正式不会写重复、不是缺陷），后果是 `code_review_formal_records` 成为**在同一张表中混合了两种含义的行**——同一张表里 GITLAB 行是一个 MR 一行（实测 10,010/10,010）、LEGACY 行是一条走查记录一行（只读推演：30,508 兼容行 → 30,508 行 fact 覆盖 25,651 个 MR，4,857 个 MR 多行）。任何按 MR 去重或 join `merge_request_id` 的消费方在 LEGACY 数据下会失配或重复计数。该设计看起来是有意为之（对齐老平台一条记录一行），问题不在"漏了去重"而在"把一条记录一行放进了按 MR 汇总的事实表"。与 D14 同源，本单元不修代码。
- **权限收口副作用（已裁定，实现后须观察）**：A5 收紧为按记录归属判定且不设代改通道（D8/D10），原「有权限即可改」的用户将失去代改能力；若上线后出现真实代改诉求，须另立单元补通道，不得临时放宽这条判定。
- **本地草稿的副作用**：草稿落在浏览器本地存储，共用电脑场景与含敏感内容的表单须在退出登录时清空（FR-B10），且草稿不得被当作已提交数据；恢复草稿后提交必须仍过乐观锁，否则会把陈旧内容写回。
- **版本跃迁的存量处置（已澄清，风险低）**：阶段一后 `collect_form_records`（v1）成为只读历史。因表单数据当前**没有面向用户的统计消费者**（§5.5），迁移与否都不改变任何现有产出；建议迁移以保留将来接链路的连续性（D13）。
- **「可查」入口的期望错位**：数据库查看是运维排查导向的白名单表浏览器（`DatabaseBrowserService:25` 明确「不是任意 SQL 控制台」）；若业务期望「按 MR 查看该表单的全部历史版本」，那不是数据库查看能提供的体验，属阶段二的页面级需求。另：整库备份是回滚手段，不能替代「可查」。
- **老平台并行期**：改造期间老平台仍在产出代码走查非法数据等，两侧不得互相污染；FR-E2 的下线不在本单元范围。
- **身份识别待办**：会议「从 GitLab 跳转链接识别点击用户 GitLab 账号」目前无实现基础（平台侧只有 LDAP 人员与 GitLab 镜像用户，且 LDAP 在职者中有 GitLab 镜像缺失人员），须先调研再决定是否纳入。
- **假设**：会议所述「表单挂载于质量点域名下」与现网部署形态（平台同源前端路由）一致，因此 FR-D1 基本已满足，仅需确认内网访问入口；若实际为独立域名部署，则跨域与登录态共享需重新评估。
