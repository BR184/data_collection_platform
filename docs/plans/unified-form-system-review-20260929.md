## 〇、术语表

本文中"版本""记录"等词有多个含义，先统一如下，避免歧义。

| 术语 | 含义 |
| --- | --- |
| 合并请求（MR） | GitLab 的 Merge Request，本文中"一个合并请求"指一条 MR。 |
| 表单实例 | 某个合并请求下的一张表单。一个合并请求在本期只有一个模板（代码走查表），即一张表单实例。 |
| 记录 | 表单实例下的一次填写，独立编号。会议确定的"多人接力填写、每人一条"即一条记录对应一次填写。 |
| 填写人 | 在表单页面上提交该条记录的登录账号。编辑权限归属按此账号判定。 |
| 走查人 | 记录中的一个字段，表示本次走查由谁执行。**正常流程下与填写人相同**；允许填写非本人（代填），因此模型上可能与填写人不是同一人。 |
| 模板版本（表单结构版本） | 字段集合的版本。字段变更即新建独立物理表，版本体现在物理表名上。 |
| 数据产生版本 | 记录上保存的模板版本号，表示"这条数据是用哪一版表单填写的"，与它当前所在的表无关。 |
| 记录版本号 | 记录每次被更新时递增的序号，**仅**用于编辑冲突检测。与上述两种版本无关。 |
| 历史版本查询 | 第二期的页面功能，用于查看旧版本物理表中的历史数据。 |

**关于"填写人"与"走查人"是否需要区分**：现状下两者实际上是同一个人。对本地 GitLab 镜像中 463 条代码走查评论的实测显示，449 条（97.0%）的"走查人"就是发评论的人，其余 14 条也是同一个人、只是 GitLab 显示名不同（`徐昊2`↔`徐昊`、`lixinran2`↔`李欣然`），**没有任何一条是代填**。方案仍然把两者分开记录，原因有三：①**代填是会议明确要求保留的能力**（"不限制用户填写非自身的走查人信息"），虽极少发生，但保留后两者就不再必然相同；②**编辑权限必须按登录账号判定**——走查人是姓名而非登录身份，历史姓名不可靠、未入职或无账号的人根本无法判定，只有创建账号能唯一确定"谁能改这条记录"；③**审计可读**，审计记录同时留下操作账号与该次填写的走查人，两者不同即可识别出代填。

因此，**正常流程下填写人就是走查人**，填写者不需要做任何额外操作；分开记录只影响服务端判定与审计，不影响填写体验。

## 一、方案概述

平台当前的表单实现仅支持「代码走查表」一种模板，且模板名称、表单标题与操作权限均硬编码在代码与数据库表结构中。本方案将该实现改造为可支撑多模板的表单系统，具体包含三方面的调整：

1. **模板定义改为元数据登记**：模板编码、字段定义及其对应的物理表以数据形式登记在平台模板元数据表中，平台代码不再硬编码模板判断逻辑与模板专有权限码；
2. **数据存储改为按记录组织**：一次填写生成一条记录，同一合并请求下可存在多条记录，每条记录独立编号并记录填写账号；
3. **页面与接口依据当前版本工作**：字段变更时新建独立物理表，同一模板的历史数据一次性迁移至新版本表，页面与接口只访问当前版本表。

本期交付上述框架，并仅以「代码走查表」一个模板作为落地实例。

**关于"不再修改代码"的准确表述**：登记消除的是平台代码中的模板判断与模板专有权限码。本期页面结构仍写在代码中（见第九节第四项）；字段变更时，物理表、事实层的合并逻辑与黄金基线对照数据仍需同步调整（见 3.1）。因此本项目不会因引入元数据而免除上述三类工作量。

## 二、当前存在的问题

| 序号 | 问题 | 说明 |
| --- | --- | --- |
| 1 | 模板不可扩展 | 平台仅识别 `code_review` 一种模板；模板名称、表单标题以及新建、编辑、删除三个操作的权限码均硬编码在代码中。新增或调整模板必须修改代码。 |
| 2 | 字段变更会破坏历史数据的可比性 | 建表注释已声明该表数据将并入代码走查与评审的分析。物理表列固定，字段变更后新旧数据共存于同一张表，统计结果无法横向比较。 |
| 3 | 缺少填写人标识 | 现有表结构中没有记录填写账号的列，因此"仅填写人可编辑其填写内容"这一要求在服务端无法判定。 |
| 4 | 单一记录结构无法承载多人填写 | 现有唯一键保证同一表单上下文只存在一行，重复提交会覆盖既有数据。会议确定的"多位走查人接力填写、每人一条记录"在当前结构下无法实现。 |

## 三、本期建设内容

1. **模板元数据登记**：模板的定义以数据方式登记，具体含义与边界见 3.1。
2. **记录独立提交**：同一合并请求下可存在多条走查记录，每条记录独立编号；不同记录之间互不影响；同一条记录被同时修改时返回明确的冲突提示，不静默覆盖。两人先后新增记录的处理见 3.2。
3. **页面规范**：单列纵向布局；除"补充说明"外所有字段必填；保存后默认转为只读文本，需点击"编辑"后方可修改。
4. **走查人字段采用下拉选择，不允许手工输入**：手工输入会产生错别字、同音字等不一致数据，直接影响统计结果。下拉选项保存人员标识、界面显示姓名，以避免同名人员混淆。
5. **时间字段仅保留创建时间与最后修改时间**：页面不提供修改历史；后台保留操作审计（内容与可追溯程度见 5.5）。
6. **输入保护**：未保存内容在本地保存草稿并在重新打开页面时恢复；离开页面前提示确认；会话过期或保存失败时保留已填写内容。

### 3.1 模板元数据登记的含义与边界

**登记的含义**：在平台的模板元数据表中写入该模板的定义，内容为三项：

1. **模板标识与版本**：模板编码、显示名称、当前版本号；
2. **字段定义**：该模板包含的全部字段，逐字段声明英文列名、界面标签、数据类型、是否必填、控件类型，以及下拉选项的数据来源；
3. **物理表指向**：该版本对应的物理表名。

不同模板的字段本就不同，字段定义按模板各写一份，因此字段差异不影响登记本身。以代码走查表与其他模板对比说明：

| 项目 | 代码走查表 | 其他模板（以回复模板为例） |
| --- | --- | --- |
| 字段 | 走查人、走查时间（分钟）、规范、逻辑、性能、设计、其他、补充说明 | 按该模板实际需要填写的字段声明 |
| 字段定义的描述方式 | 每个字段声明英文列名、界面标签、数据类型、是否必填、控件类型、下拉选项来源 | 采用相同的描述方式，另写一份 |

**登记可解决的问题**：平台代码不再硬编码模板判断与模板专有权限码，后续新增模板时不需要修改平台代码中的模板判断逻辑。

**登记不能免除的工作**：以下四项仍需逐个模板完成。

| 仍需完成 | 原因 |
| --- | --- |
| 创建该模板的物理表 | 会议要求字段变更时新建独立表；平台现有统计链路按真实列读取数据，字段仅存在于元数据中无法被消费。 |
| 保证字段定义与物理表结构一致 | 元数据中声明的字段必须在物理表中真实存在。本期将增加自动校验，不一致时直接报错。 |
| 配置该模板的权限码并授予角色 | 现有权限码属于该模板专有；新模板需要各自配置一套。 |
| 确定该模板数据的消费方、可填写人员与下拉选项来源 | 不同模板的适用范围不同，需逐个模板配置。 |

**元数据在本期如何维护**：本期不提供运行期编辑入口（配置界面在第二期）。模板元数据随版本发布的数据库迁移脚本写入，与代码一同评审，符合会议"变更在发版间隙推进、风险提前告知需求方"的要求。

**每次字段变更都要走一遍黄金基线回归**：字段一旦变更即新建物理表，事实层合并逻辑所读取的表名与列随之变化，相关黄金基线对照数据必须同步更新并复跑通过。因此字段变更的成本为物理表、事实层合并逻辑、黄金基线三处，并非一次简单的登记。

**本期适用范围**：仅登记并落地「代码走查表」一个模板。回复模板、响应模板等虽在框架设计上可支持，本期不为其建表、不编写页面，后续需要时再按上述流程逐个完成。

### 3.2 两人先后新增记录的处理

**问题**：两位走查人先后打开同一个合并请求的表单页，各自新增一条记录（可能前后脚提交）。若保存以整张表单为单位，后提交的人会覆盖先提交的人已保存的记录。

**处理方式**：

1. **每条记录独立提交**：保存请求只携带当前这一条记录，服务端只写入或更新这一条；不得因请求中缺少其他记录而删除它们。因此甲、乙先后新增的两条记录在保存后同时存在，任一方都不影响对方。
2. **保存成功后重新加载全部记录**：保存成功后页面重新加载该表单下的全部记录，使填写人能看到他人刚新增的条目。本期不做实时推送，仅在保存成功后刷新。
3. **同名走查人的提示在服务端判定**：新增时若该表单下已存在同一走查人的记录，页面给出提示。判定**按人员标识**（下拉已保存人员标识），不按姓名，否则两个同名的不同人会被误判为同一人。该判定必须在服务端提交时执行，不能只依据页面已加载的列表——列表可能已经过期，他人刚新增的记录不在其中。**接口需支持二次提交**：首次提交命中同名且未带确认标记时返回"需确认"结果且不写入；用户确认后带确认标记重新提交才写入。提示之后仍可继续新增，不做唯一性限制。
4. **同一记录的编辑冲突**：编辑权限按记录归属判定，只有填写该记录的账号可编辑，因此两位不同人员不会同时编辑同一条记录。该项冲突覆盖"同一账号在多台设备或多个标签页同时编辑"与"重复提交"两种情形；其中编辑冲突由保存时比对记录版本号识别，重复提交由新增请求携带的请求标识识别（新增时还没有记录版本号）。冲突时提示"已被他人修改，请重新加载"，不静默覆盖。

以上四种情形均需有自动测试覆盖，共四个场景：甲、乙交叉新增；同一人在两个标签页分别新增；同一账号在两处编辑同一条记录；同名走查人提示在服务端判定并能二次确认提交。

## 四、页面形态

打开某一合并请求的表单页面后：

- 页面提供跳转到该合并请求的链接。会议确认表单内不需要展示上下文信息。
- 页面按"一位走查人的一次填写"分块展示。每块包含以下字段：走查人（下拉选择）、走查时间（分钟，表示本次走查的时长）、规范／逻辑／性能／设计／其他（表示各类问题的数量）、补充说明（选填，其余字段均为必填）。
- 页面提供"+"按钮，用于新增一个填写块，供下一位走查人填写。
- 每个填写块保存后转为只读文本；仅填写该块的人员可再次点击"编辑"进行修改。
- 对本人填写的记录，页面提供"作废"操作（保留现有表单页已有的作废入口），点击后需二次确认；作废后该记录不再参与统计。他人填写的记录不显示该操作。
- 填写块内容被修改后，在块下方以灰色小字显示最后修改时间。

## 五、数据存储

**5.1 表结构**：表单数据分为两张表。一张记录"某合并请求的某张表单"；一张记录"该表单下的每一条填写记录"。记录表至少包含以下列：

| 列 | 用途 |
| --- | --- |
| 记录 id | 独立编号，由服务端在写入时分配全局唯一主键（数据库序列），不使用表单内序号，并发写入不会重号。 |
| 创建账号 | 编辑权限的归属依据。**与走查人字段分离**，因为允许代填，两者可能不是同一人（正常流程下两者相同）。 |
| 记录版本号 | 每次更新递增，仅用于编辑冲突检测。 |
| 创建时间、最后修改时间 | 页面展示这两项时间。会议确定其用途之一是校验响应是否延期。**不承担编辑冲突检测**，冲突检测由记录版本号负责。 |
| 数据产生版本 | 该记录填写时所使用的模板版本号。 |
| 新增请求标识 | 客户端在提交新增时生成的标识，用于识别重复提交。该列带**唯一约束**（只靠应用层判重，并发下仍可能写入两条）。同一标识的重复提交**返回首次写入的那条记录并视为成功**，不提示冲突。标识随记录长期保留，不设短期过期；该列**允许为空**（迁移来的历史记录没有该标识），空值不参与唯一性判断。 |
| 作废标记 | 逻辑删除标记。作废记录不参与事实层合并与统计（与现状一致：事实层只看未作废的记录）。 |
| 业务列 | 按该模板字段定义生成的列，例如走查人、走查时间（分钟）、各类问题数量、补充说明。 |

**5.2 模板元数据**：模板编码、字段定义与物理表名称存储在模板元数据表中，应用代码不硬编码。本期**没有运行期的维护入口**，模板元数据只随版本发布的迁移脚本变更，维护范围限于内部开发人员（与 3.1 一致）；配置界面在第二期实现。

**5.3 版本处理**：字段发生变更时新建独立物理表。同一模板的历史数据在新版本发布时一次性迁移至新版本表。页面与接口仅访问当前版本表，不进行跨版本联合查询。

**5.4 迁移时新增必填字段的处理**：新增的必填字段在历史数据迁移时允许为空，属历史数据豁免；服务端的必填校验只对新建与编辑提交生效。用户编辑历史记录时，页面提示需要补填这些字段。

**5.5 操作审计与可追溯程度**：页面不提供修改历史，追溯依赖操作审计表。现有审计表每次操作写入的是**操作后的记录全量快照**（含操作人、IP、浏览器信息），**不单独记录字段级前后值**；因此字段级追溯需要通过比对同一条记录相邻两次快照实现。记录改为多条结构后，审计快照必须落到记录一层，否则同一表单内多条记录的变化无法区分。

**5.6 本地草稿**：草稿保存在浏览器本地。共用电脑场景下存在泄露风险，因此退出登录时必须清空草稿；草稿恢复后提交仍须通过记录版本号校验，不得以草稿内容覆盖服务端已更新的数据。

## 六、权限

| 角色 | 权限 |
| --- | --- |
| 填写人（登录账号） | 打开表单链接并填写；仅可编辑**本人账号填写的**记录。归属依据是记录的创建账号，不是走查人字段。 |
| 内部开发人员 | 与填写人相同；另可通过随版本发布的迁移脚本维护模板元数据（本期无运行期配置界面，第二期实现）。 |
| 管理员／运维 | 本期不提供代他人修改表单的能力；后续如确有此需求，另立工作项（见第九节第五项）。 |
| 业务侧普通用户 | 与填写人相同（本期不提供模板元数据入口，该入口自第二期起仅对内部开发人员提供）。 |

**记录作废**：本期**提供作废功能**，但权限收到本人——仅填写人自己可以作废本人填写的记录，页面需二次确认，不设代作废。权限按"本人删除"授予填写人角色（平台在评审域已有同类的"本人删除"先例），不使用"有权限即可删除任意记录"的语义。该建议列入第九节第五项，请评审确认。

**历史记录**：迁移来的历史记录没有创建账号，按归属判定本期**只读**——不可编辑也不可作废；确需补填时走第九节第五项的一次性运维流程。本地开发库中该表为 0 行，内网存量需在实施前用只读查询确认。

**填写人离职或账号停用后的处理**：由于编辑权限按记录归属判定且不设代改通道，该情形下记录保持只读。是否需要补充受控的处理通道，列入第九节第五项。

会议允许填写非本人的走查人姓名（即代填），本方案在功能上保留该能力，但实际流程中极少出现。据此，编辑权限按记录归属判定，不额外为代填场景提供代改权限。

## 七、对现有统计的影响

1. **本期不改变任何现有页面。** 当前代码走查非法数据页面、各统计看板与 BI 图表的数据来源均为老平台同步的数据，没有任何一处读取该表单。因此本期改造表单不会改变任何现有页面的数据。
2. **需调整一处底层合并逻辑。** 表单数据会并入底层的合并请求数据表，本期需同步调整该合并逻辑，并按平台既有的黄金基线回归流程核验：先展示差异，确认属于有意的变更，再更新基线对照数据，最后复跑通过。字段变更时该回归需重新执行（见 3.1）。
3. **关于"一个合并请求显示一行"的建议不在本期生效。** 第九节第二项所列的显示与计算规则，属"由表单提供数据、平台自建非法判定"接入时才启用的目标规则，属第二期。本期不改动非法数据页面，因此与第 1 条不矛盾；第二期接入时按有意变更处理（路线见配套底稿第 5.8 节）。
4. **"由表单替代评论、进而替代老平台"属于后续工作项。** 该项需新建"表单 → 代码走查统计"的数据链路，并重新定义代码走查异常的判定类型，范围大于表单框架本身，本期不涉及。

## 八、本期不含范围

- 不实现多人实时协同编辑。
- 不实现记录占用或锁定（页面长时间停留不影响他人填写）。
- 不强制将表单账号与 GitLab 账号绑定。
- 不实现向 GitLab 评论回写（第二期实现）。
- 不实现模板元数据的可视化配置界面（第二期实现）。
- 不实现页面按字段定义自动生成（见第九节第四项）。
- 不新增"代码自查数据"模板（按老平台现有处理方式，保持现状）。
- 不承担老数据采集平台的下线工作。

### （二）一个合并请求存在多条记录时，页面与统计的计算方式（本期仅确认方向）

- 字段语义：走查时间（分钟）是**时长**；规范／逻辑／性能／设计／其他是**各类问题的数量**（老平台按五者相加得到缺陷总数）。
- "走查日期"不是表单字段：表单只有创建时间与最后修改时间，统计所用的走查日期由**记录产生时间**派生。**表单场景建议取创建时间**——创建时间不随编辑后移，而最后修改时间会因一次编辑而顺延、甚至跨到下一个统计周期。因此有两处需在第二期接入时确认：①**取首次还是末次**——本方案建议取最早（首次走查），而现有事实层取的是最晚，两者不一致；②**填表时间不等于走查实际发生的时间**，两者可能相差数天，统计使用方需要知悉。
- 现状：非法数据页面当前一条记录显示一行，同一合并请求会出现多行。
- 建议的目标规则：页面以一个合并请求为单位显示一行，总数即非法合并请求数；走查人姓名去重后拼接、按最早一次走查日期排序；走查工作量（时长）相加；缺陷数按五项相加；走查日期取最早；新增代码行数不重复累加。
- 需与统计使用方确认的业务含义：全部相加意味着两位走查人报告**同一缺陷**时会被计为两次，缺陷数偏大，接入前需确认是否接受。
- 生效时点：本期不改动该页面，该规则在第二期接入时启用（见第七节第 3 条）。

### （三）走查人下拉选项的来源

- 建议：候选取自平台人员表（含已离职但表中仍有记录者），可覆盖新入职、改名、离职三类缺口；下拉保存人员标识、界面显示姓名，落库同时保存人员标识与该次填写的权威姓名。
- 待确认三点：①**同名提示与判重按人员标识**（不按姓名）；②**统计按姓名会把同名的两个人合并**为一人，这与现状一致，但需统计使用方确认可接受；③**人员表之外的走查人**（外包、非本公司人员等）目前没有任何登记途径——需确认内网是否存在这类走查人，若存在必须补一条人员补录流程。
- 不采用：直接使用历史上手工输入过的姓名字符串作为候选（会把历史错别字带入候选），以及允许手工输入姓名。

### （四）本期页面是否依据字段定义自动生成

- 建议：**本期不做**。目前只有一个模板，配置界面在第二期，自动渲染的投入在本期难以产生回报。
- 若采用该建议，需同时承诺：**服务端的必填与类型校验仍按元数据中的字段定义执行**，使字段定义成为校验的唯一来源；并在文档中如实说明"页面结构本期仍写在代码中"，避免与第一节"不再硬编码"产生落差。
- 若本期要做：后续新增模板时，只要字段类型属于通用能力范围（文本、数字、下拉、多行文本），即不需要编写页面代码，但本期工作量增加。

### （五）记录作废与账号停用后的可维护性

- 记录能否作废、谁可作废：**保留作废功能，但权限收到本人**——仅填写人自己可作废本人填写的记录，页面二次确认，不设代作废；权限按"本人删除"授予填写人角色（现有表单页已有作废入口与确认弹窗，本期沿用）。
- 填写人离职或账号停用后记录变得无人可改：按现有决定不设代改通道。**建议的过渡做法**（采纳第二轮复核意见）——本期先约定一条**带审计、需负责人批准的一次性运维处理流程**，按记录逐条处理，该做法不改变归属判定，也不需要现在新立工作项。**批准人角色与审计留存位置须在执行方案中写定**（建议由该模板所属团队负责人批准，审计写入操作审计表），不得只作口头约定。
