## 目标与边界

### 用户目标

1. 对 GitHub 已推送的最近一版全部更新做一次整体测试。
2. 第一轮发现的所有问题先统一标记，全部测试完成后再集中修改，避免边测边改掩盖其他失败。
3. 修复后执行完整复验；全部通过才按内网离线打包标准生成保数据更新包。
4. 将当前已应用 721 更新包的内网实例升级到前端端口 `20001`，保留现有容器和数据卷身份。

### 成功标准

- 后端完整测试、生产构建、Checkstyle、SpotBugs 和项目支持的覆盖率门禁通过；前端完整 Vitest、类型检查、ESLint/项目既定 lint 入口和生产构建通过。
- Flyway 不可变性、破坏性迁移审查、自测、profile 覆盖、源码/JAR 集合、空库迁移与 721 基线升级验证通过。
- 同步物理删除、事实目标、publication fence、工作区刷新、统计/记录/导出等本轮高风险链路有自动化与代表性运行验证。
- 所有仓库门禁、打包契约测试、计划解析和产物独立审计通过；任何既存用户文件造成的门禁阻塞均明确列出，不擅自删除。
- 在独立 Compose 栈完成“721 直接基线 -> 新版升级 -> 应用回滚 -> 再次升级”，前后端健康、Flyway 正确、备份可恢复、`counts.diff` 为空、PostgreSQL 容器 ID 与关键表行数守恒。
- 20001 现场升级前后 PostgreSQL 容器 ID、external volume、Compose project 和数据保持不变；目标前后端镜像、健康、端口、Flyway、代表 API/页面和本次同步删除链路验收通过。

### 明确禁止

- 第一轮测试尚未全部结束时不得修改业务代码、测试期望、迁移或打包脚本。
- 不使用 `docker compose down -v`，不删除或重建现场 PostgreSQL 容器，不更换、复制或清空其 volume，不执行手工生产 DDL/DML。
- 不以全新空平台包覆盖现场，不跳过打包器默认构建/测试/归档门禁，不手工拼装更新包。
- 不把 20260721 字样、容器创建时间或历史文档当作直接基线；必须以现场合并 Compose 的实际前后端镜像与上一成功包清单交叉确认。
- 不回退或删除用户既存工作树改动、运行日志和其他项目文件；不把本工作单元之外的改动提交到发布。

## 约束与背景

- 源码基线必须是 GitHub `origin/main` 当前提交；测试期间若远端主线变化，停止并重新建立代码版本基线，不能混合两个提交的结果。
- 更新包以 20001 实例当前成功部署的完整 Compose 为唯一直接基线；用户描述的“721 更新包”必须映射到可审计 release ID、镜像和 `RELEASE-MANIFEST.json`。
- 现场唯一配置模型为一个完整 `docker-compose.yml` 加现场 `.env`；发现 override 或多个有效 Compose 时停止部署，先查明配置事实。
- 更新包不得包含真实 `.env`、PostgreSQL 镜像、数据库 dump、volume 数据、裸后端/前端产物或运行日志。
- 本轮涉及 Java 21、Spring Boot、MyBatis-Plus、Vue 3、TypeScript、Vite、PostgreSQL/Flyway、Docker Compose v2 和 Ubuntu 24.04 amd64 离线发布。
- GitLab 源库只读；删除链路的现场测试必须使用隔离业务对象，并在执行前确认不会修改既有业务记录。

## 方案与步骤

### 阶段 0：冻结基线与定位现场

1. 记录本地/远端提交、工作树、Java/Node/Maven/Docker/Bash 版本和可用测试入口。
2. 定位 20001 实例主机、SSH/受控操作入口、唯一部署目录、Compose project、现场 `.env`、前后端镜像、PostgreSQL 容器 ID、volume 与 Flyway；读取其最后成功更新包清单。
3. 证明现场直接基线与 721 更新包目标镜像一致，记录受保护表行数与当前运行任务；证据不一致则停止。

### 阶段 1：第一轮全量测试，只登记不修复

1. 仓库门禁：工作树产物、运行产物位置、文本空白、`git diff --check`、跟踪文件和仓库自定义静态契约。
2. 后端：完整测试、生产编译/打包、Checkstyle、SpotBugs、覆盖率及定向高风险测试。
3. 前端：完整 Vitest、类型检查、项目 lint、生产构建及发布测试。
4. 数据库：Flyway checksum/破坏性审查/自测/profile/源码-JAR 集合、空库迁移、schema 漂移和 721 数据副本升级烟测。
5. 打包：打包器单元/契约测试、`--plan-only` 及脚本 Bash 语法，但不生成正式交付包。
6. 运行：使用隔离本地数据与端口验证健康、认证、关键 API/页面，以及物理删除到 ODS/事实/投影的代表链路；真实 GitLab 只进行已授权的隔离对象测试。
7. 所有失败登记完成后冻结问题清单，区分产品缺陷、测试缺陷、环境阻塞、既存用户文件和非阻塞告警。

### 阶段 2：统一修复

1. 按严重度和共同根因归组，先补稳定复现或回归测试，再修改单一权威实现与全部调用者。
2. 不保留废弃内部路径、别名、双轨兼容或只为旧测试通过的错误行为。
3. 每组修复只运行最小充分定向验证；所有问题关闭后进入完整复验。

### 阶段 3：完整复验

1. 在同一最终提交/工作树状态重新执行阶段 1 的全部自动化与运行门禁。
2. 检查差异、迁移不可变性、敏感信息、文档新鲜度和问题清单关闭证据。
3. 任何失败返回阶段 2，不能带失败打包。

### 阶段 4：正式打包与隔离升级验收

1. 以 20001 实例最后成功 721 包目录或其受控部署目录副本作为 `--baseline-dir`，根据直接基线代码差异决定事实重建范围。
2. 先执行 `--plan-only`，确认基线、包类型、目标镜像和事实范围，再使用完全相同参数正式无缓存打包。
3. 独立审计 manifest、SHA-256、归档内容、包内校验和和 Bash 语法。
4. 在独立 Compose project、端口和 PostgreSQL volume 上复现 721 基线，执行备份、升级、应用回滚、再次备份与再次升级；证明 PostgreSQL 容器 ID、数据和行数守恒。

### 阶段 5：20001 现场部署与验收

1. 再次只读确认直接基线、无活动同步/事实任务、磁盘、健康、容器/volume ID 和关键行数；执行包内 `backup.sh` 并验证 dump、校验和与恢复目录。
2. 使用同一备份目录执行包内 `upgrade.sh`；脚本必须原子替换唯一 Compose，不修改 `.env`，只重建应用服务。
3. 验证目标镜像、20001 HTTP、后端健康、Flyway、容器/volume 身份、`counts.diff`、关键 API/页面、后台调度恢复和运行诊断。
4. 按发布清单执行必要的事实重建；GitLab 全量同步/补偿只在清单和既定首次历史清理要求明确时执行，不能用作日常链路兜底。
5. 使用隔离业务对象验收自动增量与手动刷新对真实物理删除的 ODS、事实、统计/记录投影收敛，并确认无关表格不变。

### 阶段 6：收尾

1. 将最终 release ID、归档路径/大小/SHA-256、基线、Flyway、事实范围、隔离与现场证据写入 `docs/progress.md`。
2. 检查 `docs/architecture.md`、ADR 和发布 runbook 是否仍与实现一致；只更新发生变化的权威事实。
3. 删除已完成的本活动计划及已无未完成事项的前置计划，运行最终仓库门禁。
4. 若本工作单元产生已验证且职责单一的仓库修改，按 Git 规则提交；推送远端必须由用户或既定发布流程明确，不能猜测。

## 风险与假设

- 20001 实例可能只能从另一台内网主机访问；连接信息不足时只完成可验证的本地测试与打包准备，不猜测主机或凭据。
- 现有根目录运行日志可能继续阻断产物位置门禁；它们属于用户文件，第一轮登记后由用户授权或既有活动计划处置，本工作单元不擅自删除。
- 721 基线若没有完整 manifest 或现场已被手工修改，commit diff 不能证明镜像内容；必须先恢复可追溯基线，否则不打包。
- 全量测试可能依赖本地 PostgreSQL、GitLab、LDAP 或兼容模式服务；环境失败须先证明是环境还是代码，不能修改断言掩盖。
- 最近提交包含 117 份 Flyway 迁移与高并发同步状态机，测试必须防止连接真实内网库或破坏现有开发数据，写入型验证只用隔离数据库/对象。
- 现场部署具有外部状态变化；升级脚本执行前必须具备有效预部署备份并再次核对精确目标，任何不一致立即停止。
