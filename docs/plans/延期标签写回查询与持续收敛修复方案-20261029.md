# 延期标签写回查询与持续收敛修复方案

## 一、结论与取舍

| 症状 | 根因 → 改动 | 不选的方案与原因 |
| --- | --- | --- |
| 查询30秒超时 | 谓词不匹配部分索引 → 统一谓词、补议题索引 | 不扩大超时，重复全扫仍会发生 |
| 剩余任务等一小时 | IDLE来源未重新申请授权 → 条件UPDATE推回REQUESTED | 不加版本记账字段，阶段条件已能去重 |
| 失败后重复重查 | 唤醒提前了next_check_at → 有失败计数时保留退避截止 | 不加重试时间列，现有字段足够 |
| 慢HTTP拖延调度 | 发送占用公共调度线程 → 专用单线程执行器 | 不增加发送并发，先修线程归属与空等 |

**待审批：新增持久字段0、类0、表0、迁移0；在现有配置类增加1个执行器Bean。**

## 二、查询与索引

- `FactBuildService.loadOpenCustomerIssueFacts`、队列服务的`loadCandidates/loadCandidate`三处读取统一使用`mirror_deleted = false`。
- 已查明：ODS由`GitlabMirrorSchemaService`动态建表/补列，DDL均为`mirror_deleted boolean not null default false`；NOT NULL契约在动态DDL中，不在Flyway静态建表脚本中。
- `GitlabMirrorIndexCatalog`新增`issues(project_id,iid) WHERE mirror_deleted=false`，通过现有准备路径为新表、既有表补齐；复用已有标签关联索引。
- 临时索引与正式索引定义相同则保留复用；不同则在正式索引生效后执行`DROP INDEX CONCURRENTLY <临时索引名>;`。具体名称取最后一节所需DDL。

## 三、来源恢复

### 最小方案

在现有进度仓库增加一段条件UPDATE，由同步/事实终态事件、worker发现版本过期、60秒恢复检查共用：

| 条件 | 更新 |
| --- | --- |
| 当前配置写回开启、来源匹配；`stage=IDLE`；`authorized_fact_version < 当前来源ISSUE版本`；存在`PENDING/RETRY_WAIT/RUNNING`作业 | `stage=REQUESTED`、`request_revision=request_revision+1`；按下述退避规则设置`next_check_at` |

条件判断与更新同一条SQL执行。随后走现有前置刷新、事实收敛、重算、授权和入队流程，不修改旧任务版本号直接放行。

### 并发序列与判断

| 具体先后顺序 | 判断 |
| --- | --- |
| A、B同时发现过期；A先将IDLE改REQUESTED，B随后更新 | B重检阶段后更新0行，不产生第二轮；无需去重字段 |
| 事件检查时仍在ENQUEUE，返回0；之后本轮结束回IDLE，授权已过期 | 60秒检查再次执行同一SQL，补上请求；无需记录目标版本 |
| A登记REQUESTED后进程退出，B重启检查 | 请求已落库，原进度领取继续；无需新增恢复状态 |
| 本轮尚在WAIT_FACT/ENQUEUE时版本再次变化 | 现有版本复核拒绝旧授权、等待重评估；若最终回IDLE仍有过期工作，由同一SQL接续 |

这些序列可由阶段条件、现有领取围栏和周期检查处理，没有需要新增持久字段的反例，删除上一版两个字段及配套迁移。

### 失败退避与旧任务结算

- 事件和周期请求在`failure_count>0`时使用`next_check_at=GREATEST(next_check_at,CURRENT_TIMESTAMP)`，否则允许立即唤醒。重试开始不清零，成功越过失败步骤后才清零；保留1/5/15/30/60分钟退避。现有字段能够表达截止时间，不新增列。
- 本轮完整评估结束后，未被本轮重新选中且授权修订过旧的任务，按来源、任务修订及领取围栏结束，避免旧PENDING永久残留。

判定公式与标签结果保持不变；严格版本核验、真实时钟租约、单并发和每次发送前复核继续生效。旧平台继续停写。

## 四、发送调度

在`PlatformAsyncConfiguration`增加专用执行器Bean：线程1、等待队列0，复用worker现有`running`单飞标志；公共调度器只提交任务。

选**每批最多6条**，不另设时间预算。6=30秒÷原5秒间隔，限制一次连续占用的作业数；PUT发起间隔至少5秒，HTTP耗时已超过5秒时立即处理下一条，不再追加空等。每条均重新领取、复核和结算，批末交还执行器。

提交拒绝、执行异常及正常退出均释放单飞标志；未完成任务留在数据库，由下一次触发继续。

## 五、测试验收

先写第2项红测，再改实现；测试只验证本轮新增行为及其保护边界。

| 测试 | 做法与通过标准 | 不做会漏掉什么 |
| --- | --- | --- |
| 1. 查询等价 | 真实PG同一冻结样本结果一致，计划不再逐候选全扫标签关联；新旧ODS均补齐索引 | 判定改变或生产继续超时 |
| 2. 恢复红绿 | 入队→IDLE→部分发送→版本推进；旧版本停发，自动重新授权并完成剩余任务，不触发小时周期 | 仍需人工切开关或等一小时 |
| 3. 恢复语义与并发 | 真实PG合测重复事件、两个推进者、事件丢失、重启、补计划/关闭/删除；断言请求幂等、任务不丢、已成功且一致者不重复PUT，并覆盖旧租约/修订拒绝结算 | 重复轮次、旧任务残留或旧处理者覆盖新工作 |
| 4. 失败退避 | 查询失败后注入事件风暴及周期请求，截止前无重试；恢复后继续，失败事务无残留写入 | 重复重查及半提交 |
| 5. 调度隔离 | HTTP替身用屏障阻塞发送，公共调度器仍能执行短任务；验证单飞、6条上限、拒绝/异常恢复 | 慢GitLab拖延正常同步触发 |
| 6. 连续真实链路 | 本地GitLab前置代理对每个写回PUT固定延迟6秒；15分钟自动同步、1小时检测。准备454条初始差异议题，其中3条在等待时补计划/关闭/删除，余451条需真实PUT。451=⌊3×900÷6⌋+1，故单并发队列必跨至少3个同步周期；各周期均制造ISSUE版本变化，最终积压清空且无重复PUT | 少量静态样本掩盖跨版本恢复缺口 |

运行后端默认套件与发布前黄金严格compare，不更新快照。

## 六、升级、回退与交付

**升级：** 审批后在隔离环境实施，不连生产。更新应用并补动态索引，保留进度和队列；计算规则未变，无需全量同步或事实重建。

**回退：** 关闭新平台写回，恢复兼容旧应用；新增索引保留，旧平台保持停写。

**交付：** `DELIVERY.md`首屏列两项修复结论、候选提交和验收结果；日志放附件。经理复审后决定合入main及打包，测试结束停掉本任务资源。
