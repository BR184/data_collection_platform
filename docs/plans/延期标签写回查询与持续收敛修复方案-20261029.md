## 一、问题与选定方案

| 问题 | 已确认原因 | 选定方案 |
| --- | --- | --- |
| 延期查询30秒超时 | 三处查询使用 `coalesce(mirror_deleted,false)=false`，与现有部分索引谓词不匹配；缺少议题 `project_id+iid` 定位索引 | 统一查询谓词，补动态索引，验证既有库补建；保持全局30秒查询超时 |
| 同步后剩余写回等待下一小时 | 入队结束即回 IDLE；版本变化后 worker 只 defer；终态唤醒与60秒检查不会为已结算 IDLE 登记新请求 | 为过期且未完成的工作持久化一个合并后的来源恢复请求，事件推动、周期兜底 |
| 失败后重复查询 | 运行终态和周期请求可以提前 `next_check_at`，绕过失败退避 | 单独记录失败重试截止时间，普通唤醒不能提前 |
| 慢请求放大积压并延迟调度 | 每次只处理一条，结束后再等5秒；同步 HTTP 直接运行在公共单线程调度器 | 专用有界单线程执行器，有界批次连续发送，保留发送前围栏和限速 |

本地 PostgreSQL16 的机制验证：200条候选、8万标签关联，原查询全扫标签关联200次；只加议题部分索引仍全扫；统一谓词后使用标签关联索引，完整结果摘要相同。该证据证明执行机制，不替代内网容量实测。

## 二、范围与约束

1. 改动限于延期重算查询、动态索引准备、写回进度/队列及发送调度。延期公式、模板/日期判定、关闭议题业务边界、页面与统计口径保持现状。
2. 保留1010同步机制、事实发布协议、授权版本核验与真实时钟租约围栏。旧平台继续停写；不靠关闭自动同步、改旧任务版本号或缩短小时检测周期解决问题。
3. 所有索引和迁移只作用于采集平台自己的 PostgreSQL；本地实现与测试不访问生产 GitLab、生产数据库或凭据，不自动部署。
4. 实施从当时已验证的 main 创建中文任务分支和独立工作树；不从较旧审批目录开发业务，也不带入未完成表单。配置、库、端口、Compose、构建输出与测试 GitLab 均独立。

## 三、查询与索引修复

### 3.1 同时修正三个读取位置

- `FactBuildService.loadOpenCustomerIssueFacts`：延期三列重算。
- `CustomerIssueDelayLabelWritebackQueueService.loadCandidates`：分页入队。
- 同服务 `loadCandidate`：发送前单议题重读。

以上两份 SQL 的 issues、label_links、labels 有效行条件统一为 `mirror_deleted = false`。保持当前来源、项目、时间、关闭状态筛选、标签排序、关联缺失及空标签处理语义；不在此单元改计算规则。

前置核查三张实际 ODS 表的 `mirror_deleted NOT NULL`。代码按此契约建表；若现场结构不符合，停止该来源写回准备并报告结构差异，不静默改变 NULL 含义，也不增加第二套长期查询。

### 3.2 使用现有唯一索引目录

- 在 `GitlabMirrorIndexCatalog` 新增 `issues(project_id,iid) WHERE mirror_deleted=false`；复用现有 `label_links(target_type,target_id,label_id)` 部分索引。
- 由 `GitlabMirrorSchemaService` 控制面准备路径调用 `GitlabMirrorIndexService`，确保既有 ODS 表与新表都补齐，不把 DDL 放入数据批次或发送循环。
- 对本次依赖的索引核对定义及有效性；同名异定义不能当成已满足，更不能自动删除未知归属索引。索引使用并发创建，失败遗留的本任务无效索引按现有机制修复。
- 生产已经补的两条索引先保留。实施交付时列出其与正式索引的关系；只有正式索引有效、执行计划确认后，才给出冗余索引清理步骤，由用户安排执行。
- 保留全局查询超时30秒和进度租约120秒。测量查询、重算、三列更新、generation与授权整个事务；超出预算则阻断验收，不通过提高全局超时或取消租约检查放行。

## 四、持续恢复与失败退避

### 4.1 最小数据变更

复用 `customer_issue_delay_closure_requests`，每个来源仍只有一行，不新增每轮快照或另一套任务表。

| 新增字段 | 类型 | 职责 |
| --- | --- | --- |
| `recovery_requested_fact_version` | bigint，默认0、非空 | 已登记恢复请求的最高 ISSUE 版本，用于合并重复事件与多个旧作业的相同请求 |
| `retry_not_before` | timestamp，可空 | 最近一次推进失败的重试截止；与普通等待/唤醒时间分离 |

追加一份新 Flyway 迁移；版本号在实施时核对主线最新迁移后确定，已有140份迁移内容与编号不变，校验和锁只追加。利用已有队列 `(source_instance,status,next_run_at,id)` 索引做来源级 `EXISTS` 检查，不逐条加载全部作业。

### 4.2 登记恢复请求

新增来源级原子操作 `requestRecoveryIfStale`，由三处复用：相关运行终态、worker发现授权事实版本过期、60秒恢复检查。周期恢复按启用来源检查，既补事件丢失，也补重启后尚未登记请求的情况。

仅当配置唯一、来源和写回开启、存在 `PENDING/RETRY_WAIT/RUNNING` 工作且当前 ISSUE 版本高于授权版本时登记；只有暂时存在在途同步、版本尚未变化时，等待收敛，不重复提交前置刷新。`SUCCEEDED/SKIPPED/DEAD` 历史行不触发恢复。

以数据库行锁或条件更新保证：

- 同一来源/已登记版本重复发现只返回已有请求，不重复推进修订或提交镜像。
- 新版本只抬高恢复目标；当前已挂起下一轮请求时合并到该请求，不叠加无限轮次。
- 已结算 IDLE 进入 REQUESTED；在飞 `WAIT_MIRROR/WAIT_FACT/ENQUEUE` 保留本轮 `processed_revision`、游标与领取身份，最多挂一个后续请求，不抢占当前处理者。
- 目标版本合并、请求修订与阶段更新在同一事务提交；配置关闭/来源切换仍通过现有配置保存事务撤销授权。

### 4.3 恢复后的状态与作业结算

沿用 `REQUESTED → WAIT_MIRROR → WAIT_FACT → ENQUEUE → IDLE`。重新授权前仍需四表刷新完整成功、来源事实收敛、事务重算及版本复核；旧任务不能仅修改 `required_fact_version` 后发送。

| 情况 | 动作 |
| --- | --- |
| 旧任务仍有标签差异 | 按最新事实、ODS标签重建差异，更新授权和任务修订后发送 |
| 已成功且当前标签一致 | 不新增发送 |
| 等待期间补计划时间、关闭、删除或离开范围 | 按当前既有规则处理；无候选的旧任务明确结束，不重放旧 add/remove |
| 本轮完整分页结束 | 分批结算未被本轮重新选中的旧授权待处理任务，再完成进度；旧 RUNNING 由持有者按围栏结束或租约到期后接管，不强清有效租约 |
| 再次发生版本变化 | 立即停止使用旧授权发新请求，并合并新的恢复目标 |
| HTTP已发出后状态变化或结果未知 | 保留现有重读、重试和最终收敛路径，不能承诺撤回已发送请求 |

旧任务清理只覆盖该来源、旧授权修订且本轮已完整评估的范围，按任务修订/所有权保护，不能误清新差异或其它来源工作。`DEAD` 保持现有契约，不自动复活。

### 4.4 退避规则

- 保留现有1、5、15、30、60分钟失败退避；失败更新计数与 `retry_not_before`，普通事件/周期请求不得提前它。
- 领取同时满足普通检查时间和失败重试截止。失败计数只在成功跨过失败阶段或完成后清零，重新领取、收到事件、开始下一次失败重试不清零。
- 相关事件只登记/合并请求并提交短推进；事件回调和公共调度线程不等待同步、查询或HTTP。

## 五、发送调度调整

- `runOnce` 只提交短触发，实际领取、校验和HTTP在专用单线程有界执行器中运行。提交前单飞，执行器等待队列最多1项；拒绝、异常和退出均释放本地单飞标志，数据库任务保留，后续触发可恢复。
- 先维持单实例单条HTTP并发。保留既有5秒配置作为触发间隔和最小PUT起始间隔；API已耗时超过间隔时，不再额外空等5秒。多实例正确性继续由数据库领取和修订围栏保证。
- 初始批预算取最多6条或30秒，先到者停止领取；6条来自默认5秒最小间隔下的30秒预算。已领取任务按现有查询/HTTP超时结束，不因批末时间撤销已发送请求；参数在固定负载验证后确认，不提高请求并发来掩盖恢复缺陷。
- 每条领取后、发送前仍校验配置、最新事实与标签、当前来源版本、授权和租约。旧授权任务由来源恢复流程接管；领取过滤当前进度阶段/授权修订，避免把整批过期任务反复取出再延后。
- 一个来源等待时让出本批预算，不能阻塞其它可写来源。HTTP429、5xx、不可重试4xx、超时及未知发送结果沿用既有分类。

## 六、实施顺序与验收

依次实施：**确定性红测 → 查询/索引 → 来源恢复/退避 → 发送隔离 → 集成验收**。可提交职责单一且已验证的阶段；两项修复作为完整候选交审，不将半成品合入main。

| 必测场景 | 层级与通过标准 |
| --- | --- |
| 原查询与新查询 | 真实PG：同一冻结样本完整结果、延期三列与标签差异一致；覆盖删除标记、无标签、ODS缺失；计划不再为每条候选全扫标签关联 |
| 既有库与新建ODS索引 | 真实PG：均能准备；同名异定义、无效索引、事务外并发创建有明确结果；历史迁移摘要零变化 |
| 入队回IDLE后，发一部分再推进版本 | 先红后绿：旧版本不发送；来源收敛后自动新请求、重算、恢复剩余任务，不等小时触发、不人工切开关 |
| 重复事件与两推进者 | 真实PG：同版本只形成一个合并请求；在途新增版本不被旧结算清除；保留R1–R3所有权、租约到期及整体回滚反例 |
| 事件丢失、重启 | 真实PG：未登记及已登记恢复请求均能由周期检查续接；旧PENDING不永久滞留 |
| 恢复时内容变化 | 合法计划时间、删除/关闭/重开、无差异、DEAD、在途新修订均按当前规则结算；其它来源及无关标签不受影响 |
| 查询失败与失败事件风暴 | 三列与generation回滚、无新入队/PUT；退避正确，普通唤醒不能提前；条件恢复后自动继续 |
| 慢API与线程归属 | 可控时钟/屏障和HTTP替身：公共调度器不被发送占用；单飞、预算、限速、拒绝恢复、429/超时及关闭围栏通过 |
| 连续真实GitLab接替 | 独立平台/GitLab：准备451条有明确差异的测试议题，自动同步15分钟、写回新轮次仍设1小时，至少跨3个真实同步周期；包含队列中途版本变化、评论更新、关闭和删除，最终有穷输入停止后待处理归零，已成功且一致者无重复PUT |

真实链路新增规模用于暴露“队列尚未清空即跨版本”的恢复缺陷，不用于推算内网数据库容量。451条若提前完成，需用受控API延迟构造跨周期队列，不靠关闭自动同步制造通过。固定负载另记录API耗时分布、PUT速率、最老等待时长、各状态数量、重新授权次数及普通同步耗时；有穷积压必须清空，持续新输入超过发送能力时明确报告积压。

最终候选运行相关定向/真实PG套件、后端默认套件和黄金严格compare；不更新黄金快照掩盖差异。正常全量→自动增量交接、手工同步与事实重建触发、代码走查等回归入口按实际影响执行。内网实际表规模的计划、事务耗时、索引I/O与积压由用户安排实测，本地小样本不替代。
