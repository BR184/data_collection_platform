### 1. 下钻表格没有左右滚动条，浏览器缩放<100%时右侧没有占满空间

**问题描述**：
- 下钻明细弹窗在浏览器缩放小于100%时，表格右侧出现空白区域
- 表格主体没有显示左右滚动条

**确切原因**（源码分析）：

`frontend/src/components/StatisticBoardDetailDialog.vue:235-237`
```css
.stat-detail-table-shell :deep(.el-table__body-wrapper .el-scrollbar__bar.is-horizontal) {
  display: none !important;
}
```

**分析**：
1. 原生横向滚动条被强制隐藏，依赖浮动滚动条（Line 278-316）
2. 浮动滚动条显示条件：`hasHorizontalOverflow && (hover || focus || awake)`
3. `hasHorizontalOverflow` 计算基于表格内容宽度和容器宽度
4. 浏览器缩放时，CSS 像素和设备像素比例变化，导致：
   - 表格内容宽度计算不准确
   - `hasHorizontalOverflow` 可能误判为 false
   - 浮动滚动条不显示，又没有原生滚动条
5. 弹窗宽度 `72%`（Line 116）是相对于视口的，缩放后可能不适配

**解决方案**：

**方案1（推荐）：不要隐藏原生滚动条，只在有浮动滚动条时隐藏**
```css
/* 移除强制隐藏 */
/* .stat-detail-table-shell :deep(.el-table__body-wrapper .el-scrollbar__bar.is-horizontal) {
  display: none !important;
} */

/* 只在浮动滚动条可用时隐藏原生滚动条 */
.stat-detail-table-shell.has-horizontal-overflow :deep(.el-table__body-wrapper .el-scrollbar__bar.is-horizontal) {
  display: none !important;
}
```

**方案2：修复浮动滚动条在缩放场景下的检测逻辑**
文件：`frontend/src/composables/useFloatingHorizontalScrollbar.ts`
```typescript
// 使用 ResizeObserver 而不是简单的宽度比较
const observer = new ResizeObserver(() => {
  const table = tableShellRef.value?.querySelector('.el-table__body');
  const shell = tableShellRef.value;
  if (table && shell) {
    // 考虑设备像素比
    const scale = window.devicePixelRatio || 1;
    hasHorizontalOverflow.value = table.scrollWidth > shell.clientWidth + 1 / scale;
  }
});
```

**方案3：优化弹窗宽度适配**
```vue
<!-- 使用固定宽度 + max-width 代替百分比 -->
<el-dialog
  :model-value="modelValue"
  width="1200px"
  style="max-width: 90vw"
  ...
>
```

**代码位置**：
- `frontend/src/components/StatisticBoardDetailDialog.vue:235-237` (隐藏原生滚动条)
- `frontend/src/components/StatisticBoardDetailDialog.vue:278-316` (浮动滚动条)
- `frontend/src/composables/useFloatingHorizontalScrollbar.ts` (滚动条检测逻辑)

### 2. 下钻表头的升降箭头分离，排序按钮崩坏

**问题描述**：
- 表头的排序升降箭头显示异常，箭头和表头文字分离
- 用户认为是表头样式被强制修改导致的

**确切原因**（源码分析）：
`frontend/src/components/StatisticBoardDetailDialog.vue:244-251` 强制将所有 `.cell` 设置为 flex 布局：
```css
.stat-detail-table :deep(.cell) {
  display: flex;
  align-items: center;
  min-height: 24px;
  width: 100%;
  line-height: 1.35 !important;
  overflow: hidden;
}
```

这个选择器同时影响了表头（`th .cell`）和表体（`td .cell`）。Element Plus 的表头排序箭头依赖 `.cell` 的默认布局，强制 flex 后：
1. 表头文字和 `.caret-wrapper` 排序箭头容器被当作 flex 子元素
2. `.caret-wrapper` 的定位逻辑被破坏，导致箭头分离

**解决方案**：
修改 `frontend/src/components/StatisticBoardDetailDialog.vue:244-251`：
```css
/* 只对表体单元格应用 flex 布局，不影响表头 */
.stat-detail-table :deep(td .cell) {
  display: flex;
  align-items: center;
  min-height: 24px;
  width: 100%;
  line-height: 1.35 !important;
  overflow: hidden;
}

/* 保持表头 cell 默认布局 */
.stat-detail-table :deep(th .cell) {
  /* Element Plus 默认样式，不覆盖 */
}
```

**代码位置**：
- 文件：`frontend/src/components/StatisticBoardDetailDialog.vue`
- 行号：244-251

### 3. GitLab 标签颜色未从镜像库 labels 表读取

**问题描述**：
- 所有的 GitLab labels 都需要从数据库镜像库 `labels` 表里的 `color` 列取色

3. **镜像库中有数据**：GitLab 镜像同步会将 `labels` 表同步到本地，`color` 字段格式为 `#6699cc`

**解决方案**：

**步骤1：修改事实层构建，JOIN labels 表获取颜色**

- 在构建 `issue_fact` 时，增加一个 JSON 字段存储标签颜色映射
- 或者在明细查询时实时 JOIN `labels` 表

**步骤2：修改明细查询 SQL，返回标签颜色**
文件：`backend/src/main/java/com/data/collection/platform/service/statistics/*BoardService.java`
示例 SQL 修改：
```sql

-- 修改为返回标签和颜色的映射

  label_names,
```

### 9. 客户问题模块在没有测试阶段 label 时应通过里程碑字段分类

**问题描述**：
- 客户问题模块下的所有页面，在没有测试阶段的 label 时，应该通过"里程碑"（milestone）字段进行分类
- 这是一个特殊的业务逻辑，需要参考老平台的实现

**确切原因**（源码分析）：

**现有实现**：
`backend/src/main/java/com/data/collection/platform/service/statistics/CustomerIssueTestingPhaseFilterSupport.java:93-114`
```java
private static boolean matchesCondition(
    String milestoneTitle,
    String testingPhase,
    StatisticFilterCondition condition,
    SystemTestPhaseScopeResolver phaseScopeResolver,
    List<String> enabledParentNames) {
  String value = TextQuerySupport.trimToNull(condition.value());
  String milestone = TextQuerySupport.trimToNull(milestoneTitle);
  String phase = TextQuerySupport.trimToNull(testingPhase);
  boolean allowedParent = value == null || containsIgnoreCase(enabledParentNames, value);
  return switch (condition.operator()) {
    case "eq" -> value == null || (allowedParent
        && (equalsIgnoreCase(milestone, value) || matchesResolvedPhase(phase, value, phaseScopeResolver)));
    // ...
  };
}
```

**分析结论**：
该代码**已经实现了里程碑降级逻辑**！
- Line 104-105：`equalsIgnoreCase(milestone, value) || matchesResolvedPhase(phase, value, ...)`
- 逻辑：先匹配 `milestoneTitle`，如果不匹配再匹配 `testingPhase`
- 这正是"没有测试阶段时用里程碑"的实现

**问题根因**：
`backend/src/main/java/com/data/collection/platform/service/IssueFactRecord.java:143-150`
```java
public String primaryPhaseLabel() {
  if (hasSystemTestScope(testingPhase)) {
    return testingPhase;
  }
  if (hasSystemTestScope(systemTestLabel)) {
    return systemTestLabel;
  }
  return labels.stream().filter(this::hasSystemTestScope).findFirst().orElse("");
}
```

**真正的问题**：`primaryPhaseLabel()` 只从包含"系统测试"或"回归测试"关键字的字段中提取，完全**忽略了 `milestoneTitle`**！

客户问题的议题：
- 不带"系统测试"/"回归测试"标签
- 但有里程碑（如 `CC2026R3`）
- `primaryPhaseLabel()` 返回空字符串
- 导致客户问题页面无法按里程碑分组

**解决方案**：

**方案1（推荐）：修改客户问题页面使用 milestone 而不是 primaryPhaseLabel**
文件：`backend/src/main/java/com/data/collection/platform/service/statistics/CustomerIssue*BoardService.java`

将所有使用 `issue.primaryPhaseLabel()` 的地方改为：
```java
// 原代码
String phaseKey = issue.primaryPhaseLabel();

// 修改为
String phaseKey = StringUtils.hasText(issue.milestoneTitle()) 
    ? issue.milestoneTitle() 
    : issue.primaryPhaseLabel();
```

**方案2：修改 IssueFactRecord，客户问题场景下返回 milestone**
文件：`backend/src/main/java/com/data/collection/platform/service/IssueFactRecord.java:143`

```java
public String primaryPhaseLabel() {
  if (hasSystemTestScope(testingPhase)) {
    return testingPhase;
  }
  if (hasSystemTestScope(systemTestLabel)) {
    return systemTestLabel;
  }

```

**推荐方案1**，因为：
1. 不影响系统测试模块的逻辑
2. 客户问题和系统测试的分类维度本来就不同
3. 更符合业务语义：客户问题按里程碑分类，系统测试按测试阶段分类

### 14. 单表刷新时间异常，造成一系列表响应缓慢或无法打开

**问题描述**：
- 单表刷新时间异常
- 导致一系列统计看板响应缓慢或无法打开
- 非常容易请求超时

**确切原因**（源码和架构分析）：

**刷新链路**：
1. GitLab 镜像同步：`gitlab_mirror_records` 表
2. 事实层构建：从镜像表构建 `issue_fact`、`merge_request_fact` 等
3. 统计查询：从事实表查询并聚合

**性能瓶颈分析**：

**瓶颈1：GitLab 镜像同步慢**
- GitLab API 响应慢（内网环境网络问题）
- 表同步串行执行，相互阻塞
- 缺少增量同步，每次全量同步

检查方法：
```sql
SELECT 
  table_name,
  started_at,
  finished_at,
  EXTRACT(EPOCH FROM (finished_at - started_at)) as duration_seconds,
  status
FROM gitlab_table_sync_tasks
WHERE started_at > NOW() - INTERVAL '1 day'
ORDER BY duration_seconds DESC
LIMIT 20;
```

**瓶颈2：事实表构建慢**
`backend/src/main/java/com/data/collection/platform/service/FactBuildService.java`

可能的问题：
- 复杂的 JOIN 查询
- 缺少必要的索引
- 全量刷新而非增量刷新

检查方法：
```sql
SELECT 
  task_type,
  started_at,
  finished_at,
  EXTRACT(EPOCH FROM (finished_at - started_at)) as duration_seconds,
  status,
  message
FROM fact_build_tasks
WHERE started_at > NOW() - INTERVAL '1 day'
ORDER BY duration_seconds DESC
LIMIT 20;
```

**瓶颈3：数据库连接池耗尽**
大量同步任务和统计查询同时执行，连接池被占满。

**瓶颈4：锁竞争**
如果事实表刷新使用表级锁，会阻塞查询请求。

**解决方案**：

**短期方案（优化索引）**：
```sql
-- 镜像表索引
CREATE INDEX CONCURRENTLY idx_gitlab_mirror_records_updated 
ON gitlab_mirror_records(table_name, updated_at_source);

-- 事实表复合索引
CREATE INDEX CONCURRENTLY idx_issue_fact_query 
ON issue_fact(deleted, project_id, testing_phase) 
WHERE deleted = false;

CREATE INDEX CONCURRENTLY idx_issue_fact_module 
ON issue_fact(deleted, project_id) 
INCLUDE (module_names, testing_phase)
WHERE deleted = false;
```

**中期方案（增量同步）**：
修改 GitLab 同步逻辑，支持增量同步：
```java
// 只同步 updated_at > last_sync_time 的记录
SELECT * FROM issues 
WHERE updated_at > :lastSyncTime
ORDER BY updated_at
LIMIT 1000;
```

**中期方案（异步事实刷新）**：
- 镜像同步完成后，异步触发事实表刷新
- 不要阻塞用户查询请求

**中期方案（缓存统计结果）**：
```java
@Cacheable(value = "statisticBoard", key = "#boardKey + #filters", unless = "#result == null")
public StatisticBoardResponse loadBoard(String boardKey, Map<String, String> filters) {
  // ...
}
```

**长期方案（读写分离）**：
- 主库：处理写入和事实刷新
- 从库：处理统计查询
- 避免刷新和查询相互影响

**长期方案（物化视图）**：
```sql
-- 预计算的汇总表
CREATE MATERIALIZED VIEW issue_summary_by_module AS
SELECT 
  testing_phase,
  module_name,
  severity_level,
  COUNT(*) as total,
  COUNT(*) FILTER (WHERE is_fixed) as fixed

```
